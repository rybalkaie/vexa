## Пункт 1 плана. Дедуп при записи в реестр по `iCalUID`

### Как именно протянут `iCalUID` (находка Н1: поля в коде не было вообще)

Тянуть пришлось два независимых конца, потому что в реестр пишут два разных пути:

```
Google API ──► lib/gcal.event_ical_uid(event)  ← НОВОЕ, единственное место чтения поля
                    │
                    ├──► scheduler._queue_item()  → элемент .queue.json: "ical_uid", "calendar_id"
                    │        (событие уже на руках: list_instances / get_event)
                    │
                    └──► [вечерний блок] → snapshot → meetings_apply_reply._build_record()
                             → запись watched.yaml: ical_uid / event_start_at / event_url
```

Запросы к Google `fields` не сужают, поле приезжает само — новых сетевых походов ноль.

**Разрыв, который я закрыть не мог, и это честно:** `ical_uid` в snapshot кладёт
`meetings_evening_block.py`, а он вне карты владения (закоммичен фазой 4, править запрещено).
Поэтому в `apply_decisions` точный ключ читается **опционально** (`item.get("ical_uid")`), а
сегодня работает страховка второго уровня. Включение — одна строка в снапшот-блоке вечернего
блока (`"ical_uid": evt.get("iCalUID")` рядом с `"event_id"`), миграции реестра не требует:
`meeting_fingerprint()` и `_same_meeting()` уже понимают оба варианта. Тест
`test_two_calendars_one_record_by_ical_uid` проверяет именно вариант «поле пришло» — он зелёный,
то есть код готов заранее.

### Что кладём в запись реестра и зачем именно это

| Поле | Зачем |
|---|---|
| `ical_uid` | точный ключ: у копий события в разных календарях совпадает |
| `event_start_at` | старт экземпляра. **Обязателен рядом с `iCalUID`**: у всех экземпляров одной рекуррентной серии `iCalUID` ОБЩИЙ (различаются только `id`). Без времени «вторник» и «четверг» одной серии схлопнулись бы в одну запись — бот пришёл бы только на первую |
| `event_url` | вторая половина страховочного ключа «время старта + URL» |

Приметы пишутся в саму запись, потому что сверять их иначе не с чем: в `watched.yaml` нет ни
времени встречи, ни ссылки, а ходить за ними в календарь на каждое «да» — лишний сетевой поход
в пути, который сегодня офлайновый. Валидатор `validate_watched_record` неизвестные поля не
отвергает (проверено), CLI и планировщик их игнорируют — обратная совместимость полная.

### Что будет со старыми записями реестра, у которых примет нет

1. Дедуп **при записи** их не видит (сверять не с чем) — `find_duplicate_watched` такие записи
   пропускает молча. Это осознанно: гадать по одному `title` опаснее, чем не гадать.
2. Их держит **второй рубеж** — схлопывание очереди в `scheduler` по «URL + время старта».
   То есть критерий 9 («один бот») выполняется и для целиком старого реестра, ещё до того как
   в нём появится хоть одна примета.
3. Реестр **лечится сам**: `_merge_fingerprint()` дописывает недостающие приметы каждый раз,
   когда владелец касается записи (сказал «да» повторно, передумал, отказался). Чужие значения
   не перетираются — только пустые поля.

### Отказы владельца (ISS-53) — не сломаны, наоборот

Дедуп ищет **и среди выключенных записей**: отказ — это тоже «встреча известна». Три эффекта:

- «да» по копии из второго календаря поверх отказа → оживает ТА ЖЕ запись (метки отказа сняты),
  вторая не заводится (`test_yes_on_twin_of_rejected_meeting_does_not_add_second_record`);
- «нет» по копии → гасится запись-близнец, по которой бот реально приходит. Раньше отказ
  завёл бы вторую выключенную запись, а бот всё равно пришёл бы по первой — то есть «нет»
  было бы услышано только на словах (`test_no_on_twin_disables_existing_record`);
- «не предлагай эту серию» по копии → глушится запись-близнец (`test_never_on_twin_mutes_existing_series_record`).

`test_iss53_55_evening_reject_tz.py`: 59 тестов, зелёные до правок и зелёные после.

## Пункт 2 плана. Дедуп в `scheduler` + лог о схлопывании

`dedupe_queue()` вызывается в `main()` после сортировки, до `write_queue`. Два уровня ключа —
ровно как в риске 5 плана («ключ `iCalUID` вместо url+время, url+время только страховкой»):

1. **Точный:** `iCalUID` + время старта.
2. **Страховка:** URL комнаты + время старта — когда `iCalUID` неизвестен (ручные записи,
   старый реестр, событие без поля).

**Вето:** если у обоих элементов `iCalUID` известен и они РАЗНЫЕ — не схлопываем никогда, даже
при совпавших комнате и времени: это доказуемо две разные встречи. Вместо схлопывания —
`logger.warning` («в комнату придут два бота и запишут один и тот же разговор; проверь календарь»).
Так риск 5 закрыт с обеих сторон: и «не схлопнуть нужное», и «не промолчать».

**Лог о каждом схлопывании** (`logger.info`) называет обе записи, оба календаря, время и то, по
какой записи ведём:

```
Схлопнул дубль встречи (один iCalUID vystavka-st1@google.com): «oneoff-ef50c3ab» [primary]
и «anzhee-vystavka-st1-20260727» [anzhee@example.com] @ 2026-08-05T12:00:00+00:00 —
веду по «anzhee-vystavka-st1-20260727», второй старт не ставлю (иначе придут два бота)
```

Чтобы лог был читаемым, в элемент очереди добавлен `calendar_id` (его там не было): без него
строка не отвечает на вопрос «из каких двух календарей».

**Кто из дублей выживает** — решение, которого в плане не было (см. «решил сам», п. 1):
побеждает запись с человеческим именем, автоимя `oneoff-<8hex>` / `series-<8hex>` уступает.
Причина: выживший определяет, в какой чат уедет протокол и какой режим открытых вопросов
применится; у записи владельца есть привязка чата, разметка company/visibility и режим, у
автоимени от вечернего блока — ничего.

**Отдельная находка про сам метод проверки.** Первый прогон батареи дал два ложных «не упало».
Причина — `.pyc`: сдвига `os.utime` на +10 секунд **недостаточно**, когда мутации идут подряд.

мутаций mtime попадает в одну и ту же секунду при близком размере файла → Python берёт байткод
предыдущей мутации, и проверка врёт (у меня она соврала ровно так: мутация №11 показала падение
теста от мутации №10). Надёжный рецепт: перед каждым прогоном сносить `__pycache__` **и**
запускать с `PYTHONDONTWRITEBYTECODE=1`. После этого все 15 мутаций укусили, включая обе
«потерянные» — они были ложноотрицательными, а не дырами в тестах (проверено вручную поштучно).

## Что решил сам (в плане этого нет)

1. **Кто из дублей выживает.** План говорит «схлопывать», но не говорит «что оставлять». Оставляю
   запись с человеческим именем (автоимя `oneoff-<8hex>`/`series-<8hex>` уступает): выживший
   определяет чат доставки протокола и режим открытых вопросов. Выбери код автоимя — протокол
   боевой выставки уехал бы в личку вместо группы Anzhee.
2. **Вето точного ключа поверх страховки.** Если оба `iCalUID` известны и различны — не схлопываю
   даже при совпавших комнате и времени, вместо этого пишу warning. Прямая реализация митигации
   риска 5; в плане сформулировано как «url+время только страховкой», я довёл до «страховка
   молчит, когда точный ключ говорит обратное».
3. **Дедуп распространён на «нет» и «никогда», не только на «да».** В плане пункт про дедуп
   «при записи в реестр» — я применил его ко всем трём решениям владельца. Иначе получался
   абсурд: «нет» по копии заводит вторую выключенную запись, а бот приходит по первой.
4. **Граница «серия vs разово»: запись другого рода не считается дублем.** «Записывать всю серию»
   и «записать только этот экземпляр» — разные обещания владельцу, подменять одно другим нельзя.
   На их пересечении (разовое «да» по копии инстанса, покрытого серией из другого календаря)
   в реестре временно живут две записи, но бот всё равно один — снимает схлопывание очереди.
   Тест `test_once_yes_does_not_hijack_series_record` фиксирует эту границу как намеренную.
5. **Два хелпера (`_instant_key`, `_url_key`) продублированы в `scheduler.py` и
   `meetings_apply_reply.py`** вместо выноса в общий модуль. Причина: общее место — только
   `lib/gcal.py` (остальной `lib/` вне карты владения), а импорт `gcal` затащил бы в
   применение ответа владельца зависимость от `requests`. Путь применения ответа сегодня
   офлайновый и fail-closed; тащить туда HTTP-клиент ради 16 строк — плохой размен.
6. **`calendar_id` добавлен в элемент очереди** (в плане не упоминался) — иначе лог о схлопывании
   не отвечает на главный вопрос владельца «из каких двух календарей приехала одна встреча».

## Что осталось за фазой (не мой файл / не мой прогон)

2. **Вечерний блок всё ещё ПРЕДЛОЖИТ копию отклонённой встречи из второго календаря**: он
   считает встречу известной по `(calendar_id, event_id)`, а у копии они другие. Владелец
