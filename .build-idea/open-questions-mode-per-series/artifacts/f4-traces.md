## СЛЕД 2 — невалидные входы каждого перехода

```
$ sh trace2.sh   # текст владельца, JSON модели, snapshot
$ sh trace2b.sh  # сам реестр, ретеншн на мусоре
$ python3 trace2c.py  # радиус поражения + расхождение STATE_DIR
```

Каждый кейс прогонялся **отдельным процессом с таймаутом** — первая (однопроцессная)
версия повисла: `load_watched(lock=True)` берёт flock ДО `_read_yaml`, а `_read_yaml`
на битом реестре кидает `SystemExit` мимо `try` → лок утекает, следующий вызов в том же
процессе блокируется навсегда. В проде процесс одноразовый (лок умирает вместе с ним),
поэтому это ⚪, но воспроизводимо.

### Вход: текст ответа владельца

| вход | что делает код (проверено прогоном) | верно? |
|---|---|---|
| `''` / `'   '` | `rc=1`, `{"error": "пустой reply"}`, реестр не тронут | ✅ |
| `'ок'`, `'угу'`, `'👍'` | `rc=0`, `no_decisions=true` + `hint` для демона, реестр ПУСТ | ✅ |
| `'нет, никакие'` (без номеров, но со смыслом) | общий отказ всем номерам: `rejected=1`, запись на диске | ✅ по промпту |

| вход | что делает код | верно? |

| `n=0` | отфильтрован (`n not in expected_ns`) → `no_decisions=true`, реестр ПУСТ | ✅ |

| `n=1.0` (float) | отфильтрован | ✅ |

## Что вскрыли следы

### 🔴

1. **Молчание владельца о номере теперь = вечный отказ, записанный на диск.**
   Правило промпта `meetings_apply_reply.py:158` («номер не упомянут → reject») до Ф4
   было пустышкой. Теперь «1 да» на список из трёх встреч убивает две оставшиеся
   навсегда (след 1(е)). Это самый частый реальный сценарий, и план его не обсуждал.
2. **`meetings_evening_block.py:82` не выдержал того, ради чего чинили ISS-55.**
   Пустая или мусорная `MEETING_NOTARY_DISPLAY_TZ` роняет вечерний блок при импорте
   (`rc=1`, вопроса не будет вовсе), тогда как починенный `display_tz()` мягко
   откатывается. Двери согласны на happy-path и расходятся на сбое.
3. **Ещё 3 места показывают владельцу время мимо `MEETING_NOTARY_DISPLAY_TZ`:**
   `lib/render.py:115` (дата встречи в шапке протокола — сырой UTC, без подписи пояса),
   `lib/render.py:138` (`generated_at` — часы машины), `lib/morning_digest.py:307`
   (жёсткий МСК). Про одну и ту же встречу вечер скажет «13:00», протокол — «09:00»,
   утро — «12:00 МСК».
4. **Бот рапортует «запись снял / запись сдвинул» про встречу, от которой владелец
   отказался** — отказ попадает в кэш `known-instances` (пятый вопрос, доказано прогоном).
5. **Ретеншн удаляет записи, которых не создавал.** «Нет» по уже существующей
   размеченной записи превращает её в отказ, и через 30 дней она исчезает вместе с
   `telegram_chat_id`, `company`, `visibility`, `open_questions_mode`.
6. **`pending_room` — тот же ISS-53 на ветке «да».** Владелец сказал «пиши», следа на
   диске нет, назавтра спросят снова (`meetings_apply_reply.py:410-418`).
7. **Кривой элемент снапшота хоронит весь вечерний ответ.** `KeyError`/`TypeError` на
   `event_id`/`calendar_id`/`start_at` вылетают из `main()` необработанными: согласия по
   исправным встречам теряются, на stdout пусто, демон владельцу не отвечает.
   Для `event_id`/`calendar_id` это **новая** поверхность — до Ф4 ветка reject

### Что следы подтвердили как сделанное правильно
