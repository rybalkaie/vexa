## Находки

### 🔴 Н-1. `SystemExit` из битого `watched.yaml` пробивает объявленный фолбэк и валит боевые пути

`series_memory.open_questions_mode` обещает в докстроке: «реестр НЕ ПРОЧИТАЛСЯ (нет PyYAML, **битый YAML**, гонка правки руками) → `carry`». Обещание не выполняется для одного класса битого YAML. `cli/registry.py:_read_yaml` на «верхний уровень не словарь» делает `raise SystemExit(...)`, а `SystemExit` — не подкласс `Exception`:

```python
        try:
            watched = load_watched_for_modes()
        except Exception as e:   # ← SystemExit сюда НЕ попадает
            ...
            return OPEN_QUESTIONS_MODE_CARRY
```

Тремя строками ниже, вокруг вызова, который файлов не читает, стоит правильное `except (Exception, SystemExit) as e:  # noqa: BLE001 — SystemExit из _read_yaml`. То есть про класс ошибки исполнитель знал и защитил не тот вызов. Ф2 в `meetings_listener.maybe_route_to_oq_mode` ловит вокруг `load_watched()` именно `(Exception, SystemExit)` — это конвенция проекта, и здесь она нарушена.

Прогнал на подложенном `watched.yaml` со списком верхнего уровня:

```
  sm.open_questions_mode  ← ФОЛБЭК ДОЛЖЕН ДАТЬ carry → ВЫЛЕТЕЛО SystemExit
  morning_digest.send_series_digest             → ВЫЛЕТЕЛО SystemExit
  series_memory.set_task_status                 → ВЫЛЕТЕЛО SystemExit
  pending_reconciler.reconcile_all              → ВЫЛЕТЕЛО SystemExit
```

Радиус: `morning_digest.run()` ловит `except Exception` вокруг серии — не поймает, тик утреннего дайджеста умирает целиком (не одна серия — все); `reconcile_all` ловит `except Exception` вокруг префетча реестра — не поймает, ночная сверка умирает; `set_task_status` вызывается из шести писателей, и `except Exception` в роутах listener'а его тоже не удержит. Триггер — ровно тот, что назван в плане: правка `watched.yaml` руками.

Существующий тест мимо: `test_unreadable_registry_falls_back_to_carry` подаёт `OSError`, то есть `Exception`.

Чинится одним словом в двух местах (`series_memory.open_questions_mode`, `pending_reconciler.reconcile_all`): `except (Exception, SystemExit)`. Тест — тот же, но с `side_effect=SystemExit("битый yaml")`.

### 🔴 Н-2. Гейт хвоста в ОБОИХ call-site защищён грепом по исходнику, а не поведением

`test_both_call_sites_gate_by_mode` читает `finalize-meeting.py` и `lib/clarify_worker.py` как текст и ищет подстроку `carries_open_questions` в 700 символах перед `build_open_tasks_block(`. Мутанты R29/R30: гейт обезврежен (`if open_questions_carry or True:`, `if series_memory.carries_open_questions(...) or True:`), вызов оставлен на месте — **оба выжили, тест зелёный**. Хвост «Вопросы с прошлых встреч…» печатается в шпаргалочный протокол, и ком едет дальше через сам протокол — то есть ровно РИСК1 плана и грабли ISS-10, ради которых пункт и заведён (`[[review-checks-two-call-sites]]`).

R9 (гейт в clarify удалён ЦЕЛИКОМ, вместе со строкой) тест ловит — но это мутация в текст, а не в поведение: она красит грепалку, а не логику.

Сам код при этом верный, проверил статически: `open_tasks_block = ""` инициализируется до `try` в обоих файлах (`finalize-meeting.py:802`, `clarify_worker.py:208`), `open_questions_carry = True` — до `try` в finalize, поэтому else-ветка и любой отказ резолва оставляют старое поведение. Дефекта в проде нет — **дефект в стороже**: единственный инвариант фазы, потеря которого необратима (хвост, собранный без раздела, не восстановить), не имеет ни одного поведенческого теста.

Что нужно: поведенческий тест на протокольный путь. Дешёвый вариант — вынести сборку блока в тонкую функцию `resolve_open_tasks_block(series, ...)` в `series_memory` и звать её из обоих call-site (тогда один поведенческий тест закрывает оба, а грепалка становится не нужна). Дороже, но без рефакторинга — прогнать `clarify_worker._apply_resolution` на фикстуре и проверить, что в собранном протоколе нет `PENDING_SECTION_HEADING`.

### 🟡 Н-4. Гейт в understand-роуте не покрыт (R16 выжил)

Отчёт исполнителя заявляет гейты в четырёх роутах; тестами закрыты три (`digest`, `pending_status`, `mixed`). Снятие гейта в `maybe_route_to_reply_understand` тест не замечает. ### 🟡 Н-5. `set_task_status` читает весь реестр на КАЖДУЮ запись статуса

Замер: три записи статуса подряд → **три** полных чтения `watched.yaml` (до Ф3 — ноль). Пачка из восьми статусов одним reply — восемь. Обиднее всего в сверщике: он честно префетчит реестр один раз на прогон (`watched_modes`), но `set_task_status` этот префетч не принимает и перечитывает файл на каждую закрытую задачу — оптимизация обнуляется в том же прогоне.

Остальное дёшево и вопросов не вызывает: **на одну сборку дайджеста — 1 чтение** (тик по N серий = N чтений, по одному на серию), **на один протокол — 1 чтение** (finalize) и 1 при поздней пересборке (clarify), **на прогон сверщика — 1**.

Лечится параметром: `set_task_status(..., watched=None)` с прокидыванием из сверщика и из роутов, которые уже держат реестр. Не блокирующе.

### 🟡 Н-6. «Правка + статус» одним reply в шпаргалочной серии — правка молча теряется

Проверил на трёх текстах при `ENABLE_MIXED_REPLY_SPLIT=1`:

```
  текст: 'расчёт сделан, и в протоколе поправь Иванов на Петров'
   detect_status=True  looks_edit_heavy=False
   mixed забрал=False (сплиттер звался=False) | статус-роут забрал=True
   ответ бота: 'Спасибо 🙏 В этой серии я вопросы не веду — тот список был сп…'
   → правка дойдёт до шлюза правок: False
```

Решение Р7 («mixed возвращает False, правки уйдут в шлюз») работает только для reply, которые `looks_edit_heavy` признаёт пачкой правок (третий кейс из моего прогона — уходит вниз корректно). Одна правка + один статус: mixed отказался, статус-роут забрал целиком, ответил справочной фразой, правка исчезла. Это класс ISS-33 (инцидент Ольги, «тихая потеря — худший режим»), заново открытый для шпаргалочных серий. При дефолт-OFF флаге регрессии нет (правка терялась и раньше), при включённом — есть.

Минимальная починка: в шпаргалочной ветке `maybe_route_to_pending_status_reply` забирать reply себе только если в нём нет правочного остатка; иначе `return False` и пусть шлюз правок отработает (справочную фразу тогда не шлём — человек и так получит ack о правке).

Там же ⚪: carry изменился и по поведению — `already_sent` больше не засчитывает переотправки, а `record_sent` пишет новый формат состояния с `also`. Это фикс ISS-45, обратная совместимость закрыта тестом; просто «без изменений» в отчёте относится к документу, не к серии целиком.

### 🟡 Н-8. Шапка помечена «согласована», хотя план держит её как черновик

Дословность подтвердил программно: строка в коде совпадает с черновиком плана **посимвольно, 130 из 130**. Но план говорит «Черновик владельцу на утверждение», а пункт Фазы 3 — «→ показать владельцу, **утвердить** формулировку». В коде стоит «ДОСЛОВНО черновик владельца … согласован 29.07», в отчёте — «согласованный владельцем 29.07». Журнал решений №2 фиксирует ТОН («для удобства, шпаргалка»), не формулировку. Утверждения формулировки в артефактах прогона нет — пункт плана остаётся открытым, на приёмку. Туда же — тексты, которых план не диктует и которые исполнитель сочинил сам: `_MINOR_HEADING_LAST_ONLY = "Просто напоминаю"` (решение Р4) и `LAST_ONLY_STATUS_REPLY` (расширение плановой формулы «в этой серии я вопросы не веду, это была справка» — по смыслу верное).

### 🟡 Н-9. Третья копия резолва таймзоны показа

`meetings_apply_reply.display_tz()`, `meetings_evening_block.resolve_display_tz()`, теперь `morning_digest.display_tz()` — три реализации одного: та же env-переменная, тот же дефолт, тот же мягкий откат. Расходятся в деталях (у одного фолбэк на МСК при отсутствии tzdata, у других нет; ярлык зоны только у нового). Это ровно тот класс, из которого вырос сам ISS-55 («вечер говорит 13:00, утро — 12:00 МСК»). Не блокирую — фаза чужая, файл вне зоны, — но кандидат в follow-up: один `display_tz` на проект.

### 🟡 Н-10. В listener'е режим сравнивается со строковыми литералами

```python
def _is_last_only_series(series): return _series_open_questions_mode(series) == "last-only"
...        return "carry"
```

Рядом лежат `series_memory.OPEN_QUESTIONS_MODE_LAST_ONLY` / `_CARRY`, которыми пользуются все остальные пять мест. ### 🟡 Н-11. Решение №7 («возврат в накопление — с чистого листа») без сторожа

### ⚪ Мелочи (действий не требуют)

- **Недостижимая ветка.** `if mode not in (OPEN_QUESTIONS_MODE_CARRY, OPEN_QUESTIONS_MODE_LAST_ONLY)` в `open_questions_mode` — резолвер реестра валидирует значение и не может вернуть третье (R33 выжил, потому что ветка мертва). Комментарий это честно признаёт («страхуемся»). Три строки защитного кода — оставить.
- **Дефолт `collect_items(mode=None)`** не покрыт (R34 выжил): все боевые вызовы передают `mode` явно, а у `build_digest_markdown` аналогичный дефолт как раз проверен (`test_default_mode_is_carry_for_direct_calls`). Асимметрия без последствий.
- **Заголовок мелочи в шпаргалке** тестом не удержан (R32 выжил): проверяется только отсутствие подстроки «статус не нужен».
- **Подпись в вырожденном случае.** Если значимых нет, а мелочь есть, подпись говорит «Открытых вопросов: 0 · мелочей…». Читается странно, но не ломает — и случай редкий.
- **Молчание при сбое детектора.** В роуте дайджеста при падении импорта `pending_status_reply` берётся `has_status = False` → бот молчит и съедает сообщение, хотя комментарием заявлено «молчать нельзя». Путь маловероятный.
- **Состав диффа.** 87 строк комментариев из 497 — ровно конвенция этого проекта (у соседних функций плотность та же). Выбрасывать нечего: перфекционизма в коде я не нашёл, каждая новая функция (`latest_digest_date`, `filter_tasks_born_on`, `carries_open_questions`, `load_watched_for_modes`) имеет ≥2 потребителя или служит точкой инъекции для тестов. ~105 строк (21 %) — это ISS-45 и ISS-55, находки Ф1 и Ф4, а не Фаза 3; они заявлены в отчёте, но на приёмке их надо предъявлять владельцу отдельно: Ф4 помечена `[x]`, а часть ISS-55 приехала сюда.
