# Мутации, которых никто не заметил

Для каждой из семи отдельно доказано, что это НЕ мёртвый код: сценарий воспроизведён на эталоне
и на мутанте, поведение разное. Иначе «зелёный гейт» ничего бы не значил.

## М1 — обещание фазы 6 не закреплено ни одним тестом

Фаза 6 называется «бот понимает просьбу прислать файл, а не список глаголов». Исполняет это одна
строка в `should_ask_ai`: у однозначно названного объекта («протокол», «открытые вопросы») просьбу
опознаёт ФОРМА (`looks_like_a_request_in_shape`: вопросительный знак, «можно / прошу / мне бы /
нужен / пожалуйста / в студию», обращение к боту), а не словарь глаголов. Убрал эту половину
условия — гейт не шелохнулся.

Что при этом ломается (эталон → мутант):

```
'а можно протокол?'                    True → False
'мне бы протокол последней встречи'    True → False
'список открытых вопросов в студию'    True → False
'протокол, пожалуйста'                 True → False
'бот, открытые вопросы'                True → False
```

Это дословно те фразы, которыми докстринг самой функции объясняет, ЗАЧЕМ она написана.
Причина слепоты видна в фикстурах: все 10 «живых просьб» в `TestLiveRequests` начинаются с глагола
отправки («вышли», «скинь», «пришли», «дай», «шли», «отправьте»), и `OWNER_PHRASE` тоже. Набор
проверяет, что старый гейт не крадёт просьбу со словом-статусом, — но ни одной просьбы БЕЗ глагола
в наборе нет. Вся выгода фазы 6 держится на честном слове: любой будущий рефакторинг
`should_ask_ai` вернёт бота к словарю, а гейт останется зелёным.

## М2 — самая дорогая: утечка чужого документа, и её не видит никто

Ремонт фазы 6 заменил `allow_bare_file=is_reply` на `allow_bare_file=surface is not None`, и в
комментарии прямо написано: «раньше сюда шёл `is_reply` — “ответ на ЧТО УГОДНО”, включая реплай
коллеге… “пришли файл с ценами” в ответ человеку выкладывало в чат PDF протокола». Вернул старое
условие — полный гейт дал ТУ ЖЕ тройку базовых файлов, слово в слово.

Воспроизведение (реплай на реплику коллеги, серия у чата привязана, surface не резолвится):

```
сообщение: «Оля, пришли файл с ценами» (в ответ на «у нас закупка на 300к»)
эталон:  роут забрал сообщение False | протокол отправлен False
мутант:  роут забрал сообщение True  | протокол отправлен True
```

Тесты `TestBareFileNeedsReply` покрывают только `is_reply=False` (там оба выражения дают False)
и реплай на НАШ документ (там оба дают True). Ровно средний случай — реплай на чужое сообщение —
не покрыт, а это единственный случай, в котором два выражения расходятся. Тест написан «под ответ»:
проверяет обе стороны, между которыми починка не проходит.

## М3 — ложное срабатывание, которое чинили после боевого инцидента

Комментарий в коде: «`да[йте]+` ловил “дате”/“дату”: “уточню по дате протокола” уходило быстрым
путём и бот молча высылал протокол (ремонт возобновления)». Вернул старую форму — гейт зелёный.

```
'уточню по дате протокола'      → protocol   (бот вышлет файл)
'вопрос по дате в протоколе'    → protocol
'что там по дате протокола?'    → protocol
```

Починка, сделанная по живому инциденту, не оставила после себя ни одного теста. Она откатится
незамеченной при первой же правке регулярки.

## М6 — «да» после «нет»: согласие владельца снова остаётся словами

Выброшенный круг закрывает боевой случай «первую копию не надо, вторую пиши серией»: одноразовая
заглушка отказа не попадает в `candidates` (другой род), а планировщик её видит и гасит старт.

```
сценарий: заглушка отказа (one-off, с метками) + «да, серией» по копии той же встречи
эталон:  записей с метками отказа осталось 0
мутант:  осталось 1 (oneoff-deadbeef) → планировщик снимет старт, бот не придёт
```

Отчёт `seams-repair.md` (позиция 2) заявляет 6 тестов и мутацию «дедуп зовётся только когда записи
по id нет» — она действительно ловится. Но именно эта строка ремонта («снимаем отказ и с записей
ДРУГОГО рода») тестом не закрыта: все тесты про близнецов в `test_iss54_meeting_dedup.py` — про
«нет» и «никогда», не про «да» поверх заглушки другого рода.

## М7 и М8 — «счёт с чистого листа» закрыт только грубо

Сторож на отсечку есть и работает: контрольная мутация «`_drop_tasks_before_carry_since` ничего
не режет» роняет 4 теста в `test_iss51_last_only_digest.py` — ровно как обещает `seams-repair.md`.
Но он ловит только полное отключение. Обе точные мутации проходят насквозь:

```
М7  мелочь «просто напоминаю», висящая с 01.07, отсечка с 01.08
    эталон: срезана | мутант: ПОКАЗАНА
М8  хвост собран по окну из 2 последних встреч (обе после отсечки),
    по полной истории пункт тянется с 01.06
    эталон: срезан  | мутант: ПОКАЗАН
```

Обе — на боевом пути: `morning_digest.collect_items` зовёт `_resolve_minor_open_tasks_raw`
с `series_dir` (то есть М7 реально выключает отсечку для второй корзины), а окно
`SERIES_MEMORY_DEPTH` — это раздел протокола, ради которого М8 и написана.

Цена одинаковая и в точности та, которую ремонт называет своим смыслом: бот вслух пообещал всему
чату «старые вопросы не поднимаю» и минутой позже поднял их. У М8 состояние вдобавок
самоподдерживающееся — дайджест считает пункт снятым, протокол его печатает, на диске всё выглядит
нормально.

Ни `_drop_tasks_before_carry_since`, ни `_tail_run_origins` не упомянуты НИ В ОДНОМ тесте зоны
по имени — их проверяют только через внешнее поведение дайджеста и только в одном срезе.

## М9 — валидатор реестра

Ремонт добавил смысловую проверку поверх формы, объяснив: «регулярка пропускала “2026-13-45” и
“2099-01-01”, а сравнение дат строковое: такая отсечка старше любой реальной выжимки и срезает
хвост серии на ВСЕХ поверхностях навсегда, оставляя один INFO в логе». Вернул проверку только
по форме:

```
2026-13-45 → ПРИНЯТО БЕЗ ЖАЛОБ   (эталон: «такой даты не существует»)
2026-02-30 → ПРИНЯТО БЕЗ ЖАЛОБ   (эталон: «такой даты не существует»)
2099-01-01 → ПРИНЯТО БЕЗ ЖАЛОБ   (эталон: «дата из будущего…»)
```

Поле правится руками при выкатке — опечатка тут рядовое событие, а последствие необратимое.
Сторожа нет.

## Что это значит в сумме

Разрыв проходит ровно по границе «класс дефекта» / «одна конкретная строка»:

* **Т6 и класс «запись стирает сама себя»** закрыты честно — у них есть свой сторож
  (`test_stale_date_record_prune`), и он ловит обе мутации.
* **Ремонт фазы 6 (М1, М2, М3) не закреплён ничем.** Три починки, две из них по боевым
  инцидентам, откатятся молча. Формально фаза зелёная, потому что тесты писались на фикстурах,
  подобранных ПОД уже принятое решение (все просьбы с глаголом; голый объект только в двух
  крайних положениях реплая). У фазы 6, единственной из семи, в артефактах нет файла
  `f6-mutation.md` — мутационного прогона по ней и не было.
* **Ремонт швов (М6, М7, М8) закрыт грубо:** мутации уровня «функцию выключили целиком» ловятся,
  мутации уровня «ветка обошла функцию» и «функции дали не тот источник данных» — нет. Именно
  вторые и происходят при живом рефакторинге.
* **М9** — валидация, у которой нет ни одного теста; заявленной красноты по ней в отчётах и
  не обещали.

Практический вывод для владельца: зелёный гейт этой зоны сегодня доказывает, что не сломано
поведение, ПРО КОТОРОЕ ЕСТЬ ТЕСТ, и ничего не говорит про семь названных выше починок. Дешевле
всего закрывается М2 (одна фраза-фикстура «реплай на чужое сообщение»), дороже всего — М8
(нужен сценарий с окном истории).

# Сторож `test_stale_date_record_prune`

**Краснеет ли на дефектах, ради которых написан — да, на обоих.**

| мутация | результат файла | какие тесты |
|---|---|---|
| М4 (`at` → `date` в слепке нумерации) | `FAILED (failures=3)` | `test_old_document_date_survives_its_own_write`, `test_records_created_long_ago_are_still_pruned`, `test_record_without_creation_stamp_does_not_age` |
| М5 (прун отметки отправки по ключу-дате) | `FAILED (failures=3)` | `test_old_date_send_is_recorded_and_idempotent`, `test_old_date_send_remembers_its_mode`, `test_records_created_long_ago_are_still_pruned` |

Важно, что он краснеет **не только на «выкинули прунинг»**: в обеих половинах есть парный тест
`test_records_created_long_ago_are_still_pruned`, который падает, если починку «починить» удалением
ретенции. Это и есть требуемое доказательство сдачи на подмешанных данных: подложил заведомо
корректные по форме, но старые ПО ВРЕМЕНИ СОЗДАНИЯ записи (правкой поля `at` прямо в JSON) —
сторож обязан их вынести, и он выносит.

**Протухает ли от календаря — нет.** Все даты в файле считаются как `date.today() - timedelta(n)`,
жёстко зашитых дат в нём нет ни одной. Проверено не глазами, а прогоном: подменил в процессе
`datetime.date` и `datetime.datetime` (наследники реальных классов со сдвинутыми `today()`/`now()`)
ДО импорта тестового модуля и дополнительно переприсвоил `morning_digest.datetime` — он берёт
класс на импорте.

```
сдвиг  -400 дней  → «сегодня» 2025-08-01 → Ran 9 tests, OK
сдвиг  +365 дней  → «сегодня» 2027-09-05 → Ran 9 tests, OK
сдвиг  +730 дней  → «сегодня» 2028-09-04 → Ran 9 tests, OK
сдвиг +3650 дней  → «сегодня» 2036-09-02 → Ran 9 tests, OK
```

И, что важнее, на сдвинутом календаре он **не разучивается ловить**: при сдвиге +365 мутация М4
даёт те же 3 падения, М5 — те же 3. То есть зелёный на 2036 году — это зелёный работающего
сторожа, а не сторожа, которого сломала подмена времени.

# Чего проверить не смог и почему

1. **Полностью зелёной базы не добился** — три файла (`test_iss33_mixed_reply_split`,
   `test_phase6_journal`, `test_watson_phase4_morning_digest`) красные из-за окружения:
   не импортируется пакет `lib` для journal-контура, нет systemd-юнитов
   (`/tmp/systemd/meeting-notary-morning-digest.service`), не поднято окружение утреннего
   дайджеста. Внутри этих трёх файлов новые падения я вижу не поимённо, а по счётчику
   `FAILED (failures=N, errors=M)`: гейт печатает лишь последние 25 строк вывода упавшего файла.
   Для М5 этого хватило (3→6 в `watson`), но мутация, ломающая ровно те тесты, что уже красные,
   теоретически осталась бы незамеченной. Отдельно перепроверил: ни одна из семи «незамеченных»
   мутаций счётчиков в этих трёх файлах не меняет вовсе.
2. **Подмену времени сделал в процессе, а не системно.** `faketime`/`libfaketime` и `freezegun`
   в системе отсутствуют, ставить пакеты в рамках этого задания не стал (наружу — ничего).
   Подмена `datetime.date`/`datetime.datetime` покрывает всё, что читает время в этом сторожe
   (`date.today()`, `datetime.now(MSK)`), но НЕ покрывает дочерние процессы и mtime файлов —
   их сторож не использует.
3. **Ничего не гонял на боевых данных и на настоящей модели.** Все сценарии — на временных
   каталогах и заглушках, `claude` не звался. Утверждения вида «бот в реальном чате вывалит PDF»
   доказаны на уровне роута листенера (`maybe_route_to_send_artifact` вернул True и позвал
   `_resend_protocol`), а не на живом Telegram.
4. **Оценки трудоёмкости починки** («дешевле всего М2, дороже всего М8») — суждение по коду,
   не измерение.
5. **Взаимодействие мутаций** (две одновременно) и мутации внутри уже красных файлов не гонял —
   задание было про девять одиночных.
