### 2.3. Инвариант на исходнике `test_the_route_asks_for_our_surface_not_for_any_reply` — цена почти нулевая

Он делает `inspect.getsource` и проверяет два литерала: нет `allow_bare_file=is_reply`, есть
`allow_bare_file=surface is not None`. Проверял в обе стороны:

* **Ложная тревога.** Переписал условие ПРАВИЛЬНО, но другими словами — `allow_bare_file=bool(surface)`
  (поведение идентично). Тест **падает**. То есть он запрещает не ошибку, а формулировку.
* **Пропуск.** Переписал ту же поломку М2b другими словами — завёл `_ctx_ok = isinstance(msg.get("reply_to_message"), dict)` и передал его. Литерала `is_reply` в тексте нет, правильный
  литерал остался на втором call-site → инвариант зелен. **Весь гейт зелен** (эксперимент C1).
* **Пропуск второй, хуже.** Сломал тем же способом НЕСУЩИЙ call-site — предварительную проверку
  `may_be_request`, ту самую, которая реально останавливает утечку. **Весь гейт зелен**
  (эксперимент C3), подпись карантинной тройки не изменилась.

**Почему поведенческого теста на М2b не существует.** Разобрал по коду: `surface` вычисляется
один раз (`meetings_listener.py:1121/1124`) и между двумя call-site'ами не меняется, а
предварительная проверка **fail-closed** — `except` на строке 1163 делает `return False`. Поэтому
два места взаимно подстраховывают друг друга, и поломка ОДНОГО из них поведенчески не наблюдаема
ни при каком входе. Автор упёрся в это и взял сверку текста — понятный выбор. Но в нынешнем виде
она даёт и ложные тревоги, и пропуски, поэтому засчитывать М2b как «поймана» я бы не стал.

**Поведенческий сторож при этом настоящий.** Сломал ОБА места сразу, но другими словами
(эксперимент C4, без литерала `is_reply`) — `test_reply_to_a_colleague_does_not_hand_out_our_documents`
краснеет. То есть реальную утечку «ответ коллеге выдаёт наш протокол» гейт ловит независимо от
формулировки; текстовым остаётся только сторож защиты в глубину.

## Часть 3. Календарная устойчивость

Тот дефект — «фикстуру чинили датой вместо кода» — в новых сторожах **не воспроизведён**.

**`test_stale_date_record_prune.py`** (пришёл с коммитом починки): все даты через
`_ago(n) = date.today() - n дней`, ни одной жёсткой. В шапке прямо записано, почему.
Протухнуть не может.

**`test_clean_slate_and_rejection_guards.py`** — жёсткие даты есть, но они сравниваются
**только друг с другом**, не с сегодня:

| место | даты | протухнет? |
|---|---|---|
| `TestCleanSlateCoversMinorBucket` | `2026-07-01`, `2026-07-15`, `2026-07-22` | **нет**: сравниваются с `since` из той же фикстуры |
| `TestCleanSlateUsesFullHistory` | `2026-06-03`…`2026-07-01`, `since=2026-06-10` | **нет**: то же |
| `TestYesCancelsNoAcrossKinds` | `now(utc) + 5 дней` | **нет**: относительная |
| `TestCarrySinceValidation.test_future_dates_are_rejected` | `today() + 1 день` | **нет**: относительная |
| `TestCarrySinceValidation.test_real_past_dates_and_absence_are_fine` | `2026-02-28` | **нет**: должна быть в прошлом — и останется в прошлом навсегда |
| `TestCarrySinceValidation.test_future_dates_are_rejected` | `"2099-01-01"` | **формально да — 01.01.2099**, через ~73 года. Практически не важно: рядом стоит относительная проверка `today()+1`, которая и несёт смысл |
| `TestCarrySinceValidation.test_impossible_dates_are_rejected` | `2026-13-45` и пр. | **нет**: невозможны при любом календаре |

Проверил и механизм: фикстуры пишутся через `sm.save_digest(...)` без `prune_days` (дефолт `0`),
`list_series_digests` и `_tail_run_origins` к `today()` не обращаются — состариться выжимкам
нечем.

Единственная календарная запись во всём наборе, у которой есть срок годности, — литерал
`"2099-01-01"`, и он дублирован относительной проверкой.

## Часть 4. Чего ещё не хватает

Только то, что показано мутацией с зелёным гейтом.

### 4.1. Ядро починки — распознавание просьбы ПО ФОРМЕ — пришпилено меньше чем наполовину

Коммит починки заявляет «14 живых формулировок из 14 против 9 молчавших». Новый класс держит
**7 фикстур** на **13 признаков** `_REQUEST_SHAPE`. Выбивал признаки по одному (каждый раз —
полный гейт):

| признак | фикстур | гейт краснеет? |
|---|---|---|
| `\?` (вопрос) | 2 | нет — фразы держатся ещё и «можно» / «есть у кого» |
| `можно / можешь / можете` | 1 | нет — фраза держится ещё и `?` |
| `есть у кого / где` | 1 | нет — то же |
| `мне бы` | 1 | **да** |
| `в студию` | 1 | **да** |
| `пожалуйста` | 1 | **да** |
| обращение к боту (`бот,` / `@ник`) | 1 | **да** |
| **`прошу`** | **0** | нет |
| **`нужен / нужна / нужно / нужны`** | **0** | нет |
| **`надо`** | **0** | нет |
| **`хотел бы`** | **0** | нет |
| **`плиз`** | **0** | нет |
| **`плз`** | **0** | нет |

Шесть признаков не покрыты ни одной фикстурой. Пять из них — реальная потеря понимания живой
фразы при зелёном гейте (проверено прямым вызовом `should_ask_ai` до и после):

```
выбито «надо»     → «надо бы протокол»           перестаёт доходить до модели
выбито «прошу»    → «прошу протокол встречи»     перестаёт доходить
выбито «хотел бы» → «хотел бы открытые вопросы»  перестаёт доходить
выбито «плиз»     → «протокол плиз»              перестаёт доходить
выбито «плз»      → «открытые вопросы плз»       перестаёт доходить
```

(«нужен» — единственный из шести, кто держится: его подхватывает `_REQUEST_EXTRA` в
`looks_like_request`, то есть другая дорога.)

Смысл для владельца: сегодня можно молча удалить половину нового распознавания, бот снова начнёт
молчать на части живых просьб — и гейт этого не заметит. Лечится дешёво: добавить в
`VERBLESS` по фикстуре на каждый непокрытый признак и развести фразы так, чтобы каждая держала
РОВНО ОДИН признак (сейчас «а можно протокол?» держит сразу два, и потому не держит ни одного).

### 4.2. Согласованность двух мест `allow_bare_file` держится только на сверке текста

Показано в 2.3: поломка любого ОДНОГО из двух мест, записанная другими словами, проходит гейт
насквозь (C1, C3), включая поломку несущего пред-чека. Поведенческого теста тут быть не может
(места взаимно подстраховывают друг друга), но и текстовый сторож обходится переименованием
переменной. Честнее было бы поставить тест, который **ломает первый пояс намеренно** (мокнуть
`may_be_request`, чтобы он пропускал всё) и требует, чтобы второй удержал — тогда защита в
глубину проверялась бы поведением, а не grep'ом по исходнику.

### 4.3. Два новых класса не проверяют собственную предпосылку

Показано в 2.1 (D3, E2): `TestYesCancelsNoAcrossKinds` зеленеет 14/14, если отказная заглушка
перестаёт создаваться; связка `TestVerblessRequests` + `TestMentioningIsNotAsking` зеленеет, если
`_SEND_VERB` мёртв. Сегодня их страхует гейт в целом (другие файлы краснеют), поэтому это не
дыра, а хрупкость: если те файлы когда-нибудь тоже уедут в карантин базовой линии, оба сторожа
станут декорацией и никто об этом не узнает. Закрывается одной строкой в каждом классе —
утверждением о предпосылке (заглушка отказа в `watched` действительно появилась; словарь
быстрого пути действительно ловит хотя бы «пришли протокол»).

## Итог

* Поймано **10 из 10** (в прошлом заходе — 2 из 9). Сторожа дописаны по делу, ни один не оказался
  фикцией: все краснеют и на мутации, и на полном удалении охраняемого кода.
* Слабых мест три: **инвариант на тексте исходника** (ложные тревоги + обходится переписыванием,
  и именно он один держит М2b), **непокрытая половина `_REQUEST_SHAPE`** (шесть признаков без
  фикстур, пять — с доказанной потерей понимания при зелёном гейте) и **непроверяемая предпосылка**
  у двух новых классов.
* Календарной хрупкости, из-за которой дефект трижды чинили в фикстурах, в новых сторожах нет.
