Разбор: `_read_yaml` кидает `SystemExit` (потомок `BaseException`). В
`series_memory.open_questions_mode` вызов `load_watched_for_modes()` защищён только
`except Exception` — `SystemExit` пролетает насквозь. Второй `try` ниже ловит
`(Exception, SystemExit)`, но он обёрнут вокруг кода, который читать файл уже НЕ может
(резолвер получает `watched` параметром) — страховка стоит не на том блоке.
Симметрично дырявы `meetings_listener._series_open_questions_mode` (`except Exception`)
и `pending_reconciler.reconcile_all` (`except Exception` вокруг
`load_watched_for_modes`). Ф2 в `maybe_route_to_mode_command` этот же класс закрыла
правильно (`except (Exception, SystemExit)`) — то есть паттерн в проекте известен,
но в Ф3 не применён.

Последствие: битый (руками правленный) `watched.yaml` роняет `SystemExit` из
слушателя — до `save_offset`, то есть петля перезапусков бота; из утреннего тика;
из ночного сверщика; из финализации протокола.

### 3б. Другие решения по полю реестра — одинаково ли читают

```
реестр: запись A — МЁРТВАЯ (enabled: false), запись B — живая; значения РАЗНЫЕ
  open_questions_mode → last-only   (ЖИВАЯ запись главнее — учитывает series_record_is_live)
  telegram_chat_id    → -111        (первое совпадение, ЖИВОСТЬ НЕ УЧИТЫВАЕТСЯ)
  company             → anzhee      (из МЁРТВОЙ записи)
  genre               → None
  visibility          → private

мусор в поле:
  open_questions_mode → last-only (дефолт)   company → None   genre → None   visibility → None

серии НЕТ в реестре — направление фолбэка:
  registry.series_open_questions_mode → last-only
  series_memory.open_questions_mode   → carry
```

Два расхождения:
1. `open_questions_mode` — **единственный** резолвер реестра, который смотрит на живость
   записи. Соседи (`telegram_chat_id`, `company`, `visibility`, `genre`) берут первое
   совпадение. На одном и том же реестре режим определяет ЖИВАЯ запись, а чат — МЁРТВАЯ.
   Решение осознанное и задокументировано, но конвенция «как читать поле серии» в проекте
   теперь не одна, а две.
2. Мусор в поле: `open_questions_mode` уезжает в `last-only` (МЕНЯЕТ поведение),
   соседи возвращают `None` (поведение НЕ меняют — caller берёт мягкий дефолт).
   Полярность обработки мусора у нового поля обратная соседям.
3. `registry.series_open_questions_mode` и `series_memory.open_questions_mode` дают
   РАЗНЫЙ ответ на «серии нет в реестре» (`last-only` против `carry`). Это сознательный
   разворот дефолта (задокументирован), но два резолвера одного вопроса — сам по себе
   риск: команда бота отвечает владельцу первым, боевые потребители слушают второй.

### 🔴 Читатель №6 — роут ответа на ВОПРОС бота (`maybe_route_to_ack_reply`)

Гейта режима нет, роут стоит ПЕРВЫМ. Сценарий полностью реальный: бот задал вопрос,
пока серия была в накоплении → владелец переключил серию в шпаргалку → человек
отвечает. `reply_ack_state` персистентный, переживает и рестарт, и смену режима.

Прогон `handle_ack_reply` на одном и том же состоянии в двух режимах (`trace5c.out`):

```
ОТКАТ «не так, верни»
  режим carry      → бот отвечает: '↩️ Вернул в работу: «расчёт по марже». Спасибо, что поправили.'
  режим last-only  → бот отвечает: 'Не нашёл, что откатить — уточните, пожалуйста.'

ПРЯМО: _closed_reply при пустом списке применённых
   'Ок, ничего не отметил.'
```

Человек в шпаргалочной серии слышит «Не нашёл, что откатить — уточните, пожалуйста.»
или «Ок, ничего не отметил.» — то есть бот просит уточнить то, чего он в этой серии
никогда не примет, вместо честного «вопросы тут не веду». Ровно тот дефект, который
искали: одна дверь знает про режим, соседняя — нет.

### 🔴 Читатель №7 — ИИ-разбор reply: гейт узкий, статус-машина не молчит

Гейт в `maybe_route_to_reply_understand` срабатывает только когда
`pending_status_reply.detect_status_intent(text)` вернул код. Фразы без явного маркера
проходят насквозь:

```

detect_status_intent('да, всё готово'                     ) = 'done'
detect_status_intent('по марже уже не актуально'          ) = 'cancelled'
detect_status_intent('закрой первую'                      ) = None     ← проходит гейт
detect_status_intent('мы это обсудили и решили не делать' ) = 'done'
```

Сквозной прогон в серии `last-only` (`understand_reply` подменён заглушкой, LLM не звался):

```
maybe_route_to_reply_understand вернул: True
LLM позван раз: 1 | ответы бота:
  ['🤔 Не разобрал, про какую задачу речь. Напишите: название задачи (как в протоколе) + что с ней, например «юани — закупили».']

```

То есть в серии, где «отвечать не нужно», бот (а) тратит платный вызов ИИ и (б) **просит
человека прислать статус по формату протокола** — прямо против цели фазы «тишина
статус-машины». Запись при этом не проходит (`set_task_status` → `None`), так что порчи
данных нет; ломается обещание тона.

## Список вскрытого

### 🔴 Красное

1. **`SystemExit` из битого реестра валит ВСЕ семь боевых потребителей режима**
   (СЛЕД 2.3). Красный дефект Ф1 не закрыт: `except (Exception, SystemExit)` в
   `series_memory.open_questions_mode` стоит вокруг блока, который файл не читает, а
   сам `load_watched_for_modes()` защищён только `except Exception`. Те же дыры в
   `meetings_listener._series_open_questions_mode` и `pending_reconciler.reconcile_all`.
   Достижимо ручной правкой `watched.yaml` (владелец правит его руками — это
   штатный сценарий). Последствие: падение слушателя ДО `save_offset` (петля
   перезапусков), падение утреннего тика, ночного сверщика и финализации протокола.
   Образец правильного лечения уже есть в этом же репозитории —
   `maybe_route_to_mode_command` (Ф2).

2. **На боевых данных шпаргалка вываливает ВЕСЬ накопленный ком — РИСК2 не закрыт**
   (СЛЕД 4). У серии с 21 открытым вопросом в шпаргалку попадут все 21, и они НЕ все
   из последней встречи: LLM переписывает формулировки задач при каждой генерации
   протокола, `_status_key` не совпадает, origin сбрасывается на дату последней
   встречи. Пересечение соседних выжимок на боевых сериях: 0, 1, 6, 16, 21 из ~20–25.
   На 2 из 4 боевых серий `last-only` и `carry` дают ОДИНАКОВЫЙ состав списка.
   Тест зелёный только потому, что фикстура повторяет тексты дословно.

3. **Роут ответа на вопрос бота (`maybe_route_to_ack_reply`) не знает про режим**
   (ПЯТЫЙ ВОПРОС, №6). Стоит ПЕРВЫМ из reply-роутов, `reply_ack_state` персистентный
   и переживает смену режима. В шпаргалочной серии человек получает
   «Не нашёл, что откатить — уточните, пожалуйста.» / «Ок, ничего не отметил.»
   вместо справочной фразы. Данные не портятся (`set_task_status` → `None`),
   ломается обещание тона.

4. **ИИ-разбор reply запускается в шпаргалочной серии и просит статус** (ПЯТЫЙ
   ВОПРОС, №7). Гейт узкий (только явный статус-маркер), «закрой первую» и подобные
   проходят насквозь → платный вызов LLM → ответ «🤔 Не разобрал, про какую задачу
   речь. Напишите: название задачи + что с ней». Прямо против пункта плана «тишина
   статус-машины».

### 🟡 Жёлтое

5. **Битая/нестроковая дата у САМОЙ СВЕЖЕЙ выжимки уводит шпаргалку на встречу назад**
   (СЛЕД 2.6). `latest_digest_date` пропускает мусорную дату и берёт предыдущую, а
   `origin_dates_for_tasks` хранит сырое значение — фильтр совпадает не с той датой.
   Шпаргалка молча показывает задачи ПРОШЛОЙ встречи и теряет последнюю. Ни ошибки,
   ни варнинга.

6. **Опечатка в реестре молча превращает серию-накопление в шпаргалку**
   (СЛЕД 2.1). Любой мусор (`'карри'`, `123`, `True`, список, словарь, пустая строка)
   → `last-only`. Предупреждение уходит только в лог. Для серии-накопления цена —
   протокол без раздела «с прошлых встреч», то есть НЕОБРАТИМАЯ потеря хвоста
   (на боевом протоколе — 6 из 18 пунктов за одну встречу).

7. **Ночной сверщик отсекает шпаргалочную серию ДО TTL-пруна `doubt`** (ПЯТЫЙ
   ВОПРОС, №3). Пока серия в шпаргалке, буфер `doubt` заморожен на любой срок;
   на возврате в `carry` всё выпрунивается разом (`doubt_pruned: 1`) и пункты
   многомесячной давности одномоментно возвращаются в «висит».

8. **Полярность нового поля реестра обратна соседям** (СЛЕД 3б). Мусор в
   `open_questions_mode` МЕНЯЕТ поведение (→ `last-only`), мусор в
   `company`/`genre`/`visibility` его НЕ меняет (→ `None`, мягкий дефолт у caller'а).
   Плюс `open_questions_mode` — единственный резолвер, учитывающий живость записи:
   режим берётся из живой записи, а чат серии — из мёртвой.

9. **Докстрока `_resend_digest` устарела** (СЛЕД 3а, п.15). Обещает «слепок нумерации
   пишется (ordinal-ответы на переотправленный дайджест работают)» — в `last-only`
   слепок не пишется. Сам код корректен (режим читается из реестра), врёт только
   комментарий.

10. **Ярлык зоны печатается только для Москвы** (СЛЕД 3в). При `Asia/Dubai` документ
    говорит «встреча в 17:00» без зоны; читатель в Москве прочтёт как московское.
    Вечерний блок ведёт себя так же, рассогласования между поверхностями нет.
