## Вердикт по 8 пунктам

### 1. Права и владение: кто увидит шпаргалку, кто накопление, протечёт ли серия в чужой чат — **в порядке**

Прогон с двумя сериями (`koordinatsiya` = шпаргалка, `anzhee-direktorat` = накопление),
маркированное содержимое в каждой:

```
чат -1001: СЕКРЕТ-КООРДИНАЦИИ=True,  СЕКРЕТ-ДИРЕКТОРАТА=False → OK
чат -1002: СЕКРЕТ-КООРДИНАЦИИ=False, СЕКРЕТ-ДИРЕКТОРАТА=True  → OK
resolve msg→серия: {5001: 'koordinatsiya', 5002: 'anzhee-direktorat'}
```

Адресация фазой не тронута: `send_series_digest` берёт `series_dir = root/series`, собирает
состав из выжимок ТОЛЬКО этой папки, чат резолвит прежним `chat_resolver`. Режим
читается по имени серии и на состав чужой серии не влияет. Карта `message_id → серия`
(`digest_series_for_message`) сверяет пару `(chat_id, message_id)` — в новом формате с
`also` она стала видеть ВСЕ отправки дня, кросс-серийных совпадений это не создаёт.

Переотправка по просьбе (`_resend_digest`) пересобирает документ заново через
`send_series_digest(force=True)` и режим читает сама — старый carry-файл со статусами в
шпаргалочную серию не уедет.

Справочная фраза `LAST_ONLY_STATUS_REPLY` не называет slug серии — внутренние имена в
групповой чат не утекают (паритет с приватностью Ф2).

### 2. Утечка личных данных — **в порядке** (одно замечание по ответу человеку → см. 🟡-5)

Прогон полного цикла шпаргалки с намеренно «острыми» задачами («уволить Татьяну за срыв
поставки», «закрыть долг 400 тыс»), лог собран на уровне DEBUG со всего дерева логгеров:

```
утечка 'уволить' — нет · 'Татьяну' — нет · '400' — нет · 'долг' — нет · 'срыв' — нет
```

Все новые строки журнала несут только slug серии, режим, счётчики, `chat_id` и код
исхода. Проверено поимённо: `finalize` (`серия %s в режиме last-only`), `clarify_worker`,
`morning_digest.run` (`mode=%s open=%d minor=%d`), `pending_reconciler`,
`series_memory.set_task_status`, четыре роута слушателя. Тексты задач и текст reply не
логируются нигде.

Между сериями данные не переносятся: `filter_tasks_born_on` работает по origin-картe,
собранной из выжимок ОДНОЙ серии.

В артефактах шпаргалка оставляет **меньше**, чем накопление: слепок нумерации
(`record_open_tasks_snapshot`, единственное место, где тексты задач ложились на диск
отдельным файлом) в `last-only` не пишется, статус-стор не создаётся вовсе — проверено
прогоном (`task-status.json` отсутствует). `record_sent` пишет только `chat_id`/
`message_id`/`at`/`forced`.

Новый гейт статус-ответа: бот отвечает
> «Спасибо 🙏 В этой серии я вопросы не веду — тот список был справкой к встрече, статусы по нему не нужны.»

в журнал при этом уходит `[morning-digest] серия koordinatsiya в режиме last-only — статус
НЕ пишу (ответил=True)` — ни текста ответа, ни имени человека. Чисто.

### 3. Валидация на границе — **в порядке**, одно ⚪

Прогон границ:

| вход | поведение |
|---|---|
| режим не из списка (`carrry`, `True`, список, пустая строка) | предупреждение в лог 1 раз на процесс + дефолт (**но дефолт = `last-only`** → 🟡-3) |
| серии нет в реестре | `carry` + строка в лог |
| реестр не читается (OSError / нет PyYAML / None) | `carry` + WARNING |
| реестр битый (верх YAML не словарь) | **SystemExit наружу** → 🔴-2 |
| `series=None / '' / '   ' / 123 / ['x']` | `carry`, без падения |
| регистр и пробелы (` CARRY `) | `carry` — нормализация работает |
| серия без выжимок | `{'open': [], 'minor': []}` → дайджест не шлётся (`reason=empty`) |
| выжимка с пустым списком задач | то же, пусто |
| выжимка без поля `date` | дата берётся из имени файла, шпаргалка собирается верно |
| задача без origin-даты | отбрасывается (документировано); на практике не возникает — origins считаются по тем же выжимкам |
| дата выжимки в чужом формате (`15.07.2026`) | выжимка **невидима** для `list_series_digests`, шпаргалка молча покажет более раннюю встречу → ⚪-10 |

### 4. Fail-closed на РЕЖИМЕ — **починить** (та сторона выбрана НЕ везде)

Главные ветки — те, что просили проверить прогоном — выбраны **правильно**:

```
реестр не читается (OSError)      → carry   ← старое поведение, безопасно
реестр вернул None                → carry
серии нет в реестре               → carry
реестр пуст / без ключа watched   → carry
series мусорный/пустой            → carry
```

Обоснование в докстринге верное и важное: накопленный хвост живёт ТОЛЬКО в разделе
протокола, один протокол без раздела обнуляет его навсегда — восстановить неоткуда.

Но три ветки того же класса («режим определить не удалось») падают в ОПАСНУЮ сторону:

```
опечатка в значении ('carrry')                          → last-only  ← 🟡-3
поле пустой строкой                                     → last-only  ← 🟡-3
мёртвая запись с carry + живая запись без поля          → last-only  ← 🟡-4
```

и одна не падает вовсе, а роняет процесс: битый YAML → `SystemExit` (🔴-2).

### 5. Повторы и гонки — **в порядке**

Прогон:

```
1) плановая      → sent
2) плановая ещё  → already          (идемпотентность держится)
3) по просьбе    → sent             (force обходит только already_sent)
4) плановая п.3  → already          (переотправка не открыла второй плановой)
also: [{6001}] — вложенных also внутри also НЕТ (матрёшка не растёт)
резолв ВСЕХ message_id дня: {6001: 'koordinatsiya', 6002: 'koordinatsiya'}

08:20 по просьбе → sent
09:00 плановая   → sent             ← фикс ISS-45: просьба утром не отменяет рассылку
```

Ночной сверщик и дайджест: пересечения по записи нет — сверщик шпаргалочные серии
пропускает целиком (проверено, `task-status.json` не создан, до матчера висяк не доехал),
а серию-накопление отрабатывает как раньше (`closed=1`). Статус-стор пишется под
межпроцессным локом, как и до фазы.

Единственная новая гонка — режим и УЖЕ отправленный документ, см. пункт 6.

### 6. Момент проверки режима — **починить**

Режим читается **один раз на отправку**, в самом начале `send_series_digest`, до сборки
состава и документа. Переключение между сборкой и отправкой внутри одного вызова
невозможно — это доли секунды и один снимок реестра. Здесь чисто.

Дыра в другом: в роутах ответа режим читается **в момент ответа человека**, а не берётся у
документа, на который он отвечает. Прогон:

```
дайджест ушёл в CARRY: просил статус=True, нумерация=True, слепок=True
владелец переключил серию в last-only
человек отвечает «расчёт — сделано»
  ОТВЕТ БОТА: «В этой серии я вопросы не веду — тот список был справкой к встрече»
  статус записан: False
```

Документ статус ПРОСИЛ, человек ответил, бот сказал ему, что он неправильно понял, и
выбросил ответ. План обещает обратное: «смена действует со СЛЕДУЮЩЕГО дайджеста/протокола,
задним числом ничего не пересобирается». → 🟡-5.

### 7. Серия-накопление не изменилась — **починить** (критерий 4 нарушен)

Внутри документа — да, не изменилась: golden-тест сверяет markdown и caption байт в байт с
эталоном, снятым с кода до Ф3; `collect_items` в carry по-прежнему отдаёт весь хвост;
слепок нумерации пишется; сверщик отрабатывает; раздел «с прошлых встреч» в протоколе на
месте; `commit_pending_shown` вызывается.

Но шапка документа изменилась, и это видно людям в чате. Прогон одного и того же входа на
коде ДО и ПОСЛЕ фазы:

```
ДО Ф3,  env не задана          → «встреча в 12:00 МСК»
ПОСЛЕ,  env не задана          → «встреча в 13:00»       ← на час позже, ярлык зоны исчез
ПОСЛЕ,  env=Europe/Moscow      → «встреча в 12:00 МСК»
```

→ 🔴-1.

### 8. Как узнаем, что сломали — **починить** (наполовину)

Прогон трёх серий разом:

```
[morning-digest] series=koordinatsiya    ... mode=last-only open=1 minor=0
[morning-digest] series=anzhee-direktorat ... mode=carry     open=1 minor=0
[morning-digest] series=neizvestnaya      ... mode=carry     open=1 minor=0
```

«Шпаргалка» и «накопление» в журнале различимы отлично. А вот **«режим не определён» на
уровне INFO неотличим от честного накопления**: третья серия провалилась в carry по
фолбэку, и единственный след этого — строка уровня **DEBUG** (`серии neizvestnaya нет в
реестре`), которой на проде в журнале не будет. Ровно тот сценарий, который надо уметь
поймать: Директорат тихо перестал резолвиться и живёт на фолбэке. → 🟡-8.

Ветка «реестр недоступен» отработана лучше — там WARNING, он виден.

Сверщик пишет `mode` только когда серию ПРОПУСКАЕТ; для carry-серий режим в его журнале не
печатается вовсе.

## Находки

### 🔴-1. Дайджест серии-НАКОПЛЕНИЯ поехал на час и потерял «МСК» — критерий 4

**Где:** `lib/morning_digest.py`, `display_tz()` / `_tz_label()` / `build_digest_markdown`
(строка `when = f" · встреча в {start_at.astimezone(tz)...}"`).

**Что доказано прогоном** (одинаковый вход, код до и после фазы) — см. пункт 7.
`MEETING_NOTARY_DISPLAY_TZ` не задана → время печатается в `Asia/Dubai` (МСК+1) и **без
всякого ярлыка зоны**: люди в чате Директората читают «встреча в 13:00» вместо «в 12:00 МСК».

**Почему это серьёзно:**

1. Критерий 4 плана — «в серии-накоплении поведение не изменилось **ни в одном месте**» — и
   он, по формулировке задачи, про доверие владельца. Шапка документа это «место».
2. Пункта про `morning_digest` в Фазе 3 плана НЕТ. Бюллетень ISS-55 в Ф4 касался
   `fmt_when_short` в `meetings_apply_reply.py`. Это привезённое расширение скоупа в
   документ, который читают люди.
3. Зависимость нигде не закреплена: `MEETING_NOTARY_DISPLAY_TZ` **отсутствует** в
   `.env.notary.example`, в `config/` и во всех юнитах `systemd/` (включая
   `meeting-notary-morning-digest.service`, который тянет `EnvironmentFile=/srv/meeting-notary/.env.notary`).
   Ревью Ф4 это уже фиксировало и отложило в Ф7. Комментарий в коде утверждает «на бою
   `MEETING_NOTARY_DISPLAY_TZ=Europe/Moscow` — он верен» — из репозитория это не проверяемо.
4. **Сторож структурно слеп:** `TestCarryUnchangedByteForByte.setUp` жёстко выставляет
   `MEETING_NOTARY_DISPLAY_TZ=Europe/Moscow`. Тест «carry не изменился ни на байт» физически
   не может покрасить на этой регрессии.

**Что сделать (одно из):** либо вернуть в carry-ветке жёсткий МСК и оставить env только
шпаргалке; либо (лучше) прописать `MEETING_NOTARY_DISPLAY_TZ=Europe/Moscow` в
`.env.notary.example` + в юниты дайджеста и слушателя, снять env из `setUp` золотого теста и
добавить кейс «env не задана → carry по-прежнему 12:00 МСК». И проверить на бою до выкатки,
что переменная там действительно есть — сейчас это допущение, а не факт.

### 🔴-2. Битый реестр роняет процесс вместо отката в carry — на всех пяти новых точках

**Где:** `lib/series_memory.py:open_questions_mode` (внешний `try/except Exception` вокруг
`load_watched_for_modes()`), `lib/pending_reconciler.py:reconcile_all`,
`meetings_listener.py:_series_open_questions_mode`.

`cli/registry.py:_read_yaml` при верхнем уровне YAML не-словарём делает
`raise SystemExit(...)`. `SystemExit` — не наследник `Exception`, и все три `except Exception`
его пропускают. Прогон на `watched.yaml`, где владелец сдвинул отступ у `watched:` (частый
исход ручной правки, а план как раз приглашает править реестр руками и в Ф7 пройти его целиком):

```
series_memory.open_questions_mode   → SystemExit — ПРОЦЕСС ПАДАЕТ
series_memory.carries_open_questions→ SystemExit — ПРОЦЕСС ПАДАЕТ
md.send_series_digest               → SystemExit — ПРОЦЕСС ПАДАЕТ
pr.reconcile_all                    → SystemExit — ПРОЦЕСС ПАДАЕТ
ml._series_open_questions_mode      → SystemExit — ПРОЦЕСС ПАДАЕТ
sm.set_task_status                  → SystemExit — ПРОЦЕСС ПАДАЕТ
```

**Во что это выливается:**

- **Утренний дайджест не уходит вообще** — ни одной серии, включая Директорат. Таймер молча
  завершится с ненулевым кодом, в чатах тишина.
- **Слушатель падает на входящем сообщении.** `process_message` обёрнут в
  `except Exception` (`meetings_listener.py:3667`) — SystemExit пролетает мимо, а
  `save_offset(offset)` строкой ниже не выполняется → после перезапуска то же сообщение
  прилетает снова → **цикл падений**, пока реестр не починят руками.
- **Финализатор теряет протокол:** вызов стоит в `try/except Exception` (`finalize-meeting.py:862`),
  SystemExit уходит выше — встреча прошла, протокол не собран и не доставлен.
- Ночной сверщик падает.

**Отдельно:** докстринг `open_questions_mode` прямо обещает, что случай обработан
(`except (Exception, SystemExit) as e:  # noqa: BLE001 — SystemExit из _read_yaml`) — но этот
`except` стоит на ВНУТРЕННЕМ резолве, а файл читает ВНЕШНИЙ вызов, у которого только
`except Exception`. Защита есть, стоит не на той двери. Это опаснее простого пропуска:
следующий читатель кода поверит комментарию.

**Расширение поверхности именно в Ф3:** до фазы реестр на горячем пути слушателя читал
только `maybe_route_to_mode_command`, и то после узкого детекта команды. Теперь
`_is_last_only_series` вызывается на **любом** reply в четырёх роутах.

**Что сделать:** ловить `(Exception, SystemExit)` (или `BaseException` кроме
`KeyboardInterrupt`) вокруг самого `load_watched_for_modes()` во всех трёх местах — то есть
перенести уже написанный `except` на внешний вызов. Тест: `watched.yaml` со списком на
верхнем уровне → дайджест уходит в режиме `carry`, слушатель отвечает, сверщик отрабатывает.

**Побочно, из того же места:** в `reconcile_all` при нечитаемом реестре `watched_modes = None`,
и дальше `open_questions_mode(sd.name, watched=None)` **перечитывает файл на каждую серию** —
вопреки комментарию «реестр читаем ОДИН раз на прогон». Стоит отличать «не читали» от
«прочитали и не вышло» (например, `watched_modes = {}`).

### 🟡-3. Опечатка в значении режима падает в опасную сторону

`open_questions_mode: carrry` (или пустая строка, `True`, список) → резолвер возвращает
дефолт `last-only`, то есть у **Директората** тихо выключается накопление: раздел «с прошлых
встреч» перестаёт печататься, и по собственному объяснению кода хвост «обнуляется НАВСЕГДА —
восстановить неоткуда». В журнале — одно WARNING на процесс.

Это тот же класс «режим определить не удалось», что «реестр не читается» и «серии нет», но
эти два падают в `carry`, а этот — в `last-only`. Дефолт `last-only` для **отсутствующего
поля** — осознанное решение владельца от 29.07 и трогать его не надо; речь про **битое
значение**, где выбор направления никем не проговаривался.

**Что сделать:** в `series_memory.open_questions_mode` отличать «поля нет» (→ решает
резолвер, `last-only`) от «поле есть, но мусор» (→ `carry`, как у остальных сбоев) и слать
владельцу алерт: реестр правится руками, а последствие необратимо.

### 🟡-4. Мёртвая запись с `carry` + живая без поля → шпаргалка

Прогон:

```
живая carry + живая без поля                     → carry     OK
МЁРТВАЯ carry (отказ ISS-53) + ЖИВАЯ без поля    → last-only  !!!
живая ignored=true с carry + живая без поля      → last-only  !!!
только мёртвая с carry                           → carry     OK
```

Логика слотов в `cli/registry.py` намеренно даёт живым записям приоритет над мёртвыми — это
правильно, когда значение есть у обеих. Но когда у живой записи поля НЕТ, код уходит в
дефолт `last-only`, а не к явно записанному `carry` мёртвой записи. Живые записи без поля
заводятся сами: `set_open_questions_mode_for_series` проставляет режим только существующим
записям, а новые инстансы встреч приезжают из календаря без него; ISS-53 (Ф4, этот же прогон)
как раз плодит `enabled=false`-записи.

**Что сделать:** мёртвые слоты использовать фолбэком до дефолта, а не только когда живых нет
совсем (порядок `(живая,точная) → (живая,норм) → (мёртвая,точная) → (мёртвая,норм) → дефолт`).

### 🟡-5. Переключение режима действует задним числом на уже отправленные документы

Доказано прогоном (пункт 6): carry-дайджест попросил статус, владелец переключил серию,
человек ответил — бот ответил «в этой серии я вопросы не веду, это была справка» и молча
выбросил ответ. Формулировка вдобавок ложная про ТОТ документ, который прямо просил статус:
для человека это ровно «бот меня не слышит» — класс ISS-53.

Обратная сторона: шпаргалка ушла без слепка нумерации, серию вернули в carry, ответ «первая —
сделано» получил «Не понял, по какому вопросу статус» (ничего лишнего не закрылось —
проверено, стор пуст; но ответ человека потерян).

Корень: `record_sent` кладёт только `chat_id`/`message_id`/`at`/`forced` — **режима документа
там нет**, хотя `send_series_digest` его уже знает и даже возвращает в `res["mode"]`.

**Что сделать:** писать `mode` в запись `record_sent` и в роутах решать по режиму ДОКУМЕНТА
(по `reply_to` message_id), с откатом на текущий реестр, если записи нет. Это и есть
обещанное планом «смена действует со следующего дайджеста».

### 🟡-6. Гейт в digest-роуте шире плана — просьбы-настройки в шпаргалочных сериях теряются

`maybe_route_to_digest_reply` при `last-only` делает `return True` **выше**
`_apply_digest_understand`, то есть съедает reply целиком. А understand-слой обрабатывает не
только статусы: `result["config_requests"]` → `_forward_config_to_owner(...)` — настройки
серии (R12). Теперь участник шпаргалочной серии, ответивший на список «не надо мне это
слать» / «уберите меня отсюда», не получает ничего и владелец об этом не узнаёт. Если в
тексте случайно есть статус-маркер, ответ будет ещё и мимо смысла («статусы не нужны»).

План просил заглушить **статус-машину** («reply со статусами, ночной сверщик, напоминания»),
а не весь роут. Аргумент реализации («understand сам пишет статусы в sidecar») уже закрыт
более глубоким гейтом — `set_task_status` физически ничего не пишет в `last-only`.

**Что сделать:** сузить гейт до «есть статус-маркер → ответить справочной фразой и выйти;
маркера нет → падать вниз, в understand». Платный вызов ИИ при этом не тратится на чистые
статусы, а просьбы к владельцу доезжают.

### 🟡-7. Два ключевых теста — grep по исходнику; перевёрнутый гейт их проходит

`test_both_call_sites_gate_by_mode` и `test_finalize_skips_onboarding_commit_in_last_only`
ищут подстроку в 700/800 символах перед вызовом. Мутация (прогон):

```
finalize-meeting.py:   мутация внесена=True · тест ЗЕЛЁНЫЙ=True ← мутант ВЫЖИВАЕТ
lib/clarify_worker.py: мутация внесена=True · тест ЗЕЛЁНЫЙ=True ← мутант ВЫЖИВАЕТ
finalize/commit_pending_shown: мутант выживает = True
```

То есть `if not carries_open_questions(...)` (хвост печатается в шпаргалке и пропадает в
накоплении) тесты не заметят. Это РИСК1 плана — самое дорогое требование фазы, и оно
поведенчески не покрыто ни в одном из двух call-site. Понятно, что `finalize-meeting.py` —
скрипт и импортируется тяжело, но `lib/clarify_worker.py` — обычный модуль, его путь можно
прогнать по-настоящему.

### 🟡-8. «Режим не определён» в журнале не отличить от честного накопления

См. пункт 8: фолбэк «серии нет в реестре» пишется на DEBUG, а итоговая строка дайджеста
показывает просто `mode=carry`. Если Директорат перестанет резолвиться (дрейф ключа, не тот
каталог реестра, потерянный env `MEETING_NOTARY_REGISTRY_DIR`), в журнале это будет выглядеть
как нормальная работа.

**Что сделать:** поднять строку до INFO и/или добавить в итоговую строку источник
(`mode=carry source=fallback-not-in-registry` против `source=registry`).

### ⚪-9. Реестр перечитывается на каждый вызов

Прогон: один `_is_last_only_series` = 1 чтение файла; четыре роута в одном dispatch = 4
чтения; 10 записей статуса = 10 чтений (гейт в `set_task_status` зовётся на каждую задачу, а
сверщик ходит по задачам циклом). Кеша нет. На текущих объёмах не больно, но это лишний
дисковый ввод на горячем пути и лишняя площадь для 🔴-2. Дешёвый кеш по mtime либо проброс
уже прочитанного `watched` в цикл (параметр `watched=` уже есть) снимает и то, и другое.

### ⚪-10. Выжимка с датой в чужом формате делает шпаргалку молча «вчерашней»

Выжимка с датой `15.07.2026` не попадает в `list_series_digests` вовсе, `latest_digest_date`
отдаёт предыдущую встречу, и шпаргалка уверенно показывает список позапрошлой встречи под
шапкой «зафиксировали на прошлой встрече». Фильтр досталcя от существующего кода, дата
строится программно — вероятность низкая, но в `carry` этот сбой прятался в кумулятивном
хвосте, а в `last-only` становится видимым и молчаливым.

### ⚪-11. Справочный ответ не ограничен по частоте

Любой участник группы, повторяя reply со статус-маркером, получает
`LAST_ONLY_STATUS_REPLY` каждый раз. Секретов в фразе нет, класс тот же, что у
`DIGEST_UNPARSED_HINT` в накоплении, — отмечаю как известную площадь для шума, а не как
дефект фазы.

---

## Что в фазе сделано хорошо (чтобы не потерялось при правках)

- Направление fail-safe для главных веток выбрано верно и обосновано по существу, а не «на
  всякий случай»: хвост живёт только в протоколе, потеря необратима.
- Гейт статус-стора поставлен у **физического писателя** (`set_task_status`), а не только в
  роутах — это снимает целый класс упущений «шестой писатель не знал про режим».
- Оба call-site протокола действительно закрыты (проверил чтением: условие в
  `clarify_worker` не перевёрнуто, `open_tasks_block` инициализирован `""`).
- РИСК3 закрыт по существу: `commit_pending_shown` не ставит маркер онбординга в шпаргалке.
- Фильтр по происхождению стоит ДО капа — иначе `OPEN_TASKS_MAX` съел бы слоты старьём.
- В шпаргалке слепок нумерации не пишется, а при возврате в `carry` возвращается с первого
  же дайджеста — проверено прогоном.

---

## Итог

Замысел фазы реализован и держится на прогоне: шпаргалка показывает только прошлую встречу,
статусов не просит, хвост в протокол не печатается в обоих call-site, статус-машина молчит,
накопление внутри документа не тронуто, утечек личных данных нет, адресация чистая, повторы
и переотправка отработаны. **Блокирует сдачу две вещи:** серия-накопление всё-таки изменилась
на глазах у людей — время встречи уехало на час и потеряло «МСК» (критерий 4), и битый реестр
вместо отката в накопление роняет дайджест, сверщик, финализатор и слушатель (последний — в
цикл падений). Плюс шесть 🟡, из которых самые дорогие — опечатка в реестре, уводящая
Директорат в шпаргалку, и grep-тесты, пропускающие перевёрнутый гейт хвоста.
