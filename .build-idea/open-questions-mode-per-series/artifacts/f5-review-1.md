## Вердикты по 8 пунктам

### 1. Права и владение — 🔧 починить

Схлопывание запускают два актора, и оба легитимны: владелец (ответ на вечерний блок → дедуп при
записи) и планировщик (раз в 15 минут → дедуп очереди). Чужой руки в записи нет — snapshot
пишет только вечерний блок, реестр под flock.

**Но ключи схлопывания владельцу не принадлежат.** `iCalUID`, ссылка на комнату и время старта
приезжают из события календаря, а его автор — тот, кто прислал приглашение. Сегодня на пути
записи в реестр точного ключа нет вообще (вечерний блок `iCalUID` в snapshot не кладёт — признано
самим исполнителем), поэтому решение принимается по паре «время + URL», обе половины которой
задаёт приглашающий. Отсюда прямой ответ на вопрос «можно ли чужим действием убрать нужную
встречу»: **да**. Достаточно приглашения на то же время с той же постоянной комнатой (`@t11`
владелец рассылает сам, ссылку легко скопировать из прошлого приглашения) — и «да» владельца по
этому приглашению не заведёт новую запись, а переиспользует чужую (доказано прогоном, 🔴 1).
Протокол чужого разговора уедет в чат и разметку первой встречи.

Вторая сторона того же: отказ по ОДНОЙ копии гасит запись, заведённую по ДРУГОЙ (🔴 2).

Что сделано правильно и это важно: метку `created_by_rejection` (лицензия ретеншну удалить
запись) новый код на чужую запись не ставит нигде, а при оживлении снимает. Проверено прогоном —
ретеншн через 30 дней запись владельца по новым путям не унесёт.

### 2. 🔴 Схлопывание = потеря записи. Прогон на ловушках — 🔧 починить

Восемь ловушек из задания, прогон `trap_iss54.py`:

| Ловушка | Ожидание | Факт |
|---|---|---|
| Две РАЗНЫЕ серии в одной комнате в **разное** время | не схлопывать | ✅ две записи |
| Одно событие в двух календарях | схлопнуть | ✅ один старт |
| Комната и время совпали, `iCalUID` **разные** (вето) | не схлопывать + предупредить | ✅ две записи + WARNING |
| Одна запись отказная (`enabled=false`, `created_by_rejection`), вторая живая | не воскрешать лишнего | ⚠️ «да» оживляет **первую в файле** — отказную; живая остаётся включённой → **две включённые записи на одну встречу** (🟡 4) |
| Обе отказные | оживить одну | ✅ одна |
| `iCalUID` нет у обеих (старый реестр) | схлопнуть по страховке | ✅ один старт |
| `iCalUID` = `""` / `None` / `42` / `[]` / `{}` / `"   "` (в событии, в записи реестра, в snapshot) | не падать, деградировать в страховку | ✅ 16 подслучаев, rc=0, поведение то же |
| **Две РАЗНЫЕ встречи, одна комната, одно время, `iCalUID` нет** | не схлопывать | ❌ **схлопнуты в одну запись** (🔴 1) |

Вето точного ключа работает ровно там, где точный ключ есть у **обоих**. Достаточно, чтобы у
одной стороны его не было, — и страховка съедает доказуемо отдельную встречу: в ловушке из трёх
элементов (`koord` с `k@g`, `bez-ical` без ключа, `vyst` с `v@g`) в одной комнате в одно время
очередь вышла из двух — `bez-ical` проглочен, при том что рядом система сама печатает WARNING
«две РАЗНЫЕ встречи». То есть вето и страховка соседствуют в одном тике и решают по-разному.

### 3. Валидация на границе — ✅ в порядке

`event_ical_uid()` (`lib/gcal.py:280`) отбивает не-dict, не-str, пустую строку и пробелы;
`_instant_key`/`_url_key`/`_clean_str` в обоих файлах типобезопасны. Прогнал мусор в трёх точках
входа — в поле события, в `ical_uid` самой записи реестра (владелец правит YAML руками) и в
элементе snapshot: планировщик не падает (rc=0), применение ответа не падает, `error` не
возвращается. Битый элемент очереди невозможен по построению (`_queue_item` собирает его из уже
разобранного `datetime`), битый элемент snapshot по-прежнему отсеивается поштучно
`sanitize_snapshot_items` — фаза 4 не задета.

Направление отказа безопасное: нечитаемое время или мусорный URL → ключ не собрался → **не
схлопываем** (две записи, два бота), а не «тихо потеряли». Проверено на `url_in_event` = `42` /
`[]` / `{}` / `None` / `""` — везде две записи.

### 5. Fail-closed — ✅ в порядке

Новых глушащих `except` в дифе **два**, оба — `except ValueError` в `_instant_key`
(`scheduler.py:205`, `meetings_apply_reply.py:849`), оба возвращают `None`, что ведёт к
«не схлопывать». Тихого дубля из-за них не будет (дубль как раз и есть их результат — но он
громкий: две записи, два старта в очереди), тихой потери — тоже.

- **Календарь недоступен** — `_expand_google_calendar` падает на своей записи, обработчик
  пофайлово ловит (код фазы 0), запись просто не попадает в очередь. Дедуп решения по ней не
  принимает. Если поле не пришло от Google — `_queue_item` берёт `ical_uid` из записи реестра
  (`scheduler.py:467-470`), то есть точный ключ переживает молчание календаря.
- **Реестр не читается** — прогнал `load_watched` → `OSError`: не проглочено, летит наверх
  (в бою — в `except Exception` `main()`, `push` + rc=1). Владелец узнаёт.
- **Реестр не пишется** — путь фазы 4 (`save_watched` → `save_failed`, «Ни одно решение не
  записано») дедуп не трогал, 59 тестов зелёные.
- **Битый элемент** — `find_duplicate_watched` вызывается внутри пофайлового `try` фазы 4;
  исключение → элемент в `skipped`, остальные решения владельца доезжают.

Единственный способ тихо потерять нужную запись — не `except`, а семантика слабого ключа (🔴 1).

### 6. Повторы и гонки — ✅ в порядке

- **Дважды применённый один и тот же ответ**: прогон — одна запись оба раза, id тот же.
- **`dedupe_queue` дважды**: прогон — тот же результат (в т.ч. после переноса `ical_uid` на
  выжившего).
- **Два одновременных прогона планировщика**: нового разделяемого состояния не заведено,
  `dedupe_queue` чистая функция над списком в памяти, очередь пишется атомарно
  (`_atomic_write_json` → `os.replace`). Оба прогона на одном реестре дадут байт-в-байт одну
  очередь — выбор победителя детерминирован (первый по порядку + правило «человеческое имя
  бьёт автоимя»).
- **Применение ответа** по-прежнему целиком под одним flock — дедуп внутри лока.
- Замечание: детерминированность держится на **порядке записей в `watched.yaml`**. Владелец
  переставил две строки руками — сменился победитель (🟡 5).

### 7. Момент проверки — 🔧 починить

Два места дедупа считают одно и то же **по разным правилам**, и на одних данных решают
по-разному. Три расхождения, третье доказано прогоном:

1. **Разный URL.** Реестр сверяет `event_url` — ссылку из события. Планировщик сверяет
   **разрешённый** url, где явная комната записи важнее ссылки события (`_resolve_url`,
   `scheduler.py:423-430`). Две встречи с разными ссылками в событиях, но с `room: @t11`
   в записях: реестр держит две записи (ссылки разные), очередь схлопывает в одну (комната
   одна). Прогон `test_h9` — очередь из одного элемента, вторая встреча не записана.
2. **Разная строгость.** Реестр требует `type == "google-calendar"` и совпадения рода
   «серия / только этот экземпляр»; очередь не смотрит ни то, ни другое. Значит `manual`
   (cron) и `one-off` записи схлопываются с календарными по «комната + время», а точного ключа
   у них не бывает никогда (⚪ 10).
3. **Разный ключ на одних и тех же данных сегодня.** У планировщика точный ключ есть (берёт из
   события), у записи в реестр — нет (вечерний блок `iCalUID` в snapshot не кладёт). То есть
   прямо сейчас в бою реестр решает слабым ключом, а очередь — точным. Это не будущий риск,
   это текущий режим работы.

Исполнитель расхождение №2 признаёт осознанным («на пересечении в реестре временно живут две
записи, но бот один»). Цена признания: **какая из двух записей определит чат доставки протокола,
company/visibility и `open_questions_mode`, решает порядок строк в YAML.**

### 8. Как узнаем, что сломали — ✅ в порядке с оговоркой

Лог о схлопывании по плану есть и он хороший. В `scheduler.log`:

- `INFO Схлопнул дубль встречи (один iCalUID vystavka-st1@google.com): «koord» [primary] и
  «bez-ical» [anzhee@example.com] @ 2026-08-06T03:00 — веду по «koord», второй старт не ставлю`

- `WARNING Две РАЗНЫЕ встречи (разный iCalUID) в одной комнате в одно время … — веду обе` —

Всё это снял с реального прогона, не с отчёта.

Оговорка: на стороне реестра владелец видит схлопывание в Telegram **только для «да»** («это та
же встреча, что уже в реестре («…»)»). Для «нет» и «никогда» ему приходит обычная фраза

запись, остаётся только в логе. Прогон подтвердил: `summary` не содержит id погашенной записи.
Это часть 🔴 2.

## Находки

### 🔴 1. Страховочный ключ «время + URL» схлопывает две РАЗНЫЕ встречи в одну запись — и сегодня он единственный работающий на пути в реестр

`meetings_apply_reply.py:905-908`, `scheduler.py:270-272`.

Прогон `trap_iss54.py::test_h4` — две разные встречи, «Координация» и «Разговор с юристом»,
одно время, одна постоянная комната, `iCalUID` ни у одной (ровно сегодняшний бой: вечерний блок
поле в snapshot не кладёт):

```
записей: ['oneoff-6b5b7ccc']
summary: 1. Координация — записал только этот экземпляр
         2. Разговор с юристом — это та же встреча, что уже в реестре («oneoff-6b5b7ccc»),
            просто видна в двух календарях: пишу по ней, второй записи не завожу
```

Вторая встреча не записана вовсе, а владельцу сказано неправду — это не копия, это другой
разговор. Дальше по течению выживший определяет, **в какой чат уедет протокол и с какой
разметкой** (это формулировка самого исполнителя, п. «что решил сам» №1): протокол разговора с
юристом уедет в чат координации.

Почему это не корнер-кейс: `iCalUID` на пути «ответ владельца → реестр» отсутствует **всегда**
(включающая строка — в `meetings_evening_block.py`, файл вне карты владения). Значит каждое
решение дедупа при записи принимается сегодня слабым ключом. Вето точного ключа, которым
закрывали риск 5, на этом пути не работает ни разу.

Тот же корень на стороне очереди: `test_h9` (разные ссылки в событиях, общая комната `@t11` в
записях) — вторая встреча выпала из очереди; `test_c2` (три встречи, у средней нет `iCalUID`) —
средняя проглочена, при том что рядом печатается WARNING «две РАЗНЫЕ встречи».

Что просить: либо не считать «комната + время» доказательством тождества без второго признака
(например, совпадения `title` или `recurring_event_id`), либо ограничить страховку случаем
«обе стороны без точного ключа И названия совпадают», либо (лучше всего) включить `iCalUID` в
snapshot — одна строка, исполнитель её описал, но она вне его карты владения. Пока не включена,
критерий 9 держится на ключе, который путает разные встречи.

### 🔴 2. «Нет» / «никогда» по копии гасит живую запись владельца, следа под `event_id` копии не оставляет, и владельцу не сказано, что именно погашено

`meetings_apply_reply.py:780-812` (`_mark_rejected`), `544-551` (`ignore_forever`).

Три сцепленных эффекта, все на прогоне:

**(а) Гасится настроенная запись владельца.** `test_h3`: в реестре живая запись
`anzhee-vystavka` (`room: @t11`, `chat_id`, `open_questions_mode: strict`) — владелец её сам
завёл. Вечерний блок предлагает **копию того же события** из второго календаря (он копию не
узнаёт — сам исполнитель это признаёт как незакрытый разрыв). Владелец отвечает «нет» в смысле
«я это уже завёл, не спрашивай» → `enabled=False` на его записи, бот на встречу не придёт.
До фазы 5 то же «нет» завело бы отдельную выключенную запись, а живая осталась бы работать.
Это изменение поведения в сторону потери записи, которую владелец уже одобрил.

**(б) Обещание фазы 4 нарушено.** `test_h2`: после «нет» по копии в реестре нет записи под
`event_id` копии (`{'e-b'}`, а `e-a` отсутствует). Вечерний блок сверяется по паре
`(calendar_id, event_id)` → завтра предложит эту же копию снова. При этом бот сказал в
подтверждении: **«не записываю, больше про эту встречу не спрошу»**. Это ровно тот дефект,
который закрывала ISS-53, вернувшийся на пути с близнецом. 59 тестов фазы 4 его не ловят —
среди них нет ни одного с записью-близнецом.

**(в) Владельцу не сказано, что именно погашено.** Прогон `trap2`: «никогда» по копии гасит
серийную запись `anzhee-koord` со всей её разметкой, в Telegram уходит «больше не предлагаю эту
серию», id погашенной записи — только в `apply-reply.log`. Путь «да» такую строку печатает
(«это та же встреча, что уже в реестре («…»)»), пути «нет» и «никогда» — нет. Асимметрия ничем
не оправдана: как раз выключение чужой записи и надо показывать.

Что просить: (б) писать запись отказа под `event_id` копии **дополнительно** к гашению
близнеца (иначе обещание — ложь), (в) в `summary_lines` для `reject`/`ignore_forever` называть
id погашенной записи ровно как в пути «да». (а) — продуктовое решение владельца, но с (б)+(в)
оно перестаёт быть тихим.

### 🟡 3. Слабый ключ вписывает ТОЧНЫЙ ключ в чужую запись — необратимо

`_merge_fingerprint` (`meetings_apply_reply.py:935-944`) дописывает `ical_uid` в запись,
найденную по страховке. Прогон `test_h8`: запись «Координация» без точного ключа получила
`ical_uid: vystavka@google.com` — точный ключ **другой** встречи. Оттуда он уезжает в элемент
очереди (`scheduler.py:469`) и начинает считаться доказательством: дальше вето и схлопывание
работают по заведомо ложному ключу, и откатить это нечем — в YAML лежит правдоподобное значение.
Одна ошибка страховки превращается в постоянную. Лечится вместе с 🔴 1; отдельно —
не проставлять `ical_uid` по совпадению, найденному не по `ical_uid`.

### 🟡 4. Дедуп работает с ПЕРВЫМ найденным дублем, а не со всеми

`find_duplicate_watched` возвращает первое совпадение и не смотрит, есть ли ещё
(`meetings_apply_reply.py:929-932`). В боевом реестре прямо сейчас два дубля на одну встречу
(`oneoff-ef50c3ab` + `anzhee-vystavka-st1-20260727`; чистку исполнитель оставил владельцу до
Фазы 7), поэтому сценарий не гипотетический:

- `test_h1` — «нет» гасит один дубль, второй остаётся `enabled=true`. Отказ владельца исполнен
  наполовину.
- `trap2` (г) — «да» оживляет **отказный** дубль (он первый в файле) и не трогает живой: на
  выходе **две включённые записи на одну встречу**, то есть ровно то состояние, которое ISS-54
  и убирает. Перевернул порядок строк — ожил другой. Плюс у ожившей отказной снимается
  `created_by_rejection`, и ретеншн её больше никогда не уберёт: в реестре остаётся вечный
  зомби-дубль.

Двойного бота снимает очередь, так что критерий 9 держится, но инвариант «одна встреча — одна
запись» — нет. Просить: искать и обрабатывать **все** совпадения, а не первое.

### 🟡 5. Реестр и очередь сверяют разные URL и разной строгостью — победитель зависит от порядка строк в YAML

Разобрано в пункте 7. Практический вывод для владельца: две встречи в общей комнате `@t11`

порядок строк в `watched.yaml`, который никто не считает значимым.

### 🟡 6. Название встречи впервые попало в `apply-reply.log`

### 🟡 7. «Да» по копии снимает «никогда» с записи-глушилки разовой встречи

`trap2`: запись с `ignored=true` после «да» по копии становится `enabled=true, ignored=false`,
в summary — «это та же встреча, что уже в реестре». Про снятое «никогда» не сказано ни слова.
Для серии это невозможно (род записи не совпадёт), для разовой встречи — происходит. Владелец
одним «да» по дублю отменяет собственное «никогда» и не узнаёт об этом.
