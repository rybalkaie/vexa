### 2.1 🔴 Дрейф ключа серии → бот врёт пользователю

`series_for_chat` нормализует ключ ТОЛЬКО для схлопывания дублей, а наружу отдаёт **сырую строку из
реестра**. Дальше эта строка идёт в `_resend_digest`/`_resend_protocol` как **имя папки серии**.

```
$ python3 trace2b_drift_and_order.py
=== A. дрейф ключа серии в реестре ===
series_for_chat(-1001111) = [' Anzhee-Direktorat ']   ← сырой slug из реестра
папка серии на диске: ['anzhee-direktorat']
код пойдёт в папку:   '…/protokoly2/ Anzhee-Direktorat '
такая папка есть?     False

  НАЖАЛ в чате серии: «пришлите открытые вопросы»
  вернул=True; бот сказал: ['БОТ → -1001111: Открытых вопросов по этой встрече сейчас нет — список пуст.']

  НАЖАЛ в чате серии: «пришли протокол»
  вернул=True; бот сказал: ['БОТ → -1001111: Протокол этой встречи пока не готов — пришлю, как соберётся.']
```

Оба ответа — ложь: и вопросы, и протокол лежат на диске. Это ровно тот класс тихого провала, от которого
защищает ISS-7, и докстринг функции его декларирует («Возвращается РЕАЛЬНЫЙ slug первой записи»), но
реальный slug из реестра ≠ имя папки. Прежний реплай-путь этим не болел: серия приходила из `meta.json`,
который пишет finalize каноничным именем. Ветка ISS-52 впервые пускает **человеческую строку из реестра**
в файловые пути. Чинить: отдавать каноничный ключ — среди записей нормализованной серии выбирать ту,
что проходит kebab-правило валидатора (`^[a-z0-9][a-z0-9_-]*$`), иначе минимум `strip()` пробелов и кавычек.

### 2.2 🔴 Реестр читается с диска на КАЖДОЕ сообщение в группе

Блок `_chat_context_series` стоит **до** дешёвого регекс-детекта `detect_artifact_request`:

Цена одного чтения на боевом объёме — см. след 4: **9.6 мс**. До фазы 1 функция выходила первой строкой
(`if not isinstance(msg.get("reply_to_message"), dict): return False`) и не стоила ничего.
Чинить: перенести блок `if not series: chat_series, _err = _chat_context_series(...)` **после**
`detect_artifact_request` и гейта `detect_status_intent`. Поведение не меняется: `surface` от фолбэка
не зависит, он и так остаётся `None`.

### 2.3 🔴 Битый руками `watched.yaml` роняет процесс listener'а

`_read_yaml` на не-словаре верхнего уровня делает `raise SystemExit`. `SystemExit` — наследник
`BaseException`, а `_chat_context_series` ловит `except Exception`. Главный цикл — тоже `except Exception`.

```
$ python3 trace2c_systemexit.py
верхний уровень — СПИСОК (правил руками)   → !! SystemExit('…/watched.yaml: ожидался словарь верхнего уровня,
                                              получено list') — ВЫЛЕТЕЛ ИЗ РОУТА | бот: ['(тишина)']
верхний уровень — СТРОКА                   → !! SystemExit(… получено str) — ВЫЛЕТЕЛ ИЗ РОУТА
битый YAML (табуляция/кавычка)             → вернул False | бот: ['(тишина)']   ← YAMLError ловится, ок
watched: не список                         → вернул False | бот: ['(тишина)']   ← ок
нормальный файл (контроль)                 → вернул True

ловит ли главный цикл listener'а SystemExit?
      3117|                     try:
      3118|                         process_message(token, allowed_chat, msg)
      3119|                     except Exception as e:  # noqa: BLE001
      3120|                         logger.exception("process_message упал: %s", e)
      3121|             save_offset(offset)
```

`save_offset(offset)` стоит ПОСЛЕ разбора пачки — при вылете он не выполняется, значит после рестарта
Telegram отдаёт то же сообщение и процесс падает снова: **петля падений**. Триггер — любое текстовое
сообщение в любой группе, потому что фолбэк читает реестр до детекта (см. 2.2). До фазы 1 такой
экспозиции не было: единственный per-message путь к реестру (`maybe_route_to_set_chat_command`) открывался
только после узкого парса команды владельца. Файл при этом **правится руками** — Фаза 7 плана прямо
предписывает пройти реестр и проставить режим каждой серии. Чинить: ловить `BaseException` (или явно
`SystemExit`) в `_chat_context_series`.

### ⚪ мелочи, найденные по ходу

* `series_open_questions_mode`: `isinstance(raw, str) and not isinstance(raw, bool)` — вторая проверка
  мертва, bool никогда не str.

* `meetings_listener.py:1214` — `any(w.get("series") == reply_slug …)` недостижим: если точное совпадение

### 🟡 `_err` из `_chat_context_series` выбрасывается вызывателем

Докстринг обещает: «реестр не прочитался → вторым элементом едет причина, и вызыватель показывает прежнюю
подсказку, а не молчит». Фактически `_err` присвоен в `_err` и не используется: при `is_reply=False`
роут возвращает `False` (тишина) независимо от причины, а лог — `logger.debug` (на проде не виден).
То есть недоступный реестр = фича тихо выключена. Либо править докстринг, либо поднять лог до `warning`.

## Что следы вскрыли

### 🔴 Чинить в фазе

1. **Битый руками `watched.yaml` роняет процесс listener'а в петлю падений** (2.3).
   `_read_yaml` бросает `SystemExit`, `_chat_context_series` ловит только `Exception`, главный цикл — тоже;
   `save_offset` не выполняется → после рестарта то же сообщение → снова падение. Триггер — любое
   текстовое сообщение в любой группе. Экспозиция новая: до фазы 1 per-message чтения реестра не было.
   Фикс: ловить `BaseException`/`SystemExit` в `_chat_context_series`.
2. **`series_for_chat` отдаёт сырой ключ серии → бот врёт «список пуст» / «протокол не готов»** (2.1).
   Строка из реестра уходит в файловый путь папки серии. Ровно класс ISS-7, от которого функция
   декларирует защиту. Фикс: отдавать каноничный slug (kebab-правило валидатора), минимум — `strip()`.
3. **Реестр читается с диска на каждое сообщение в группе — 9.6 мс** (2.2 + след 4).
   Фолбэк стоит до дешёвого регекс-детекта. Фикс: перенести блок `_chat_context_series` после
   `detect_artifact_request` и гейта `detect_status_intent`; поведение не меняется.
