## 2. Дубли — ПОЧИНИТЬ (🟡-4)

Прямой ответ на вопрос: **исходную формулу исполнитель не устранил, он её продублировал.**
Две копии «как узнать TZ отображения» живут в двух файлах:

- `meetings_evening_block.py:82` — `ZoneInfo(os.environ.get("MEETING_NOTARY_DISPLAY_TZ", "Asia/Dubai"))`, при импорте;
- `meetings_apply_reply.py:82-83` — `DISPLAY_TZ_ENV` + `DEFAULT_DISPLAY_TZ = "Asia/Dubai"`, на каждый вызов.

Имя переменной и дефолт — литералы в обоих файлах. ISS-55 ровно про то, что эти две копии разъехались.
Сейчас они совпадают, но **инвариант ничем не закреплён**: ни один из 22 тестов не сравнивает ДЕФОЛТЫ
двух модулей. `test_question_and_confirmation_agree_in_any_tz` патчит и env, и `meb.DISPLAY_TZ` явно —
путь резолва дефолта не задействован вовсе; `test_fmt_when_short_default_is_dubai` пинит дефолт только
`meetings_apply_reply`; `test_evening_block_reads_the_same_env_var` задаёт env явно. Итог: смени завтра
дефолт в одном файле — все 22 теста зелёные, ISS-55 вернулся.

Как правильно для этого проекта: общие хелперы тут лежат в `scripts/notary/lib/*.py` и импортируются как
`from notary.lib.X import Y` (оба файла уже так тянут `notary.cli.registry` и `notary.lib.gcal`).
Правильный фикс — одна функция `display_tz()` + имя env + дефолт в `notary/lib/`, оба модуля импортируют.
Это делает класс бага ISS-55 структурно невозможным. Дешёвый минимум, если трогать блок не хочется, —
ратчет в тесте: при очищенном env `importlib.reload(meb)` и `assertEqual(str(meb.DISPLAY_TZ), mar.DEFAULT_DISPLAY_TZ)`.

Про форматирование времени: `fmt_when_short` vs `fmt_when`/`fmt_when_simple` — **не дубль**, строки
намеренно разные («завтра 12:00» / «пт 06.08 12:00» / «06.08 12:00»). Дублируется только резолв TZ.

## 3. Мёртвый код

- `fmt_when_short:248-250`: `try: local = dt.astimezone(display_tz()) except Exception: local = dt` —
  **ветка недостижима**: `display_tz()` по построению не бросает, `astimezone` на aware-dt с валидной
  зоной тоже. Выкинуть (⚪-9).
- `display_tz:234-236`: внутренний `except → return timezone.utc` — достижим только при сломанной tzdata,
  и тогда молча выдаёт неверный час без строки в лог (⚪-10).
- `pruned_rejections` в JSON-ответе: единственный потребитель (`meetings_listener.py:2828-2856`) читает
  `summary_lines`, `pending_room`, `skipped`, `error`, `no_decisions`, `hint` — этот ключ **не читает никто** (⚪-11).
- Первый guard `is_stale_rejection` (`not rejected_at and not rejected_start_at`) логически дублирует
  `rejection_meeting_day() is None`, но НЕ мёртв: без него каждая disabled-запись без меток даёт WARNING
  на каждый прогон. Оставить.

## 4. Обработка ошибок

Три «проглатывания» — два безопасные, одно fail-open:

- `display_tz` → warning + дефолт: **fail-safe**, правильно (мусор в env не роняет применение ответа). ✔
- `finally: release_watched_lock() except: pass` — досталось от прежнего кода, в `finally` корректно. ✔
- 🟡-5 **fail-open**: `main():619-630`, hard-проверка свежести snapshot. `except Exception:` ставит
  `delta_days = None`, а дальше `if delta_days is not None and ... > 1` — то есть при нечитаемом
  `shown_date` проверка **молча выключается целиком** и реестр правится по, возможно, чужому дню.
  Комментарий рядом сам называет её «последний рубеж». Блок исполнитель трогал (менял там TZ),
  так что чинить уместно тут: нечитаемый `shown_date` → отказ применять, а не тихий пропуск.

## 7. Ничего лишнего

**Два поля `rejected_at` + `rejected_start_at` — оправданы, не выкидывать.** План просит «дату отказа»
дословно, а ретеншн по плану считает от **даты встречи** — это разные дни, и они реально расходятся
(в понедельник сказать «нет» встрече в пятницу). Одним полем либо ломается формулировка плана, либо
ретеншн считает не от того дня. Валидацию реестра они не задевают.

**Попутные правки — все три оправданы:**
- второй зашитый `Asia/Dubai` в `main()`: это настоящий баг — `shown_date` пишется блоком
  через `astimezone(DISPLAY_TZ)` (`meetings_evening_block.py:503`), сравнивать его с дубайским днём было неверно;
- формулировка `reject` в промпте: обязательна, иначе модель описывает владельцу поведение, которого больше нет;
- текст подтверждения — продуктовый, вынесен владельцу. Но см. 🔴-1: обещание «больше про эту встречу
  не спрошу» код сейчас **нарушает**.

**Что выкинуть** (по просьбе — отдельным проходом по дифу): ⚪-9 (недостижимый `except` в `fmt_when_short`),
⚪-10 (либо лог, либо снос молчаливого `return timezone.utc`), ⚪-11 (`pruned_rejections` в JSON — либо
показать владельцу в ответе демона, либо убрать; строку в лог оставить обязательно — это единственный
аудит-след удаления данных).

## Находки по приоритету

### 🔴 1. Отклонённая встреча начинает рапортоваться как «запись сдвинул» / «запись снял»

Побочный эффект решения «отказ = обычная запись watched». Запись-отказ попадает в `watched_idx`, а блок
использует тот же индекс не только для фильтра «новых», но и для сборки кэша `known`
(`meetings_evening_block.py:408-431`) и для детекта переносов/отмен (`:341-406`). Проверено на живом коде:

```
после «нет» в реестре: [('oneoff-348bbe75', enabled=False, event_id='inst-a')]
кэш known после вечера 2: ['inst-a']          ← отклонённая встреча попала в «отслеживаемые»
вечер 3 (встречу перенесли):  🔄 Перенесённые (запись сдвинул):
                              • Координация по маркетплейсам: пт 07.08 10:00 → пт 07.08 11:00
вечер 4 (встречу удалили):    ❌ Отменённые (запись снял):
                              • Координация по маркетплейсам — пт 07.08 10:00
```

Бот сообщает владельцу, что «сдвинул/снял запись» встречи, которую тот **запретил записывать** — и делает
это сразу после того, как пообещал «больше про эту встречу не спрошу». Это ровно тот класс, ради которого
заводился ISS-53 («он меня не слышит»), только с другой стороны. Ни одним тестом не покрыто.

Честно: класс дефекта **пред-существует** для `ignore_forever` (та же ветка кода). Фаза 4 переводит на этот
путь **самое частое ежедневное действие владельца** — поэтому из редкой аномалии он становится регулярным.

**Фикс — одно условие в двух местах** `meetings_evening_block.py`: при сборке `cur_start_by_eid` (:354-362)
и `new_known` (:410-424) пропускать записи с `enabled=false`. Фильтр «не предлагать» (:319-328) при этом
не меняется. Заодно чинится и пред-существующая дырка с `ignore_forever`. Требует правки соседнего файла —
исполнитель сознательно его не трогал, решение за оркестратором.
