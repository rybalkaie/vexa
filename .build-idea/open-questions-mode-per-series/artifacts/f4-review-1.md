## П.5 🔴 Ретеншн (удаление записей) — **починить**

### Что проверено и корректно
16 записей-ловушек, `today=2026-08-05`, порог 30 (прогон `p5_retention.py`):

| ловушка | ожидание | факт |
|---|---|---|
| живая запись (`enabled=True`) + метки отказа | жить | **выжила** |
| глушилка серии (`ignored=True`) + метки | жить | **выжила** |
| нет ключа `enabled` вообще | жить | **выжила** |
| `enabled: 'false'` строкой (кавычки в YAML) | жить | **выжила** (в безопасную сторону) |
| ровно 30 дней | жить | **выжила** |
| 31 день | удалить | удалена |
| встреча в будущем | жить | **выжила** |
| мусор в обеих датах | жить | **выжила** + warning |
| просто `disabled` без меток (legacy) | жить | **выжила** |

Часовые пояса: смещения `+14:00`, `−11:00`, `+04:00`, `+00:00` на рубеже 30/31 дня итог не

пороге 30. Живая запись под нож не попадает: три условия (`есть метки` ∧ `не enabled` ∧
`не ignored`) закрывают прямые пути. **Ядро ретеншна написано аккуратно.**

### 🟡 Ф4-12. Метка отказа = лицензия на удаление, и код ставит её на ЧУЖИЕ записи
`_mark_rejected:526-534` — при найденной существующей записи штампует `rejected_at` /
`rejected_start_at` поверх неё, не отличая «эту запись создал я» от «эту запись вёл владелец».

Прогон: активная запись с `room`, `telegram_chat_id: -100500`, `genre: 1-на-1`,
`open_questions_mode: carry` после «нет» получает метки; через 30 дней после встречи
`prune_stale_rejections` удаляет её **целиком вместе со всей разметкой** (`УДАЛЕНА`).

Три достижимых пути:
1. ответ на то же 📅-сообщение через полночь — допуск свежести снапшота ±1 день (`main():630`),
   вчерашнее «да» и сегодняшнее «нет» ложатся на одну запись;
2. дубль номера в одном ответе модели (Ф4-1: `accept_once` + `reject` по `n=1` — доказано,
   не дедуплицируется);
3. `meeting-watch enable` → `meeting-watch disable`: CLI (`meeting_watch.py:307`) трогает
   только `enabled` и метки не снимает. Прогон:
   ```
   метки отказа после CLI-переключений остались: True / True
     29 дн после встречи -> жива
     30 дн после встречи -> жива
     31 дн после встречи -> ЗАПИСЬ УДАЛЕНА НАВСЕГДА
   ```
   Для сравнения: та же пауза на записи БЕЗ меток — «через 400 дней жива».

Что сломается: владелец «поставил на паузу» встречу, а через месяц её нет в реестре — вместе
с привязкой к чату, жанром, режимом открытых вопросов и переговоркой. Восстановить нечем
(реестр не в git, `.bak` одношаговый).
Чинить: не штамповать метки на запись, которой у нас не было, — при найденной существующей
записи ограничиться `enabled=False` (владелец увидит её в `meeting-watch list --all`), либо
удалять только записи, у которых `id` начинается с `oneoff-` **и** нет ни одного поля разметки.

### 🟡 Ф4-13. «Нет» после «никогда» снимает `ignored` и делает глушилку временной

## П.6 Повторы и гонки — **в порядке**

Реестр читается-пишется под `flock` (`registry._acquire_lock:78`, блокирующий `LOCK_EX`),
лок держится весь read-modify-write: `load_watched(lock=True)` (`:339`) → `save_watched`
(`:459`, отпускает в `finally`) либо `release_watched_lock` в `finally` самого
`apply_decisions` (`:471-477`). Ретеншн едет под тем же локом, отдельной гонки не создаёт.

Прогоны настоящими процессами:
```
2 одновременных apply по разным встречам -> в реестре 2 записи (обе)
10 одновременных apply по разным встречам -> в реестре 10 записей, ни одной потери
один и тот же ответ владельца, обработан 3 раза -> 1 запись
```
Идемпотентность обеспечена `_mark_rejected:526` (находит существующую запись и обновляет
метки вместо добавления). Повтор записи не плодит. ✅

## П.7 🔴 Момент проверки условия — **починить**

Проверка стоит **в момент показа**: `index_watched` (`meetings_evening_block.py:119`) индексирует
записи независимо от `enabled` — утверждение исполнителя проверено прогоном:
```
index_watched({… enabled: false …}) -> [('primary', 'inst-a')]
```
Плюс второй, независимый рубеж в момент записи: `scheduler.py:109` пропускает `enabled=false`.
Два гейта вместо одного — это хорошо.

«Передумал» работает: «нет» → «да разово» даёт `enabled=True` и снимает метки (тот же id).

### 🔴 Ф4-15. Отклонённая встреча попадает в «Перенесённые (запись сдвинул)» и «Отменённые (запись снял)»
`meetings_evening_block.py:408-431` строит кэш `known` из всего, что нашлось в `watched_idx`, —
а после фазы 4 туда попадает и отказная запись. Из `known` растут разделы `moved_items`
(`:365-386`) и `cancelled_items` (`:387-406`).

Сквозной прогон (блок → «нет» → блок → перенос/отмена):
```
1) пустой реестр -> блок предлагает: ['inst-a']
2) владелец сказал «нет», в реестре: ['oneoff-348bbe75']
3) следующий вечер -> предложений: 0 | known-кэш: ['inst-a']      ← ISS-53 починен
4) встречу ПЕРЕНЕСЛИ -> блок пишет владельцу:
     📅 Встречи и запись на неделю
     🔄 Перенесённые (запись сдвинул):
     • Координация по маркетплейсам: пт 07.08 13:00 → пт 07.08 15:00
5) встречу ОТМЕНИЛИ -> блок пишет владельцу:
     ❌ Отменённые (запись снял):
     • Координация по маркетплейсам — пт 07.08 13:00
```
Что сломается у пользователя: владелец сказал «эту не пиши», а бот вечером рапортует, что
«сдвинул запись» и «снял запись» ровно по этой встрече. Записи нет и не было — бот заявляет
о работе, которой не делал, по той самой встрече, где владелец и так сомневается, слышат ли
его. Это тот же класс, что и ISS-53, и он **введён этой фазой**: до неё «нет» не оставляло
записи и в `known` не попадало. Для регулярной координации, которую двигают, — сообщение
каждую неделю.

Корень — решение исполнителя «`meetings_evening_block.py` не тронут вообще» (отчёт, п. 1):
`index_watched` используется для трёх разных вопросов сразу («знаем ли встречу», «не сдвинулась
ли наша запись», «не сняли ли нашу запись»), и переиспользование индекса склеило «известна»
с «мы её пишем».
Чинить: в шаге 5 (`:408-431`) не заносить в `new_known` записи, у которых `enabled` ложно и
`ignored` ложно (то есть отказы) — отслеживать перенос/отмену только у того, что реально пишем.

### ⚪ Ф4-16. «Нет» → «да серию» оставляет мёртвую запись рядом с живой
Прогон:
```
после «нет»:  [('oneoff-348bbe75', False, метки есть)]
«да серию» -> [('oneoff-348bbe75', False, метки есть), ('series-4fef10f4', True, метки сняты)]
```
`_clear_rejection_marks` вызывается только для записи с совпавшим id, а у серии id другой.
Мёртвая `oneoff-` запись живёт рядом с живой серией до истечения ретеншна. На поведение не
влияет (планировщик её пропускает, блок и так молчит), но реестр временно содержит две записи
на один экземпляр.

## П.8 Отправка наружу — **в порядке**

Отказная запись инертна: `enabled=false`, `ignored=false`, `notify: []`, без
`telegram_chat_id`; `scheduler.py:109-112` такие пропускает — бот на встречу не придёт,
протокол не соберёт и никому ничего не отправит. Проверено составом записи в прогоне.

Наружу из самого файла уходит ровно один поток — промпт в `claude --print` (пред-существующее).
Диф новых данных в промпт не добавил, только переписал текстовое описание действия `reject`
(`:139-141`). `tg-send` в файле нет.

«Нет» по уже активной записи **гасит** рассылку (`enabled=False`), не включает — направление
безопасное. Ретеншн удаляет только записи с `enabled=false`, поэтому удаление тоже не может
включить рассылку; единственный побочный эффект — встреча снова станет «неизвестной», но к
этому моменту (30+ дней после старта) её экземпляра в 7-дневном горизонте уже нет.

## П.9 Как узнаем, что это сломали — **починить**

Что есть: `pruned_rejections` в JSON-ответе и в итоговой строке лога (`:707-712`);
`logger.info` на каждое удаление с id и датой (`:312`); `warning` на нечитаемую дату (`:293`);
`warning` на мусорный TZ (`:232`). Для операции удаления это разумный минимум.

### 🟡 Ф4-17. Расхождение TZ между двумя процессами ничем не детектируется
ISS-55 починен тем, что обе половины читают **одну переменную** — но это два разных процесса:
вечерний блок ходит по расписанию (systemd-юнит `meeting-notary-evening-digest`, см. шапку
`meetings_evening_block.py:233`), а apply-reply — subprocess слушателя и наследует **его**
окружение. `MEETING_NOTARY_DISPLAY_TZ` не упоминается ни в `.env.notary.example`, ни в одном
конфиге репозитория (grep: только код и тесты). Разъедутся окружения двух юнитов — час разницы
вернётся, и ничто этого не поймает: `test_question_and_confirmation_agree_in_any_tz`
(`test_iss53_55…:413`) ставит переменную один раз на оба модуля в одном процессе, то есть
проверяет согласованность кода, а не согласованность развёртки.
Чинить: вечерний блок пишет применённую зону в snapshot (`shown_tz` рядом с `shown_date`,
`:503`), apply-reply сверяет со своей и при расхождении форматирует по зоне из snapshot
+ warning. Тогда правда о времени едет вместе с вопросом, а не через окружение.

### ⚪ Ф4-18. Факт «отказ записан» владелец проверить не может
`meeting-watch list` по умолчанию прячет `enabled=false` (`meeting_watch.py:94`), в сводке
удаление не отражается. Единственный способ убедиться — читать YAML руками. Для операции,
которая молча удаляет данные, это тонковато.
