## Вопрос 1. Какую проблему закрывает и закрывает ли — путь пользователя целиком

**Проблема из плана:** Т10 (критерий 10) — «в групповом чате серии просьба прислать файл срабатывает
без ответа-реплая на протокол; формулировка глагола роли не играет». Плюс фундамент Т4/Т5 (поле режима
в реестре) под фазы 2–3. Вторую половину Т10 (формулировка) план сам отдаёт в Ф6 — фаза 1 отвечает
только за «без реплая».

### Путь по звеньям, как он есть в коде

| # | Звено | Адрес | Что происходит |

**Порядок роутов сломать нельзя** — все роуты выше требуют реплая, кроме set_chat, у которого узкий
парсер и owner-гейт. Ниже стоящие роуты (digest_reply `:2894`, status `:1749-1751`, шлюз правок) тоже
требуют реплая, а не-реплай в группе раньше просто умирал на DM-гейте `:2933`. То есть роут ничего
чужого не отбирает — он подбирает то, что раньше падало в тишину. Это чисто.

**Задокументированный случай ISS-52 фаза закрывает.** В журнале (`plans/notary-issues-log.md:42`)
человек ответил реплаем на реплику бота «не понял» — тогда `is_reply=True`, оба reply-резолвера дают
None, и раньше выдавалась подсказка «ответьте на дайджест». Теперь `:1052` подхватывает серию по чату
и файл уходит. Проверено новым тестом `test_reply_without_context_still_hints` (обратная сторона) и
`test_group_single_series_works_without_reply`.

### Где путь рвётся

**Р1 🔴 — звено 2 не проверено, и unit-тестами его проверить нельзя.** Чтобы бот вообще увидел
сообщение БЕЗ реплая и БЕЗ упоминания в группе, у бота должен быть выключен режим приватности
(BotFather `/setprivacy` → Disable) либо он должен быть админом группы. В репозитории нет ни слова про
это (grep по `privacy` — только про «приватность данных»). Все три случая из журнала (ISS-51 и ISS-52,
28.07) — это **реплаи** на сообщения бота, которые доходят и при включённой приватности. Единственная
существующая фича, которая полагалась бы на обычное не-реплай сообщение в группе (команда «серию X шли
сюда»), до сих пор висит непроверенной: `plans/follow-ups-delivery-fixes-protocol.md:39` — «⏳ боевой
смоук маршрутизации … боевое поведение на живой групповой доставке НЕ закрывается синтетикой».
Итого: если приватность включена, вся ветка «без реплая» ложна для **всех** групповых чатов, а тесты
останутся зелёными — они мокают `_chat_context_series` и до Telegram не доходят. Это не правка кода,
это двухминутная проверка владельцем, но без неё Т10 нельзя считать закрытым даже наполовину.

**Р2 🔴 — ветка глохнет навсегда, как только в чате «видно» две серии, включая мёртвые.**
`series_for_chat` (`cli/registry.py:431-473`) перебирает ВСЕ записи `watched.yaml` и не смотрит ни
`enabled`, ни актуальность — в отличие от `scheduler.py:110` (`if not rec.get("enabled", True): continue`).
Реестр же накапливается: сам план в Ф4 признаёт, что «реестр за год превращается в свалку», записи
пересоздаются при смене recurring-события (`meetings_apply_reply.py:367-370` — новый `series` = новый
хэш), а `set_telegram_chat_id_for_series` привязку никогда не снимает. Прогон:

```
A. Мёртвая (enabled: false) запись старой серии + живая серия в одном чате
  series_for_chat -> ['koord-old', 'koord']
  claimed= True  resend_digest= False  resend_protocol= False
  бот ответил: «В этом чате у меня несколько серий: «koord-old», «koord».
                Ответьте на протокол или дайджест нужной встречи…»
```

То есть бот выдаёт ровно тот отказ, из-за которого ISS-52 и завели, только другими словами. Одной
выключенной записи достаточно. Фикс — одна строка фильтра (`if w.get("enabled") is False: continue`),
и Т10 перестаёт зависеть от чистоты реестра.

**Р3 🔴 — на новом пути нет ни одного следа в журнале: «как узнаем» = никак.**
`_chat_context_series` пишет только `logger.debug` (`meetings_listener.py:919, :924`), а листенер
поднят на `level=logging.INFO` (`:129`) — эти строки не попадут в лог НИКОГДА. Ветка «несколько серий»
(`:1074-1082`) и ветка «молчим, чат не привязан» (`:1083-1088`) не логируют вообще ничего. Успешный
резолв по чату в логах не отличим от резолва по реплаю (`_resend_digest` пишет только серию). Прогон:

```
D. реестр недоступен, сообщение без реплая: claimed= False, ответ бота: []   ← и в журнале пусто
```

Следствие: любой из отказов выше (Р1, Р2, сбой реестра) выглядит как «бот молчит», и различить их можно
будет только по жалобе человека. Ф7 плана требует «наблюдение на живых встречах с наблюдаемыми
признаками» — наблюдать нечего. Нужен `logger.info` на успех (серия + сколько кандидатов + чат) и
`logger.warning` на сбой чтения реестра.

**Т10 закрыт частично и это надо сказать вслух.** Дословная фраза владельца из журнала до сих пор не
понимается — проверено:

```
'Вышли актуальный файл с открытыми вопросами' -> None
'вышлите файл с открытыми вопросами'          -> None
'пришлите актуальный файл с открытыми вопросами' -> digest
```

Это по плану (Ф6), фаза не виновата. Но «формулировка глагола роли не играет» — вторая половина Т10 —
пока красная, и в отчёте по фазе Т10 нельзя помечать закрытым.

**Р4 🟡 — «человек увидел файл»: новый источник имени серии может дать уверенно ложный ответ.**
`series_for_chat` возвращает СЫРУЮ строку `series` из реестра, а оба прежних пути брали имя из
`meta.series` / сайдкара дайджеста — то есть из того же места, откуда взялось имя папки на диске
(`runner.py:419`). Если реестр и папка разошлись (ровно корень ISS-7, который в этом проекте уже
случался), то `_latest_protocol_path` (`:929`) ничего не найдёт, а `collect_items` вернёт пустые
корзины. Прогон:

```
C. реестр говорит 'Koord', папка на диске 'koord'
  collect_items(...) -> {'open': [], 'minor': []}
  бот ответил: «Открытых вопросов по этой встрече сейчас нет — список пуст.»   ← и НИ ОДНОЙ строки в лог
```

Бот уверенно сообщает группе людей, что вопросов нет, хотя они есть. Ветка `reason == "empty"`
(`:1018-1021`) не логирует ничего. Минимум — прогонять имя через `resolve_series_ref` (как это делает
команда смены чата, `:1210`) или логировать «пусто» на INFO.

## Вопрос 2. Что написано ради того, чтобы было написано

Мерка: каждое изменение должно прямо служить Т4/Т10 или явному пункту Ф1 плана. И честная поправка на
масштаб — в реестре десятки записей, сообщений в чатах единицы, поэтому «дорого/медленно» тут почти
никогда не аргумент.

**Р5 🟡 — кортеж `_chat_context_series` наполовину мёртв, а докстринг обещает то, чего нет.**
Функция возвращает `(серии, причина_сбоя)` (`:896`), докстринг говорит: «реестр не прочитался — тогда
вторым элементом едет причина, и вызыватель показывает прежнюю подсказку, а не молчит». Единственный
вызыватель: `chat_series, _err = _chat_context_series(cid, allowed_chat)` (`:1053`) — `_err` не читается
ни разу, и поведение при `err="OSError"` и при `err=None` побайтово одинаково (обе дороги ведут в
`chat_series == []`). Проверено прогоном D: реестр упал → бот молчит, никакой «прежней подсказки» нет.
Тест `test_registry_failure_is_soft` (`test_iss51_mode_registry.py:375`) проверяет значение, которое ни
на что не влияет — сторож без охраняемого объекта. Решение — любое из двух, но не текущее: либо
вернуть просто `list[str]` и убрать три строки, либо действительно развести случай (там, кстати, и
просится `logger.warning` из Р3).

**Р6 🟡 — новое поле не попало в шапку реестра.** `WATCHED_HEADER` (`cli/registry.py:169-190`)
переписывается при КАЖДОМ `save_watched` и является единственной документацией полей для владельца:
`company`, `visibility`, `genre` там расписаны абзацами. `open_questions_mode` не добавлен. Владелец —
не программист, и до Ф2 (команда боту) единственный способ выставить режим — руками в YAML, где
подсказки теперь нет. Это не перфекционизм: в этом файле сложился явный паттерн, и все три предыдущих
опциональных поля ему следовали.

**Р7 🟡 — старый сторож теперь охраняет пустоту.** `tests/test_send_artifact.py:155-161`,
`test_not_a_reply_returns_false` — «не reply → нет контекста серии → False». Фаза 1 этот контракт
СОЗНАТЕЛЬНО поменяла, но тест остался зелёным, потому что в нём `cid == allowed_chat == 555`, и
`_chat_context_series` выходит по ветке «это личка владельца» (`:913`). Проверено прогоном E. То есть
старый файл в этой точке больше ничего не проверяет, а комментарий в нём стал неверным и будет вводить
в заблуждение следующего. Настоящее покрытие есть только в новом файле
(`test_unbound_group_stays_silent`). Надо либо перенацелить старый тест («не reply + чат не привязан →
False»), либо честно удалить его как переехавший.

**Что я НЕ считаю лишним** (проверил и снимаю подозрение):
- Схлопывание по уникальным сериям в `series_for_chat` — не украшательство: одна серия реально = много
  записей (`set_telegram_chat_id_for_series` `:631` проставляет привязку ВСЕМ записям серии), без
  схлопывания переспрос вылезал бы на каждую просьбу.
- Двухуровневый резолв exact/fuzzy в `series_open_questions_mode` (`:475-531`) — план требует «тот же
  резолв, что у `get_telegram_chat_id_for_series`» дословно, симметрия с `:388` соблюдена.
- `series_open_questions_mode` пока не зовётся из боевого кода (потребитель — Ф3). Это прямой пункт
  Ф1 плана, а не задел «на будущее».
- Ветка «несколько серий» (`:1074`) — реестр действительно допускает две серии на один чат, и цена
  ветки ~8 строк против отправки чужого протокола в чат. Оставить, но см. Р2 (фильтр мёртвых).

**Р8 ⚪ — реестр читается с диска на КАЖДОЕ текстовое сообщение в любой группе, до детекта.**
`_chat_context_series` вызывается на `:1052`, а `detect_artifact_request` — только на `:1060`. Прогон B:
4 обычных сообщения («привет», «спасибо», …) → 4 чтения и разбора YAML. **Честно: на объёмах проекта
это не проблема производительности** — файл маленький, сообщений мало. Но вызов стоит не на своём
месте: он расширяет площадь отказа реестра на весь групповой трафик и зашумит будущий INFO-лог из Р3.
Перенос на 8 строк ниже (после `kind` и гейта статусов) бесплатен.

**Р9 ⚪ — мёртвая проверка типа.** `cli/registry.py:515`: `if isinstance(raw, str) and not isinstance(raw, bool)`
— `bool` не подкласс `str`, вторая половина условия не может быть ложной. В `validate_watched_record`
(`:358-364`) аналогичный комментарий про bool уместен (там рядом int), здесь — карго.

**Р10 ⚪ — переспрос советует ровно то, из-за чего завели ISS-52.** Текст на `:1077-1081` — «Ответьте
на протокол или дайджест нужной встречи». Человек в чате с двумя сериями получает ту же просьбу
приложить реплай, от которой уходили. Продуктово правильнее было бы «уточните: «протокол координации»»,
но это уже язык Ф2/Ф6 — фиксирую, чтобы не потерялось.

## Вопрос 3. Уехало бы на прод сегодня — что ляжет первым и как узнаем

**Первым ляжет не объём, а состояние реестра.** Порог — ДВЕ записи с одинаковым `telegram_chat_id`
(Р2), считая выключенные и осиротевшие после пересоздания серии. Не сто записей, не тысяча — две.
После этого чат навсегда уходит в переспрос, а сама фича перестаёт работать молча. Узнаем — только
жалобой человека («он опять просит ответить на протокол»), потому что ветка не логирует ничего (Р3).
Вторым — Р4 (дрейф ключа → уверенное «открытых вопросов нет»), тоже без единой строки в журнале.
Третьим — Р1, но он либо работает с первого дня, либо не работает никогда.

**Чем узнаем — сводка (это и есть главная дыра фазы):**

| Отказ | Сигнал сегодня | Должен быть |
|---|---|---|
| реестр не прочитался | `logger.debug` при `level=INFO` → **ничего** | `warning` + метрика в лог |
| в чате несколько серий | **ничего** (только текст человеку) | `info` с именами серий |
| серия резолвнута по чату (успех) | **ничего** | `info`: серия, чат, способ резолва |
| «список пуст» из-за дрейфа ключа | **ничего** | `info` о пустом результате |
| «протокол ещё не готов» | **ничего** | `info` |
| протокол/дайджест реально ушёл | `info` ✅ (`:986`, `:1007`) | ок |

**Регрессии — кто ещё зависит от изменённого.**
- `maybe_route_to_send_artifact` зовётся ровно из одного места — `process_message:2886`. Других
  потребителей нет (grep). Сигнатура не менялась.
- Порядок роутов не тронут, и новая ветка не крадёт чужое: все соседи требуют реплая (`:2190`,
  `:1749`, digest-роут через `_reply_context_series_digest`). Раньше не-реплай в группе умирал на
  DM-гейте `:2933` — теперь его подбирает артефакт-роут. Единственные, кто «теряет» такие сообщения, —
  никто.
- Гейт `detect_status_intent` (`:1067-1072`) остался на месте и стоит ПОСЛЕ детекта, но ДО отправки —
  новый тест `test_status_reply_still_not_stolen_without_reply` его закрывает. Риск 4 плана не задет.
- Старые тесты `test_send_artifact.py` зелёные (38/38), но один из них перестал что-либо значить — Р7.

**Р11 🟡 — побочка, охват которой эта фаза расширила: перезапись якоря дайджеста.**
`_resend_digest` зовёт `send_series_digest(force=True)`, а тот в `record_sent`
(`lib/morning_digest.py:401-405`) кладёт `sent[date] = {...}` — ОДНА запись на дату, перезаписью.
Раньше это мог вызвать только человек с реплаем; теперь — любой участник любой привязанной группы одной
фразой без реплая. Последствия два: (а) плановый утренний дайджест за тот же день будет пропущен
(`already_sent` `:387`, `run()` зовёт без `force`) — то есть шпаргалка к встрече не придёт в свой срок;
(б) ответы-статусы на ПРЕДЫДУЩЕЕ сообщение дайджеста того же дня перестают резолвиться
(`digest_series_for_message` `:423` ищет по паре chat_id+message_id), `maybe_route_to_digest_reply`
вернёт False, и ответ уедет в шлюз правок. Наследство ISS-45, но частота срабатывания выросла именно
этой фазой, поэтому чинить/ограничивать надо здесь.

**Нулевые данные / сотня записей / одновременные сообщения — проверено:**
- Нулевые: `series_for_chat` и `series_open_questions_mode` устойчивы к `None`, `{}`, `{"watched": None}`,
  мусору в списке, к `bool` вместо `chat_id` — покрыто тестами (`test_broken_watched_*`,
  `test_bool_binding_ignored`), прогнал, зелено.
- Сотня записей: обе функции — линейный проход по списку, единицы миллисекунд; чтение YAML на каждое
  сообщение (Р8) на этих объёмах не проблема. Опасен не объём, а качество записей (Р2).
- Одновременные сообщения: листенер обрабатывает сообщения последовательно (`ThreadPoolExecutor` в
  `:3059` заведён только под перевыпуск, `max_workers=1`), гонки за файл состояния нет; но два запроса

## Вердикт

**Фазу принимать нельзя без Р2 и Р3, и нельзя объявлять Т10 закрытым без Р1.**

Написанный код по существу верный и аккуратный: порядок роутов не сломан, чужие сообщения не отобраны,
гейт статусов на месте, старый reply-путь не тронут, тесты честные и зелёные. Но фаза сдаётся с
дефектом ровно того класса, ради которого её делали: в реальном реестре — с выключенными и
осиротевшими записями — новая ветка молча возвращается к тому же отказу, из-за которого завели ISS-52
(Р2), и ни один из отказов не оставляет следа, по которому это можно заметить раньше жалобы человека
(Р3). Обе правки маленькие: одна строка фильтра и три-четыре строки логов. Р1 — не код, а
двухминутная проверка настройки бота владельцем, но без неё половина Т10 держится на предположении.

Р4–Р7 и Р11 — в этот же заход, если он открыт; Р8–Р10 можно унести в фазу 6, когда этот же роут будет
переписываться под ИИ-детект.
