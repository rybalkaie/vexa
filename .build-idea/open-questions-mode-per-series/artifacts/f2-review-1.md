## Находки

### 🔴-1. Список ВСЕХ серий реестра печатается в групповой чат

`meetings_listener.py:1639-1655` + вызовы на 1567 и 1591.
`_oq_mode_unknown_series(..., list_known=is_owner)` спрашивает «это владелец?», но
не спрашивает «а где он это набрал?». Ответ уходит в `cid` — то есть в тот чат,
где дана команда. Владелец, набравший команду **в любой группе** с
нерезолвящейся ссылкой на серию, вываливает туда полный список внутренних имён
всех своих серий.

Прогон (реестр из 4 серий):

```
владелец, чат = группа Директората: "слушай, в каком режиме эта серия"
 → 🤔 Не нашёл серию «слушай» в реестре. Известные серии: 1-na-1-ivan-petrov,
   anzhee-direktorat, koordinaciya, sovet-direktorov-mpfirst. Уточни slug или имя.

владелец, чат = ПОСТОРОННЯЯ группа: "какой режим у серии — гибридный"
 → тот же полный список в чат, который к этим сериям отношения не имеет

владелец, чат = группа: "так, эта серия теперь шпаргалка пожалуйста"
 → тот же полный список; команда при этом НЕ СРАБОТАЛА
```

Почему это не редкий случай. Корень — жадный `_extract_series_ref`
(`mode_command.py:192`): он вычитает служебные слова, а всё, что осталось, объявляет
именем серии. Любое вводное слово даёт мусорный `series_ref`, который **отменяет**
резолв по контексту чата и уводит прямо в ветку «не нашёл»:

| фраза | `series_ref` |
|---|---|
| `слушай, в каком режиме эта серия` | `слушай` |
| `так, эта серия теперь шпаргалка пожалуйста` | `так` |
| `а в каком режиме эта серия работает` | `работает` |
| `какой режим у серии — гибридный` | `гибридный` |

Владелец диктует через Wispr Flow (CLAUDE.md прямо предупреждает про вводные слова
и кривую пунктуацию) — то есть это не край, а типовой ввод.

Что именно утекает: `1-na-1-ivan-petrov` (личная встреча с названным человеком),
`sovet-direktorov-mpfirst` (другая компания) — участникам группы Anzhee. Ровно тот
класс, который исполнитель закрывал для лички.

Дырой в тестах это не поймано: `test_known_series_list_is_owner_only` дёргает
хелпер в изоляции (`list_known=True/False`), а `test_unknown_series_lists_known_ones`
гоняет роут только с `chat=OWNER` (личка). Групповой случай не покрыт.

Плюс два последствия сверх утечки: (а) команда владельца молча не срабатывает от
вводного слова — это ломает критерий 5 плана; (б) у участника та же фраза даёт
непустой `series_ref` → гейт молча её отбрасывает.

**Починка:** `list_known = is_owner and cid == allowed_chat` (список — только в
личку), и отдельно — не пускать в `series_ref` то, что не похоже на ссылку на
серию (либо при нерезолвящемся мусорном `ref` откатываться на контекст чата вместо
ветки «не нашёл»). Соседний `maybe_route_to_set_chat_command` (строки 1296-1307)
страдает тем же — там списка вообще ничем не прикрыто; это долг вне Ф2, но
чинить их стоит одним движением.

### 🔴-2. QUERY-путь валится необработанным `AttributeError` на битой записи реестра

Прогон:

```
watched = {"watched": ["строка-вместо-записи", {...}]}
QUERY  → ИСКЛЮЧЕНИЕ AttributeError: 'str' object has no attribute 'get'
         ответов человеку: 0 (молчание)
SET    → корректно: "⚠️ Не смог сохранить режим серии", лок отпущен
```

Причина: `registry.resolve_series_ref` (`registry.py:594-598`) обходит записи без
`isinstance(w, dict)`. В SET-ветке этот вызов стоит внутри `try/except Exception` →
человек получает ответ. В query-ветке после `load_watched()` кода под защитой нет —
исключение улетает из роута.

Последствия: (1) человек не получает НИЧЕГО — нарушен R-REPLY, ровно то, ради чего
писались «видимые реакции»; (2) `process_message` обрывается, и все роуты ниже это
сообщение не увидят; (3) достижимо **любым участником группы** — query owner-гейта
не имеет. Процесс при этом выживает (`except Exception` в главном цикле, `save_offset`
отрабатывает) — петли рестартов, как в Ф1, нет.

Сценарий не гипотетический: `_read_yaml` проверяет только словарь верхнего уровня,
элементы списка не валидирует, а «реестр правят руками» — заявленная в этой же
фазе модель. Что исполнитель этот класс ввода знает, видно по новому сеттеру: там
`isinstance(w, dict)` стоит. Защитили новую функцию, не защитили путь.

**Починка:** обернуть query-ветку тем же `try/except Exception` с ответом человеку
(симметрично SET), либо добавить `isinstance(w, dict)` в `resolve_series_ref`.

### 🟡-1. Занятый лок вешает весь слушатель, а сообщение обещает отказ

`registry._acquire_lock` → `fcntl.flock(fd, LOCK_EX)` без таймаута. Прогон с
настоящим конкурирующим процессом, державшим лок 8 с:

```
через 4.0 с роут ВСЁ ЕЩЁ ЗАБЛОКИРОВАН на flock — ответов человеку 0
вернулся только через 8.03 с, когда чужой процесс отпустил
```

Пока роут стоит, слушатель однопоточный: `getUpdates` не крутится, heartbeat не
идёт, остальные сообщения не обрабатываются. При этом текст
«⚠️ Реестр серий занят — режим не поменял» на занятый лок **не выдаётся никогда** —
он выдаётся на битый YAML (прогоны C/D). Формулировка обещает поведение, которого
нет. Унаследовано от `set_chat`, но Ф2 добавляет вторую и более частую дверь.

### ⚪-1. Query-роут без дедупа и лимита

Любой участник группы может дёргать «в каком режиме эта серия» сколько угодно:
каждый раз чтение `watched.yaml` с диска + исходящее сообщение в группу. У соседних
команд дедуп есть (`_protocol_command_is_dupe`, окно 30 с). Спам, не дыра.

### ⚪-2. Бот учит участника команде, которой тот не может воспользоваться

`_OQ_MODE_STATE` заканчивается «Переключить: «эта серия — шпаргалка»» — участник
попробует, гейт молча проигнорирует, участник решит, что бот сломан.

### ⚪-3. Управляющие символы и RTL-override проходят в `series_ref`

`"эта серия\x00\x07 — шпаргалка"` → `series_ref='\x00\x07'`;
`"эта ‮серия‬ — шпаргалка"` → `series_ref='‮ ‬'`. Дальше отражаются в
ответ. Кода не исполняют; максимум — кривое отображение собственного сообщения
бота. Побочно усиливают 🔴-1: невидимый символ отменяет резолв по контексту чата.

### ⚪-4. `is_dm = cid == allowed_chat` предполагает, что это личка

Если `TELEGRAM_NOTARIUS_CHAT_ID` когда-нибудь укажет на группу, все её участники
станут «владельцем» и получат и переключение, и список серий. Унаследовано от
`set_chat`; дешёвая страховка — проверить `allowed_chat > 0` при старте.
