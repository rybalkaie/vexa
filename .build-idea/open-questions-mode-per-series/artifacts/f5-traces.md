### `event_ical_uid` — 14 входов, ни одного падения

```
  событие без поля iCalUID                  → None
  iCalUID = '' / '   ' / None               → None
  iCalUID = 12345 / ['a'] / True            → None
  iCalUID = 100 000 символов                → 'xxxxxxxxxxxxxxxxxxxx…(100000)'   ← пропускает как есть
  iCalUID с пробелами по краям              → 'uid@g'
  iCalUID в другом регистре ('UID@G')       → 'UID@G'                            ← регистр значим
  event = None / 'строка' / [] / 42         → None
```

Длину никто не ограничивает, и `validate_watched_record` про `ical_uid` не знает вовсе —
стокилобайтная строка уедет и в `.queue.json`, и в `watched.yaml`. Практического вектора нет
(поле приходит от Google), помечаю как ⚪.

### элемент очереди — пропуски и мусор

```
  два элемента БЕЗ url, один старт                     → 2 → 2   (не схлопнуто, верно)
  два элемента url='' / url=42                         → 2 → 2
  два элемента БЕЗ start_at / start_at='вчера' / '' / число → 2 → 2 (страховка молчит без времени)
  старт БЕЗ таймзоны (naive) у обоих                   → 2 → 1   (naive трактуется как UTC)
  один naive, второй +00:00                            → 2 → 1   (считаются одним моментом)
  разные офсеты, один момент                           → 2 → 1   ✔
  url отличается ТОЛЬКО слэшем/регистром               → 2 → 1   ✔
  ical_uid = 42 (не строка) у обоих + один url         → 2 → 1   (падает на страховку, верно)
  ical_uid у одного есть, у второго нет, комната одна  → 2 → 1   (вето НЕ включается)
  элемент = None в списке                              → 💥 AttributeError
  элемент = строка в списке                            → 💥 AttributeError
  очередь пустая                                       → 0 → 0
  очередь из одного элемента                           → 1 → 1
```

Мусор в позиции элемента роняет функцию. Сегодня недостижимо (очередь строит только
`_queue_item`), но `dedupe_queue` — публичная функция без защиты входа. ⚪.

### реестр и запись

```
  реестр без ключа 'watched' / watched=None / {} / 'строка' / [None,'мусор',42] → None (не падает)
  данные = None вместо словаря / данные = список → 💥 AttributeError
  запись: ical_uid=42 / event_start_at=42 / 'позавчера' / event_url=42 → 'не найден'
  запись: recurring_event_id='' → 'не найден'   (граница «серия vs разово» держится)
  запись: type='manual' → 'не найден'           ← manual/one-off НИКОГДА не считается близнецом
  запись: всё совпадает → найдена
```

### (б) барьеры ниже по течению — спасут ли, если дедуп промахнётся

Измерено (`sled35.py`, блоки 3б-1…3б-3), не рассуждением:

```
3б-1 без дедупа                       → кандидатов 2 → ботов 2, пропущено []
     если бы series совпадала         → ботов 1, второй: skip_series «уже идёт запись серии»
3б-3 вето (разные iCalUID, одна комната) → в очереди 2 → ботов 2
```

- `_candidates` + `state_acquire` — по `event_id`; у копий он разный → **не спасают**.
- `_concurrency_decision` — по `series`; у копий она разная → **не спасает**. Спасла бы,
  только если бы дедуп присваивал обеим записям общую серию (проверено: тогда 1 бот).
- `MAX_CONCURRENT_BOTS = 2` — два бота ровно влезают в лимит → **не спасает**.
- Наружу владельцу ничего не уходит: `push()` в `dedupe_queue` не вызывается, и схлопывание,
  и предупреждение о столкновении — только `logger` в `~/Library/Logs/meeting-notary/scheduler.log`.

**Дыра, найденная измерением: победитель может смениться между тиками планировщика.**

```
3б-2  тик 1: очередь ['anzhee-vystavka-st1-20260727'] → runner запустил его
      тик 2 (календарь победителя не ответил): очередь ['oneoff-ef50c3ab']
      тик 2 runner: запустил ['oneoff-ef50c3ab'], пропущено: []
      ИТОГО ботов на одну встречу: 2
```

Тот же класс через другой вход — победитель гасит сам себя (`sled35b.py`, 5г):

```
5г  тик 1: очередь [('vystavka-lichno','one-off')] → runner запустил
    auto-disable сработал: [('vystavka-lichno', False), ('oneoff-ef50c3ab', True)]
    тик 2 планировщика: очередь ['oneoff-ef50c3ab'] → runner запустил
    ИТОГО ботов на одну встречу: 2
```

Причина одна: схлопывание живёт только в памяти одного прогона; `event_id` выбывшего
никто не занимает в `.state.json`, и его серия не связана с серией победителя.

Ключ схлопывания в A — `iCalUID` + время старта; в C — URL комнаты + время старта.

бьёт автоимя `oneoff-<8hex>`), а значит протокол уходит в серию `anzhee-vystavka-st1`, где
уже лежат `2026-07-27-memory.json` и привязка чата.

**Оговорка, которую снять нельзя в границах прогона:** какой именно из трёх вариантов был на
бою — A или B — определяется тем, приехали ли копии с одним `iCalUID`. Ни в реестре-зеркале,
ни в журнале задач, ни в протоколах `iCalUID` не зафиксирован (`grep` пуст), а спросить
Google — сеть и боевые данные. План и его ревью утверждают равенство `iCalUID` как факт
(«у одного события в разных календарях он СОВПАДАЕТ»); это верно для копии-приглашения и
неверно для события, продублированного вручную. Вариант A — вероятный (обе копии несут один
Telemost-URL, обе пришли из вечернего скана двух календарей), но не доказанный.

### Время дедупа

```
  боевой объём (20 стартов, половина — дубли)     20 →   10     0.213 мс
  боевой объём (20 стартов, дублей нет)           20 →   20     0.224 мс
  ×5 запаса (100 стартов)                        100 →  100    10.353 мс
  ×25 запаса (500 стартов)                       500 →  500   679.370 мс
  ×50 запаса (1000 стартов)                     1000 → 1000  2576.284 мс
  1000 стартов, половина — дубли                1000 →  500  1202.038 мс

  худший случай — все старты в одну секунду:
    50 стартов  →   3.509 мс     200 стартов →  83.541 мс     500 стартов → 786.402 мс
```

На боевом объёме (5 записей → ~10–20 стартов на 48ч) дедуп стоит **доли миллисекунды**.
Но растёт квадратично: `_instant_key` разбирает ISO-строку заново для каждой пары, поэтому
на 500 стартах это уже 0,7 с, на 1000 — 2,6 с. Планировщик не в горячем пути (launchd раз в
15 мин), запас до боли ~×25.

## ПЯТЫЙ ВОПРОС — кто ещё читает то, что мы схлопываем

Опыт `sled35.py`, блок 5: у владельца есть живая запись `anzhee-vystavka-st1-20260727`
(`telegram_chat_id=-5589869859`, `open_questions_mode=carry`, `company=anzhee`,
`visibility=company`) — заведена руками через CLI, поэтому **примет у неё нет**. Вечером бот
увидел ту же встречу во втором календаре и спросил заново. Владелец: «да».

```
  ДО:  chat_id серии anzhee-vystavka-st1 = -5589869859 | режим = carry

  ПОСЛЕ «да» по копии из второго календаря:
   записей: 2 ['anzhee-vystavka-st1-20260727', 'oneoff-79d00f27']
   строка владельцу: '1. Выставка СТ-1 (05.08 16:00) — записал только этот экземпляр…'
   ISS-54 в логе: НЕТ — дедуп не сработал
   серия 'oneoff-79d00f27':      chat_id=None,        режим=last-only, company=None
   серия 'anzhee-vystavka-st1':  chat_id=-5589869859, режим=carry,     company=anzhee
```

То есть на самой частой боевой конфигурации (запись владельца из CLI) дедуп **при записи в
реестр не срабатывает вовсе**: сверять не с чем, а поставить приметы руками нельзя —
`EDITABLE_FIELDS` их не знает. Спасает только схлопывание очереди: бот будет один.

Если приметы у записи владельца есть, всё работает как задумано:

```
  ЕСЛИ у записи владельца приметы ЕСТЬ:
   записей: 1 ['anzhee-vystavka-st1-20260727'] | привязка чата цела: -5589869859
   строка владельцу: '…это та же встреча, что уже в реестре («anzhee-vystavka-st1-20260727»),
                      просто видна в двух календарях: пишу по ней, второй записи не завожу'
   что дописал _merge_fingerprint: ical_uid=None, event_start_at='…', event_url='…'
   ⚠️ calendar_id/event_id остались от ПЕРВОГО календаря: cal-B / evtB
```

### Чьи ссылки остаются битыми

| Дверь | Ключ | Что видит после схлопывания |
|---|---|---|
| Папка протоколов (`runner.py:419`, `lib/paths.py:181`, `finalize-meeting.py:591`) | `series` победителя | Протокол падает в папку победителя. Если победил не тот — на диске остаётся осиротевшая папка проигравшего с историей (`<date>-memory.json`, статусы задач), в которую больше никто не пишет |
| Привязка чата (`registry.get_telegram_chat_id_for_series`, `llm_postprocess:4137`) | `series` | `_merge_fingerprint` `telegram_chat_id` **не переносит**. Победила запись без привязки → протокол уезжает в личку владельца вместо группы |
| Режим открытых вопросов (`registry.series_open_questions_mode`, поле `open_questions_mode`) | `series` | Тоже не переносится; проигравшая серия молча падает на дефолт `last-only` |
| Разметка `company`/`visibility`/`genre` (`lib/series_markup.py`) | `series` | Не переносится → гейт публикации знания уходит в fail-closed `private` |
| Ростер серии (`lib/series_roster.py`, `context_knowledge.roster_for_series`) | slug реестра | По slug проигравшего больше не резолвится |
| Память серии (`lib/series_memory.py`), `INDEX.md` (`lib/vstrechi_index.py`), обратный поиск в `morning_digest:442` | **имя папки на диске** | Привязаны к папке, а не к реестру: после смены выигравшего slug'а реестр и диск расходятся без единой ошибки в логах |
| Состояние запуска `.state.json` | `event_id` | `event_id` выбывшего **не занимается** → любой прогон, где выживет он, даст второго бота (доказано, 3б-2 и 5г) |
| Снапшот вечернего блока / `index_watched` | `(calendar_id, event_id)` | Копия остаётся «новой»: `find_in_watched(idx,'cal-A','evtA') → None` — блок **снова спросит про ту же встречу завтра** |
| Утренний дайджест (`due_meetings_today`) | `series` + день | До дедупа показывал встречу дважды (проверено), после — один раз ✔ |
| Проигравшая запись реестра | — | Остаётся `enabled: true`: каждые 15 мин отдельный запрос в Google и повторное схлопывание |

Дефект «одна дверь считает встречу живой, другая — удалённой» присутствует и подтверждён
измерением в двух видах: (1) вечерний блок и `index_watched` считают копию неизвестной,
пока `scheduler` уже схлопывает её; (2) `.state.json` считает выбывший `event_id`
незапущенным, пока бот по этой встрече уже пишет.

## Что вскрыто

### 🔴

1. **Вето точного ключа выключает страховку — и в самом важном случае может означать
   «фикс не сработал».** Если у двух копий `iCalUID` известен и различен (событие
   продублировано руками, а не приглашением), `dedupe_queue` не схлопывает **никогда**,
   даже при совпавших комнате и секунде, и `_same_meeting` тоже возвращает `False`. Измерено:
   вариант B на реконструкции боевого дубля → очередь 2 → **ботов 2**. Поскольку Google для
   календарных событий возвращает `iCalUID` практически всегда, страховка «url+время»
   на пути google-calendar почти никогда и не включается. Схлопнётся ли реальный дубль
   27.07 — зависит от того, A это или B, а проверить в границах прогона нельзя.

2. **Победитель схлопывания не закреплён — при смене победителя между тиками приходит второй
   бот.** Схлопывание живёт в памяти одного прогона; `event_id` выбывшего не занимается в
   `.state.json`, серии у копий разные, поэтому ни `state_acquire`, ни `_concurrency_decision`
   не ловят. Два независимых входа измерены: (а) календарь победителя не ответил в следующем
   тике → 2 бота; (б) победитель — `one-off`, `_auto_disable_one_off` гасит его после старта,
   следующий тик отдаёт очередь проигравшему → 2 бота.

3. **Страховочный ключ схлопывает две РАЗНЫЕ встречи владельца, когда `iCalUID` неизвестен
   хотя бы у одной.** На боевом зеркале `@t11` делят **три** записи, и одна из них —
   `2026-05-27-sales-quality` типа `one-off`, у которой календарного события нет, то есть
   `iCalUID` не будет известен никогда. Измерено на реальных записях зеркала: две разные
   встречи в `@t11` в одну секунду → очередь 1, выживает первая по порядку в файле,
   **директорат не записан**, наружу — ничего.

4. **Дедуп при записи в реестр не работает для записей, заведённых владельцем через CLI —
   а это самая частая боевая конфигурация.** У таких записей нет ни `ical_uid`, ни
   `event_start_at`, ни `event_url`, и поставить их нельзя: `cli/meeting_watch.py`
   (`EDITABLE_FIELDS`) этих полей не знает, `validate_watched_record` — тоже. Измерено:
   «да» по копии из второго календаря завело вторую запись рядом с записью владельца
   (`chat_id=None`, `режим=last-only`, `company=None`), строка владельцу — обычное «записал»,
   про дубль ни слова. Двух ботов при этом не будет (снимает очередь), но реестр грязный,
   вечерний блок продолжит спрашивать, а `_merge_fingerprint` `telegram_chat_id` /
   `open_questions_mode` / `company` не переносит.

5. **`dedupe_queue` — единственный барьер во всей системе.** Ни один ключ ниже по течению не
   включает `iCalUID`: `_candidates`/`state_acquire` → `event_id`, `_concurrency_decision` →
   `series`, `index_watched` → `(calendar_id, event_id)`, кэш `meetings-known-instances.json`
   → голый `event_id`, `make_record_id` → `sha1(event_id)`. Измерено: с выключенным дедупом
   два бота стартуют, пропусков ноль.

### 🟡

6. **Схлопывание и предупреждение о столкновении уходят только в лог-файл на маке.**
   `push()` в `dedupe_queue` не вызывается. План требовал «лог о схлопывании — молча гасить
   нельзя»; `~/Library/Logs/meeting-notary/scheduler.log` владелец не открывает, так что
   «две твои разные встречи я схлопнул в одну» и «в комнату придут два бота» для него
   практически молчание. (На пути реестра строка владельцу есть — там всё честно.)

7. **Среди двух записей владельца побеждает та, что раньше в `watched.yaml`, а не та, у
   которой привязка чата.** Измерено: победил `vystavka-st1-lichnyi`, серия для папки и чата
   — его. Привязка/режим/разметка проигравшего не переносятся.

8. **Проигравшую запись никто не гасит.** Она остаётся `enabled: true` навсегда: каждые
   15 минут — отдельный запрос в Google Calendar и повторное схлопывание. Вечерний блок
   продолжает считать копию новой (`find_in_watched → None`) и предложит её снова.

9. **`dedupe_queue` квадратичен с разбором ISO-времени во внутреннем цикле.** 20 стартов —
   0,2 мс, 100 — 10 мс, 500 — 0,68 с, 1000 — 2,6 с. Боевой объём в ~25 раз ниже порога боли,
   но лечится одним проходом предвычисления ключей.

### ⚪

10. `event_ical_uid` не ограничивает длину, `validate_watched_record` про приметы не знает —
    стокилобайтная строка уедет в `.queue.json` и `watched.yaml` как есть. Вектора нет,
    источник — Google.
11. `dedupe_queue` падает `AttributeError` на не-словаре в очереди; `find_duplicate_watched`
    — на `data=None`. Сегодня недостижимо (оба входа строит наш код).
12. `_same_meeting` требует `type == "google-calendar"` — записи `manual`/`one-off` близнецами
    на уровне реестра не считаются никогда; их держит только очередь.
13. `_instant_key` трактует naive-время как UTC — naive и `+00:00` схлопываются как один
    момент. Для этой системы верно (в очереди время всегда с офсетом).
14. `_url_key` приводит весь URL к нижнему регистру. Для Telemost (цифровой id комнаты)
    безопасно; для провайдера с регистрозависимым путём две разные комнаты слились бы.
15. Мусорный `start_at` из снапшота (`'завтра'`) доезжает в `watched.yaml` как `event_start_at`
    без нормализации — дедупу не мешает (`_instant_key` вернёт `None`), но поле в реестре
    нечитаемое.
