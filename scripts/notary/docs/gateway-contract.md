# Контракт шлюза Ватсона (портал → бот), версия 1

Источник истины для клиента на стороне портала. Меняешь ручку — правишь этот файл
тем же коммитом; иначе портал и бот разъезжаются молча.

Реализация — [`../gateway.py`](../gateway.py), реестр нарядов —
[`../lib/orders.py`](../lib/orders.py), пробы — `../tests/test_gateway_ph9_*.py`.

## Общее

* Адрес снаружи: `https://watson.anzhee.ru` (Caddy, авто-TLS). Внутри VPS шлюз слушает
  `127.0.0.1:8789` и наружу не смотрит.
* **Только https.** Клиент портала обязан отказаться отправлять секрет по http —
  Bearer открытым текстом уходит навсегда.
* Авторизация: `Authorization: Bearer <token>`, сравнение в постоянное время.
* Тело: `application/json`, не больше 64 КиБ (`MEETING_NOTARY_GATEWAY_MAX_BODY`).
  Заголовок `Content-Length` обязателен, chunked не принимается.
* Ответ об ошибке всегда одной формы:
  `{"ok": false, "error": "<код>", "message": "<по-русски>", …}`.
  У 422 дополнительно `errors: [{field, code, message}, …]` — **все** ошибки сразу,
  чтобы форма портала показала их человеку за один раз.

### Коды, общие для всех ручек

| Код | Когда |
|---|---|
| 401 | нет заголовка или чужой токен |
| 403 | — (не используется: «чужой токен» это 401) |
| 404 | нет такой ручки / нет такого наряда |
| 405 | верный путь, неверный метод (например POST на `/orders/<id>`) |
| 411 | нет `Content-Length` |
| 413 | тело больше лимита (тело при этом не читается вовсе) |
| 415 | `Content-Type` не `application/json` |
| 422 | тело разобрано, но наряд не прошёл проверку |
| 503 | **секрет на сервере не задан или негоден** (fail-closed), либо реестр нарядов недоступен |

## `GET /health`, `GET /health?deep=1`

Плоский: `{"ok": true, "deep": false, "version": "1"}` — жив процесс, и только.

Глубокий (`?deep=1`) реально проходит путь: реестр нарядов → раскрутка синтетической
записи настоящим планировщиком → очередь и отметка последнего успешного скана.
`200` — всё зелено, `503` — что-то сломано, тело несёт `checks: [{check, ok, detail}]`.
Красным становится и **молчание планировщика** дольше 90 минут
(`MEETING_NOTARY_GATEWAY_SCHEDULER_STALE_MINUTES`).

Сторож портала ходит именно сюда, `*/30`, и алертит по КОДУ ответа.

## `POST /orders` — поставить наряд

```json
{
  "meeting_id": "mtg-1001",
  "company": "anzhee",
  "series_title": "Координация продаж",
  "series": "koordinatsiya-prodazh",
  "room_url": "https://telemost.yandex.ru/j/11111111111111",
  "start_at": "2026-08-20T10:00:00+03:00",
  "duration_minutes": 45,
  "expected_participants": ["Илья Рыбалка"],
  "telegram_chat_id": -1001234567890,
  "owner": {"portal_user_id": "42", "name": "Илья Рыбалка"},
  "keep_audio": false
}
```

Обязательны: `meeting_id`, `company`, `series_title`, `room_url`, `start_at`.
При `ENABLE_PORTAL_ORDERS=1` к ним добавляется **`owner`** (см. ниже).

* **`company` дефолта не имеет.** Наряд без компании отвергается (422): от неё зависит,
  в какой чат уйдёт протокол и какое знание компании подмешается. Допустимо: `anzhee`,
  `mpfirst`.
  🔴 **Портал зовёт МПервый иначе.** Код компании на портале — это `slug` организации,
  и там МПервый заведён как **`m1`** (`prisma/seed-organization.ts:1204`). Шлюз принимает
  `m1` (и `МПервый`) как синоним и **кладёт в реестр канон бота — `mpfirst`**: ниже по
  течению двух слов для одной компании быть не должно. Таблица синонимов —
  `orders.COMPANY_ALIASES`.
* 🔴 **`owner` — ЧЕЙ это наряд (Ф10a, `ENABLE_PORTAL_ORDERS`).** Пока выключатель в **OFF**
  (дефолт) поле необязательно — поведение Ф9 целиком. При **ON** наряд без `owner` или без
  `owner.portal_user_id` отвергается 422 (`owner`/`required`, `owner.portal_user_id`/`required`):
  без него неизвестно, кому слать протокол и чьи правки принимать, а «считать владельцем
  Илью по умолчанию» отдало бы ему чужие встречи.
  * `portal_user_id` — обязателен при ON, строка до 128 знаков.
  * `telegram_user_id` — необязателен, но **без него сотрудник не сможет командовать боту
    в телеграме**: именно по нему бот узнаёт человека и понимает, где его личка.
  * `name` — необязателен, для подписи в протоколе.
* 🔴 **Компания наряда против компании серии (при ON).** Если серия уже размечена в
  `watched.yaml` другой компанией — 422 `company`/`company_mismatch`. Иначе протокол Anzhee
  уехал бы в чат МПервого. Неразмеченная серия конфликтом не считается.
* **`series_title` — человеческое имя серии.** Без него в шапке PDF встанет транслит
  slug'а («Koordinatsiya»).
* `series` (slug папки) можно не слать — выведется из `meeting_id`.
* `start_at` — ISO 8601 **со смещением пояса**. Без пояса 422: время без пояса это
  классический «бот пришёл на три часа раньше».
* `room_url` — только `https` и только платформа, куда бот умеет заходить (сегодня
  Телемост; расширяется `MEETING_NOTARY_GATEWAY_ROOM_HOSTS`).

Ответ `201` (создан) или `200` (такой наряд уже есть / это перенос):

```json
{"ok": true, "created": true, "order": {...},
 "capacity": {"limit": 2, "scope": "all_companies", "busy": 1, "free_slots": 1,
              "known": true, "overlapping_orders": 1,
              "by_source": {"portal_orders": 1}, "by_company": {"anzhee": 1},
              "warning": null}}
```

* **Идемпотентность по `meeting_id`.** Повтор того же тела не заводит второй наряд и не
  двигает `version` — портал имеет право повторить запрос после таймаута сети.
* Тот же `meeting_id` с другим содержимым — это **перенос** той же встречи (версия +1),
  а не вторая встреча.
* 🔴 **`capacity` (Ф10b: считаются ОБА источника занятости).** Раньше сюда попадали только
  наряды портала, и шлюз обещал свободный слот в час, когда у владельца уже стоят две
  личные встречи. Теперь складываются наряды портала **и** очередь планировщика (личные
  серии владельца), одна и та же встреча из обоих источников считается один раз.
  * `limit` — потолок одновременных записей (`MEETING_NOTARY_MAX_CONCURRENT_BOTS`,
    дефолт **2**). Он про ядра машины (2 vCPU, headless-Chrome на каждого бота), поэтому
    **`scope: "all_companies"` — потолок ОБЩИЙ на Anzhee и МПервый**. `by_company` —
    только диагностика «кто занял», решение принимается по общему числу.
  * `warning` ≠ null — «в это время бот занят»: наряд **принят**, но бот придёт, только
    если слот освободится до конца встречи, и тогда **опоздание будет подписано в
    протоколе**. Портал обязан показать это в форме создания и в реестре сразу, а не
    молчать до встречи.
  * `known: false` — посчитать не удалось (нечитаемый источник); наряд всё равно принят.

## `GET /orders`, `GET /orders/<id>`

`GET /orders?status=scheduled,stopping&company=anzhee` — список (`{"orders": [...], "count": N}`).
Неизвестный статус → 400. `GET /orders/<id>` → один наряд или 404.
Идентификатор наряда детерминированный: `portal:<meeting_id>`.

## `PUT /orders/<id>` — изменить

Тело — только меняемые поля (+ необязательный `expected_version`). Всё, что не прислано,
берётся из текущего наряда.

* `expected_version` разошёлся → **409 `version_conflict`** (+ `current_version`): портал
  показывает «встречу изменил кто-то ещё», а не затирает чужую правку.
* Попытка сменить `meeting_id` → **409 `meeting_id_immutable`**: на нём держится
  идемпотентность.
* Правка **снятого** наряда возвращает его в строй (на портале «отменил и перенёс» —
  обычный сценарий).
* Правка встречи, которая уже прошла, разрешена, пока не трогается `start_at`.

## `DELETE /orders/<id>` — снять

`200` + наряд со статусом `cancelled`. Снятие несуществующего → `404`.

## `POST /orders/join-now` — «зайти сейчас»

Тело как у `/orders`, но `start_at` не нужен (проставляется «сейчас»).

* Второе нажатие по **той же комнате** — тем же или другим человеком — возвращает
  `200`, `created: false`, `already_running: true` и **тот же** наряд. Второго бота не
  поднимаем (R12.6).
* Комната сравнивается по хосту и пути; `?utm=…` и `#якорь` отбрасываются.
* Забытый разовый наряд перестаёт держать комнату через 180 минут.

## `POST /orders/leave-now` — «выйти сейчас»

`{"meeting_id": "mtg-1001"}` либо `{"room_url": "https://…"}`. Наряд получает статус
`stopping` и отметку `stop_requested_at`; штатное завершение записи (чтобы файл ушёл в
обработку, а не потерялся) делает исполняющий слой. Ни того, ни другого нет → `400`;
живого наряда по встрече/комнате нет → `404`. Повтор безвреден.

## `GET /protocol?meeting_id=…&format=md|pdf`

`200` + `text/markdown` (или `application/pdf`). Протокол ещё не собран → `404`
`protocol_not_ready`. Неизвестный формат → `400`.

## `GET /status` — привязки и активность

Для экранов Ф12/Ф13a: какие серии привязаны к чатам, живы ли они, сколько нарядов
активно по компаниям, размер очереди, свежесть последнего скана планировщика.

🔴 **`telegram_chat_id` наружу не отдаётся** — только факт `telegram_chat_bound: true|false`.
Порталу нужен факт привязки, а не адрес приватного чата.

`activity.portal_orders_enabled` — положение аварийного выключателя `ENABLE_PORTAL_ORDERS`.
Без него «наряды не исполняются» и «фича выключена» с портала выглядят одинаково, и
разбираться пришлось бы по логам на VPS.

## Что происходит с нарядом дальше (Ф10b, исполнение)

Шлюз по-прежнему не запускает ботов и не пишет очередь: он кладёт наряд в реестр.
Исполняет его **планировщик**, и портал вправе на это рассчитывать так:

* Наряд со статусом `scheduled` попадает в очередь стартов **наравне с личными сериями
  владельца** — отдельной очереди у портала нет (две правды = два бота в комнате).
  Одна и та же встреча, приехавшая и нарядом, и личной серией (одна комната, одна
  секунда), схлопывается в ОДИН старт; связь с нарядом при этом сохраняется.
* Ключ идемпотентности — **детерминированный `id` записи реестра** (`portal:<meeting_id>`)
  плюс минута старта. Повтор наряда второго бота не даёт; **перенос даёт новый ключ и,
  значит, повторный запуск в новое время** — включая случай, когда бот уже сидит в
  комнате по старому времени (ISS-57).
* `DELETE` (или статус `cancelled`) снимает приход: наряда нет в очереди — бот не идёт.
  Статус `stopping` («выйти сейчас») нового старта тоже не получает.
* **Переполнение потолка не теряет встречу.** Старт, который не смог начаться (лимит или
  живой бот той же серии), ждёт свободного слота **до конца встречи**. Освободился — бот
  заходит с опозданием, и в конце протокола появляется строка «бот подключился с
  опозданием на N мин». Не освободился — владельцу уходит «не записал» с причиной.
* `POST /orders/join-now` исполняется **минутами, а не тиком планировщика**: разовые
  наряды runner читает из реестра напрямую. Годен к запуску 20 минут после нажатия.

Чего исполнение НЕ делает (осознанно, отдельным нарядом): не гасит УЖЕ ЗАПУЩЕННОГО бота
при отмене и не выполняет `stopping` физически — `docker stop` приходит к боту SIGKILL'ом,
и незакрытая `meta.json` стоила бы записи целой встречи. Пока это значит: отмена за минуту
до старта приход снимает, отмена ПОСЛЕ захода бота — уже нет.
