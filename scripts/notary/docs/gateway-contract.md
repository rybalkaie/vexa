# Контракт шлюза Ватсона (портал → бот), версия 1

Источник истины для клиента на стороне портала. Меняешь ручку — правишь этот файл
тем же коммитом; иначе портал и бот разъезжаются молча.

Реализация — [`../gateway.py`](../gateway.py), реестр нарядов —
[`../lib/orders.py`](../lib/orders.py), пробы — `../tests/test_gateway_ph9_*.py`.

## Общее

* Адрес снаружи: `https://watson.46-224-163-202.sslip.io` (Caddy, авто-TLS). Внутри VPS шлюз слушает
  `127.0.0.1:8789` и наружу не смотрит.
* **Только https.** Клиент портала обязан отказаться отправлять секрет по http —
  Bearer открытым текстом уходит навсегда.
* Авторизация: `Authorization: Bearer <token>`, сравнение в постоянное время.
* Тело: `application/json`, не больше 64 КиБ (`MEETING_NOTARY_GATEWAY_MAX_BODY`).
  Заголовок `Content-Length` обязателен, chunked не принимается.
* Ответ об ошибке всегда одной формы:
  `{"ok": false, "error": "<код>", "message": "<по-русски>", …}`.
  У 422 дополнительно `errors: [{field, code, message}, …]` — **все** ошибки сразу,
  чтобы форма портала показала их человеку за один раз.

### Коды, общие для всех ручек

| Код | Когда |
|---|---|
| 401 | нет заголовка или чужой токен |
| 403 | — (не используется: «чужой токен» это 401) |
| 404 | нет такой ручки / нет такого наряда |
| 405 | верный путь, неверный метод (например POST на `/orders/<id>`) |
| 411 | нет `Content-Length` |
| 413 | тело больше лимита (тело при этом не читается вовсе) |
| 415 | `Content-Type` не `application/json` |
| 422 | тело разобрано, но наряд не прошёл проверку |
| 503 | **секрет на сервере не задан или негоден** (fail-closed), либо реестр нарядов недоступен |

## `GET /health`, `GET /health?deep=1`

Плоский: `{"ok": true, "deep": false, "version": "1"}` — жив процесс, и только.

Глубокий (`?deep=1`) реально проходит путь: реестр нарядов → раскрутка синтетической
записи настоящим планировщиком → очередь и отметка последнего успешного скана.
`200` — всё зелено, `503` — что-то сломано, тело несёт `checks: [{check, ok, detail}]`.
Красным становится и **молчание планировщика** дольше 90 минут
(`MEETING_NOTARY_GATEWAY_SCHEDULER_STALE_MINUTES`).

Сторож портала ходит именно сюда, `*/30`, и алертит по КОДУ ответа.

## `POST /orders` — поставить наряд

```json
{
  "meeting_id": "mtg-1001",
  "company": "anzhee",
  "series_title": "Координация продаж",
  "series": "koordinatsiya-prodazh",
  "room_url": "https://telemost.yandex.ru/j/11111111111111",
  "start_at": "2026-08-20T10:00:00+03:00",
  "duration_minutes": 45,
  "expected_participants": ["Илья Рыбалка"],
  "telegram_chat_id": -1001234567890,
  "delivery": "group",
  "owner": {"portal_user_id": "42", "name": "Илья Рыбалка"},
  "keep_audio": false
}
```

Обязательны: `meeting_id`, `company`, `series_title`, `room_url`, `start_at`.
При `ENABLE_PORTAL_ORDERS=1` к ним добавляется **`owner`** (см. ниже).

* **`company` дефолта не имеет.** Наряд без компании отвергается (422): от неё зависит,
  в какой чат уйдёт протокол и какое знание компании подмешается. Допустимо: `anzhee`,
  `mpfirst`.
  🔴 **Портал зовёт МПервый иначе.** Код компании на портале — это `slug` организации,
  и там МПервый заведён как **`m1`** (`prisma/seed-organization.ts:1204`). Шлюз принимает
  `m1` (и `МПервый`) как синоним и **кладёт в реестр канон бота — `mpfirst`**: ниже по
  течению двух слов для одной компании быть не должно. Таблица синонимов —
  `orders.COMPANY_ALIASES`.
* 🔴 **`owner` — ЧЕЙ это наряд (Ф10a, `ENABLE_PORTAL_ORDERS`).** Пока выключатель в **OFF**
  (дефолт) поле необязательно — поведение Ф9 целиком. При **ON** наряд без `owner` или без
  `owner.portal_user_id` отвергается 422 (`owner`/`required`, `owner.portal_user_id`/`required`):
  без него неизвестно, кому слать протокол и чьи правки принимать, а «считать владельцем
  Илью по умолчанию» отдало бы ему чужие встречи.
  * `portal_user_id` — обязателен при ON, строка до 128 знаков.
  * `telegram_user_id` — необязателен, но **без него сотрудник не сможет командовать боту
    в телеграме**: именно по нему бот узнаёт человека и понимает, где его личка.
  * `name` — необязателен, для подписи в протоколе.
* 🔴 **`delivery` — КОМУ уходит протокол (Ф10d, R7.10).** Необязательное; допустимо
  `dm` (личка сотрудника-владельца наряда), `group` (групповой чат: `telegram_chat_id`
  наряда, иначе привязка серии в `watched.yaml`), `portal_only` (в Telegram не уходит
  ничего). Мусор в поле → 422 `delivery`/`unknown`: «в личку» и «в группу» отличаются
  кругом читателей, и угадывать нечего. Не прислали — бот выбирает сам: группа, если
  чат привязан, иначе личка владельца наряда, иначе только портал.
  * 🔴 **Фолбэка в личку ВЛАДЕЛЬЦА ПОРТАЛА для наряда НЕТ.** Не вывели адресата —
    результат уходит только на портал. Личные серии владельца этим не задеты: у них
    наряда нет, и `TELEGRAM_NOTARIUS_CHAT_ID` работает как работал.
  * `dm` без привязанного телеграма сотрудника и `group` без чата **не отбиваются**:
    привязка появляется на экране «Ватсон» уже ПОСЛЕ постановки наряда, и отказ
    означал бы «встречу не записать, пока не подключишь телеграм». Такой наряд
    принимается и на доставке честно деградирует в «только портал» — это видно в
    `telegram_delivery.mode`/`reason` результата.
  * **Уточнения по спикерам** («кто говорил во фрагменте…») к `delivery` не относятся:
    они несут кусок расшифровки и уходят ТОЛЬКО в личку владельца наряда, никогда в
    группу — даже когда протокол уходит в группу (R13.2). Лички нет → уточнение не
    задаётся вовсе.
* 🔴 **Компания наряда против компании серии (при ON).** Если серия уже размечена в
  `watched.yaml` другой компанией — 422 `company`/`company_mismatch`. Иначе протокол Anzhee
  уехал бы в чат МПервого. Неразмеченная серия конфликтом не считается.
* **`series_title` — человеческое имя серии.** Без него в шапке PDF встанет транслит
  slug'а («Koordinatsiya»).
* `series` (slug папки) можно не слать — выведется из `meeting_id`.
* `start_at` — ISO 8601 **со смещением пояса**. Без пояса 422: время без пояса это
  классический «бот пришёл на три часа раньше».
* `room_url` — только `https` и только платформа, куда бот умеет заходить (сегодня
  Телемост; расширяется `MEETING_NOTARY_GATEWAY_ROOM_HOSTS`).

Ответ `201` (создан) или `200` (такой наряд уже есть / это перенос):

```json
{"ok": true, "created": true, "order": {...},
 "capacity": {"limit": 2, "scope": "all_companies", "busy": 1, "free_slots": 1,
              "known": true, "overlapping_orders": 1,
              "by_source": {"portal_orders": 1}, "by_company": {"anzhee": 1},
              "warning": null}}
```

* **Идемпотентность по `meeting_id`.** Повтор того же тела не заводит второй наряд и не
  двигает `version` — портал имеет право повторить запрос после таймаута сети.
* Тот же `meeting_id` с другим содержимым — это **перенос** той же встречи (версия +1),
  а не вторая встреча.
* 🔴 **`capacity` (Ф10b: считаются ОБА источника занятости).** Раньше сюда попадали только
  наряды портала, и шлюз обещал свободный слот в час, когда у владельца уже стоят две
  личные встречи. Теперь складываются наряды портала **и** очередь планировщика (личные
  серии владельца), одна и та же встреча из обоих источников считается один раз.
  * `limit` — потолок одновременных записей (`MEETING_NOTARY_MAX_CONCURRENT_BOTS`,
    дефолт **2**). Он про ядра машины (2 vCPU, headless-Chrome на каждого бота), поэтому
    **`scope: "all_companies"` — потолок ОБЩИЙ на Anzhee и МПервый**. `by_company` —
    только диагностика «кто занял», решение принимается по общему числу.
  * `warning` ≠ null — «в это время бот занят»: наряд **принят**, но бот придёт, только
    если слот освободится до конца встречи, и тогда **опоздание будет подписано в
    протоколе**. Портал обязан показать это в форме создания и в реестре сразу, а не
    молчать до встречи.
  * `known: false` — посчитать не удалось (нечитаемый источник); наряд всё равно принят.

## `GET /orders`, `GET /orders/<id>`

`GET /orders?status=scheduled,stopping&company=anzhee` — список (`{"orders": [...], "count": N}`).
Неизвестный статус → 400. `GET /orders/<id>` → один наряд или 404.
Идентификатор наряда детерминированный: `portal:<meeting_id>`.

## `PUT /orders/<id>` — изменить

Тело — только меняемые поля (+ необязательный `expected_version`). Всё, что не прислано,
берётся из текущего наряда.

* `expected_version` разошёлся → **409 `version_conflict`** (+ `current_version`): портал
  показывает «встречу изменил кто-то ещё», а не затирает чужую правку.
* Попытка сменить `meeting_id` → **409 `meeting_id_immutable`**: на нём держится
  идемпотентность.
* Правка **снятого** наряда возвращает его в строй (на портале «отменил и перенёс» —
  обычный сценарий).
* Правка встречи, которая уже прошла, разрешена, пока не трогается `start_at`.

## `DELETE /orders/<id>` — снять

`200` + наряд со статусом `cancelled`. Снятие несуществующего → `404`.

## `POST /orders/join-now` — «зайти сейчас»

Тело как у `/orders`, но `start_at` не нужен (проставляется «сейчас»).

* Второе нажатие по **той же комнате** — тем же или другим человеком — возвращает
  `200`, `created: false`, `already_running: true` и **тот же** наряд. Второго бота не
  поднимаем (R12.6).
* Комната сравнивается по хосту и пути; `?utm=…` и `#якорь` отбрасываются.
* Забытый разовый наряд перестаёт держать комнату через 180 минут.

## `POST /orders/leave-now` — «выйти сейчас»

`{"meeting_id": "mtg-1001"}` либо `{"room_url": "https://…"}`. Наряд получает статус
`stopping` и отметку `stop_requested_at`; штатное завершение записи (чтобы файл ушёл в
обработку, а не потерялся) делает исполняющий слой. Ни того, ни другого нет → `400`;
живого наряда по встрече/комнате нет → `404`. Повтор безвреден.

## `GET /protocol?meeting_id=…&format=md|pdf`

`200` + `text/markdown` (или `application/pdf`). Протокол ещё не собран → `404`
`protocol_not_ready`. Неизвестный формат → `400`.

## `POST /protocol/edit` — правка протокола с портала (Ф10d, R6.2/R6.3)

```json
{"meeting_id": "mtg-1001", "text": "по поставке отвечает Ольга, а не Пётр",
 "author": "Ольга Иванова", "portal_user_id": "77",
 "session_uid": "2026-08-20-tm-1755284400000", "edit_id": "portal-edit-9"}
```

🔴 **Своего окна у портала НЕТ by design.** Правка кладётся в ТО ЖЕ окно сбора, что
правка ответом в Telegram: 20 минут от последней правки, потолок 2 часа от первой,
затем одна новая версия. Встреча, которую правят и в чате, и на экране, обязана
выпустить ОДНУ следующую версию с обеими правками; заведи здесь второе окно — и
выйдут две, каждая без правок другой стороны.

* Обязательны `meeting_id`, `text`, `portal_user_id`. Без автора правку принимать
  нельзя: от него зависит и подпись в ленте версий, и право расширять цитирование.
* `session_uid` необязателен, но ускоряет поиск встречи (бот прислал его в
  результате). `edit_id` — ключ идемпотентности: повтор после таймаута сети не
  задваивает правку и не сдвигает окно ещё на 20 минут.
* **Давности здесь нет (R6.7).** Портал называет конкретную встречу, и «слишком
  старая» не является ответом ни через месяц, ни через полгода.

Ответ `200`:

```json
{"ok": true,
 "edit": {"feedback_id": "fb-koordinatsiya-2026-08-20--1001234", "kind": "first",
          "round": 1, "edits_count": 1, "window_min": 20, "max_window_min": 120,
          "deadline_at": "2026-08-20T11:12:00Z",
          "hard_deadline_at": "2026-08-20T12:52:00Z", "status": "collecting"}}
```

`deadline_at`/`hard_deadline_at` портал показывает человеку («новая версия выйдет
примерно тогда-то») — иначе экран говорит «принято» в пустоту.

| Код | Когда |
|---|---|
| `400` | нет `meeting_id` / пустой `text` / нет `portal_user_id` |
| `404` | `meeting_not_found` — протокол этой встречи бот ещё не собирал |
| `413` | `text_too_long` — правка длиннее 4000 знаков |
| `422` | `quotes_require_organizer` — см. ниже |
| `429` | `window_full` — в окне уже собран потолок правок |
| `503` | `edits_disabled` (`ENABLE_FEEDBACK_EDITS=0`) / правку принять не удалось |

🔴 **`quotes_require_organizer` (R13.2).** Правка, требующая НОВЫХ дословных цитат
из расшифровки («добавь дословно, кто что сказал»), принимается только от
организатора встречи — расшифровку видит он один, а протокол видят все. От
остальных — 422 с объяснением, которое портал показывает человеком текстом.
Обычные правки («по поставке отвечает Ольга, а не Пётр») проходят от любого
участника; детектор требует глагола-действия рядом со словом про дословность.
Аварийный выключатель на стороне бота — `ENABLE_QUOTE_POLICY=0`.

⚠️ **Это ФИЛЬТР, а не гарантия — называем вещи своими именами.** Регексп ловит
прямые формулировки («процитируй Ивана», «добавь дословно», «нужны прямые
цитаты») и НЕ ловит обходные: «приведи слова Петра целиком», «напиши точную
формулировку», «перескажи максимально близко к тексту», «добавь стенограмму
этого куска», транслит, английский, а также правку, разбитую на две безобидные
по отдельности. Замер на 23 формулировках: ловит 6, ложных срабатываний 0 —
узость честная (лучше пропустить, чем отбивать нормальные правки). Реальная
защита от расширения цитирования — ВТОРОЙ слой: инструкция `OUTSIDER_QUOTE_GUARD`
в промпт перевыпуска, когда в раунде есть правка не от организатора. Она
вероятностная (это модель, а не проверка), поэтому «расшифровка не утечёт через
правку» — это НЕ гарантия системы, а два слоя снижения риска. Обещать порталу
или пользователю гарантию нельзя.

## `GET /status` — привязки и активность

Для экранов Ф12/Ф13a: какие серии привязаны к чатам, живы ли они, сколько нарядов
активно по компаниям, размер очереди, свежесть последнего скана планировщика.

🔴 **`telegram_chat_id` наружу не отдаётся** — только факт `telegram_chat_bound: true|false`.
Порталу нужен факт привязки, а не адрес приватного чата.

`activity.portal_orders_enabled` — положение аварийного выключателя `ENABLE_PORTAL_ORDERS`.
Без него «наряды не исполняются» и «фича выключена» с портала выглядят одинаково, и
разбираться пришлось бы по логам на VPS.

## Что происходит с нарядом дальше (Ф10b, исполнение)

Шлюз по-прежнему не запускает ботов и не пишет очередь: он кладёт наряд в реестр.
Исполняет его **планировщик**, и портал вправе на это рассчитывать так:

* Наряд со статусом `scheduled` попадает в очередь стартов **наравне с личными сериями
  владельца** — отдельной очереди у портала нет (две правды = два бота в комнате).
  Одна и та же встреча, приехавшая и нарядом, и личной серией (одна комната, одна
  секунда), схлопывается в ОДИН старт; связь с нарядом при этом сохраняется. Ведёт такую
  встречу серия владельца (с 06.10.2026, код), а если серия размечена другой компанией,
  чем наряд, или помечена приватной — наряд. Протокол уходит по маршруту наряда и на портал, участники из
  наряда доходят до бота, `GET /protocol` находит протокол и в папке серии владельца.
* Ключ идемпотентности — **детерминированный `id` записи реестра** (`portal:<meeting_id>`)
  плюс минута старта. Повтор наряда второго бота не даёт; **перенос даёт новый ключ и,
  значит, повторный запуск в новое время** — включая случай, когда бот уже сидит в
  комнате по старому времени (ISS-57).
* `DELETE` (или статус `cancelled`) снимает приход: наряда нет в очереди — бот не идёт.
  Статус `stopping` («выйти сейчас») нового старта тоже не получает. С 04.10.2026 (код)
  это верно и до перестройки очереди: runner каждую минуту сверяет её строки с реестром,
  и строка снятого, «вышедшего» или перенесённого наряда (другое время или комната) из
  тика выбывает.
* **Переполнение потолка не теряет встречу.** Старт, который не смог начаться (лимит или
  живой бот той же серии), ждёт свободного слота **до конца встречи**. Освободился — бот
  заходит с опозданием, и в конце протокола появляется строка «бот подключился с
  опозданием на N мин». Не освободился — владельцу уходит «не записал» с причиной.
* `POST /orders/join-now` исполняется **минутами, а не тиком планировщика**: разовые
  наряды runner читает из реестра напрямую. Годен к запуску 20 минут после нажатия.
* **Плановый наряд, поставленный или перенесённый за минуты до начала** (с 04.10.2026,
  код), тоже не ждёт тика планировщика (раз в 3 минуты): runner каждую минуту берёт из
  реестра `scheduled`-наряды со стартом в ближайшие 5 минут — с тем же ключом старта и
  теми же защитами от второго бота, что у строки планировщика. Наряд, который портал
  завёл или изменил уже после открытия окна старта (за 5 минут до начала и позже),
  годен к запуску до 5 минут после начала; опоздание подписывается в протоколе. Портал
  вправе считать, что бот такой встречи входит на ближайшем тике runner'а — если вход
  не держат общие правила: потолок одновременных ботов (старт ждёт слота), «нет»
  владельца, живой бот той же серии.
* **Одна комната и одна секунда старта — один бот** (с 04.10.2026, код). Строк у одной
  встречи бывает несколько (личная серия владельца и наряд, два наряда на одну комнату,
  встреча, пересозданная на портале), и вести её может то одна, то другая. Поэтому при
  запуске занимается не только ключ старта, но и ключ самой встречи — комната + секунда
  начала: другая строка той же встречи второго бота уже не поднимет.

Чего исполнение НЕ делает (осознанно, отдельным нарядом): не гасит УЖЕ ЗАПУЩЕННОГО бота
при отмене и не выполняет `stopping` физически. Пока это значит: отмену, перенос и смену
комнаты ДО запуска бота (он поднимается за 5 минут до начала) бот учитывает — снятая
встреча бота не получает, перенесённая получает его в новое время и в новой комнате;
ПОСЛЕ запуска — уже нет: бот остаётся в прежней комнате, а перенос даёт новый старт,
который ждёт, пока прежний бот выйдет (см. выше, ISS-57).

Почему так было решено: в прежнем образе бота первым процессом контейнера был bash без
`exec`, и `docker stop` доходил до бота SIGKILL'ом — незакрытая `meta.json` стоила бы
записи целой встречи. В образе из ветки `telemost-resilience` (ISS-60, фаза 3а, до
выкатки) это уже не так: `entrypoint.sh` запускает node через `exec`, `docker stop -t 20`
приходит SIGTERM'ом, бот выходит из встречи штатно (`index.ts` → `gracefulShutdown`). Гасить
по отмене всё равно не начали: закрывает ли бот при таком выходе WAV и `meta.json` целиком,
живьём не проверялось — это решение отдельного наряда, не побочный эффект выкатки.

# Обратное направление: бот → портал (Ф10c)

Всё выше — портал стучится к боту. Ниже — **бот стучится к порталу**: отдаёт
результат встречи. Направление другое, источник истины тот же файл; меняешь одну
сторону — правишь его тем же коммитом.

Реализация на стороне бота — [`../lib/portal_delivery.py`](../lib/portal_delivery.py)
(очередь на диске) и [`../lib/portal_ingest.py`](../lib/portal_ingest.py) (форма тела,
ACK, отправка); пробы — `../tests/test_portal_delivery_ph10c.py`.

## `POST /api/meetings/notary/ingest`

* Адрес берётся из `MEETING_NOTARY_PORTAL_INGEST_URL`, токен — из
  `MEETING_NOTARY_PORTAL_INGEST_TOKEN` (файл окружения, права 600).
* **Только https.** Схема не https → бот НЕ отправляет вовсе (Bearer в открытом
  виде уходит навсегда) и не тратит попытку: это ошибка настройки, а не портала.
* `Authorization: Bearer <token>`, `Content-Type: application/json`.
* Заголовок `X-Notary-Delivery-Key` дублирует ключ идемпотентности: портал вправе
  отбить повтор, не разбирая тело.
* Потолок тела на стороне бота — `MEETING_NOTARY_PORTAL_INGEST_MAX_BODY`, дефолт
  8 МиБ. Не влезло — режется **транскрипт** (флаг `transcript.truncated`), затем,
  в крайнем случае, протокол (`protocol_truncated`). Полного отказа «тело
  великовато» нет by design: трёхчасовое совещание не должно потеряться целиком.

### 🔴 Имена полей — snake_case

Не `orderId`, не `deliveryKey`. В этом прогоне уже дважды ловили «две половины по
отдельности зелёные, вместе не работают» (портал слал наряд в camelCase, шлюз ждал
snake_case → 422 и ноль нарядов; портал звал ручку PDF по несуществующему адресу).
Форма ниже — дословная.

```json
{
  "delivery_key": "portal:mtg-1001#v1",
  "order_id": "portal:mtg-1001",
  "meeting_id": "mtg-1001",
  "version": 1,
  "company": "anzhee",
  "session_uid": "2026-08-20-tm-1755284400000",
  "order_status": "scheduled",
  "protocol_md": "# Протокол…",
  "protocol_truncated": false,
  "transcript": {"text": "# Полный транскрипт\n…\n**[00:04] Илья Рыбалка:** …", "truncated": false, "omitted": false},
  "tasks": [{"title": "…", "assignee": "…", "due": null}],
  "participants": ["Илья Рыбалка"],
  "expected_participants": ["Илья Рыбалка"],
  "started_at": "2026-08-20T10:00:11+03:00",
  "ended_at": "2026-08-20T10:47:03+03:00",
  "duration_seconds": 2812,
  "late_join_minutes": null,
  "telegram_delivery": {"status": "sent", "mode": "group", "reason": "requested"},
  "revision_of": null,
  "edits": [],
  "generated_at": "2026-08-20T10:52:00+00:00"
}
```

* **`delivery_key` = `<id наряда>#v<версия>`** — ключ идемпотентности приёма.
  `order_id` — тот же детерминированный `portal:<meeting_id>`, что и в реестре
  нарядов, `version` — номер версии результата (перевыпуск протокола даёт `v2`).
* ⚠️ **`tasks` бот сегодня шлёт ПУСТЫМ списком.** Машиночитаемого списка задач у
  него нет: задачи живут разделом внутри протокола, а `tasks_extracted` в
  результате финализации — это счётчики (`{"ilia": 2, "others": 1, …}`), а не
  задачи. Портал разбирает задачи из `protocol_md`. Форма поля зафиксирована на
  будущее и проверяется пробой, чтобы счётчики никогда не уехали вместо задач:
  портал ответил бы 422, то есть отказом навсегда, на КАЖДОЙ встрече.
* **PDF не пересылается** (решение №3): портал забирает его у шлюза
  `GET /protocol?meeting_id=…&format=pdf`. Гонять мегабайты через очередь ради
  файла, который пересобирается за секунду, незачем.
* `telegram_delivery.status` — факт доставки в Telegram (`sent` / `skipped` /
  `error` / `unknown`). Порталу он нужен для панели «Доставка»: без него экран
  обещает данные, которых неоткуда взять.
  * **`mode` и `reason` (Ф10d)** — КУДА и ПОЧЕМУ. `mode`: `owner` (личная серия
    владельца, наряда нет) / `dm` / `group` / `portal_only`. `reason`: `requested`
    (портал попросил полем `delivery`), `auto` (бот выбрал сам), `dm_unknown`,
    `group_unknown`, `no_target`, `no_company`, `company_mismatch`. Одного слова
    «пропущено» панели мало: человек не поймёт, поломка это или так задумано.
* **`revision_of` и `edits` (Ф10d, R6.3)** — лента версий. `revision_of` — номер
  версии, которую эта заменяет (`null` у первой доставки). `edits` — кто и откуда
  правил: `{source: "telegram"|"portal", author, portal_user_id, at, is_organizer}`.
  Ровно это портал печатает строкой в истории изменений.
  🔴 **Текста правки в `edits` НЕТ by design.** Содержание уже уехало в
  `protocol_md` применённым; дублировать его отдельным полем — значит положить в
  ленту версий сырую реплику участника, которую портал будет хранить и показывать.
  Ленте достаточно «кто, откуда, когда».
* `order_status` может быть **`cancelled`**. Это не ошибка и не повод отказать:
  разговор УЖЕ записан, а встречу отменили постфактум. Портал обязан принять
  результат и показать его как «встреча отменена, но запись есть» — потерять
  запись живого разговора из-за нажатой кнопки «отменить» нельзя.

### 🔴 Ответ: подтверждение — это НЕ код 200

Удаление исходников у бота (WAV, рабочий транскрипт) завязано на подтверждение, а
не на код ответа. Поэтому портал обязан вернуть **тело**:

```json
{"ok": true,
 "ack": {"delivery_key": "portal:mtg-1001#v1",
         "meeting_id": "mtg-1001",
         "version": 1,
         "received_at": "2026-08-20T10:52:01.412Z",
         "duplicate": false}}
```

Бот считает результат доставленным **только** при `ok: true` + объекте `ack` +
совпадении `ack.delivery_key` с отправленным. Всё остальное — повтор:

| что вернулось | как понимает бот |
|---|---|
| 200 без `ack` | не доставлено, повтор (`ack_missing`) |
| `ack.delivery_key` чужой | не доставлено, повтор (`ack_key_mismatch`) |
| `ok: false` | не доставлено, повтор (`ack_not_ok`) |
| тело не JSON | не доставлено, повтор (`ack_not_json`) |

* **Повторная доставка того же `delivery_key` обязана вернуть ТОТ ЖЕ `ack`** (с
  `duplicate: true`) и не создавать второй версии протокола. Иначе бот, не
  получивший ответ из-за оборванной сети, будет слать вечно и никогда не удалит
  исходники (об этом же говорит критерий Ф11a).

### Коды ответа и что бот с ними делает

| Код | Поведение бота |
|---|---|
| 200 + валидный `ack` | доставлено, удержание исходников снимается |
| 401 / 403 | **повтор** (токен ротировали — чинится на той стороне, это не «навсегда») |
| 404 | **повтор** (ручка ещё не выкачена) |
| 429 / 500 / 502 / 503 | **повтор** с экспоненциальной паузой |
| 413 | отказ навсегда: тело не влезло даже после ужатия → алерт владельцу |
| 422 | отказ навсегда: портал разобрал тело и не принял → алерт владельцу |
| сеть оборвалась, таймаут | **повтор** |

Паузы: 1, 2, 4, 8, затем по 15 минут (`MEETING_NOTARY_PORTAL_BACKOFF_*`), потолок
попыток — 12 (`MEETING_NOTARY_PORTAL_MAX_ATTEMPTS`), то есть около двух с
четвертью часов. Тридцатиминутное падение портала накрывается пятью попытками и
не требует ни одного ручного действия.

### 🔴 Что бот НЕ делает никогда

* **Не удаляет исходники до `ack`.** Ни после доставки в Telegram, ни после
  сборки протокола, ни по сроку хранения. Исчерпал попытки — алерт владельцу, а
  WAV и рабочий транскрипт ОСТАЮТСЯ. «Устали повторять» не основание стереть
  запись разговора; отпустить их может только человек командой
  `tools/portal-delivery.py release <ключ>`.
* **Не теряет очередь при рестарте.** Очередь лежит на диске в
  `<реестр>/.portal-delivery/` (файлы 0600, каталог 0700), в памяти процесса не
  держится ничего.
* **Не шлёт ничего при `ENABLE_PORTAL_ORDERS=OFF`** — и не создаёт ни файла, ни
  удержания. Личные серии владельца доставляются в Telegram ровно как сегодня.

## Отчёт «исходники снесены» — второй диалект той же ручки

Тот же адрес, тот же Bearer, но тело другой формы: у него есть поле `event`, и
портал по нему и различает диалекты. Отправляется **после** того, как бот
физически удалил WAV и рабочий транскрипт.

```json
{
  "meeting_id": "mtg-1001",
  "event": "sources_purged",
  "occurred_at": "2026-08-20T11:05:00+00:00",
  "order_id": "portal:mtg-1001",
  "company": "anzhee",
  "delivery_key": "portal:mtg-1001#v1"
}
```

🔴 **Зачем отдельное сообщение, если есть ACK.** ACK доказывает, что ПОРТАЛ
принял результат, и ничего не говорит о том, что бот действительно стёр запись.
Панель «Запись» различает эти состояния словами («аудио удаляется, ждём отчёта
бота» против «аудио удалено»), и без отчёта она застревает на первом навсегда —
проверить R7.9 будет нечем.

* `delivery_key` обязателен и предъявляется **тот, который портал вернул в ACK**.
  Это и есть доказательство, что отчёт про эту встречу, а не про соседнюю.
* Портал отвечает ACK той же формы, эхом того же ключа (`version: null`,
  `sources_may_be_purged: true`).
* Отчёт кладётся в **ту же durable-очередь**, что и результат: портал может
  лежать и в эту минуту, а состояние «удалено» восстановить будет уже нечем —
  исходников нет. В очереди у него свой ключ `<delivery_key>#purged`, а
  подтверждения он ждёт по ключу исходной доставки.

## Событие «бот не пришёл» (`no_show`) — тот же диалект событий

С фазы 5 плана `2026-09-23-telemost-update-resilience` бот шлёт `no_show`, когда
сторож входа (`lib/join_watch.py`) **сдался окончательно**: вход сорвался и после
повтора новым контейнером `-a2` (или повтор бессмыслен — встречи нет, бота
отклонили, ссылка не на Телемост). После первого срыва не шлётся: повтор ещё мог
спасти встречу, и «бот не пришёл» было бы ложным.

```json
{
  "meeting_id": "mtg-1001",
  "event": "no_show",
  "occurred_at": "2026-08-20T11:05:00+00:00",
  "order_id": "portal:mtg-1001",
  "company": "anzhee",
  "delivery_key": "portal:mtg-1001@20260820T1100#no_show"
}
```

* Только для встреч портала (у наряда есть `order_id`); личные серии владельца
  порталу ничего не шлют. При `ENABLE_PORTAL_ORDERS=OFF` — ничего. Наряд снят
  (`status: cancelled` — встречу отменили, пока бот пытался войти) — ничего:
  колокольчик про встречу, которую организатор сам отменил, был бы ложным.
* `delivery_key` = `<order_id>@<минута старта захода UTC>#no_show` — один на
  ЗАХОД бота, а не на встречу: повторный вызов бота по той же встрече портал
  встречает снятием вердикта (`retractBotNoShow`: снова «наряд размещён»,
  колокольчик удалён), и срыв второго захода обязан дойти до портала снова — иначе
  встреча останется «наряд размещён», потом станет «запись прервана», а загрузка
  записи вручную оттуда закрыта. Портал ключ события не разбирает, а возвращает
  эхом в ACK (`body.delivery_key ?? portal:<id>#<event>`); ACK сверяется дословно.
  Без времени старта (битый элемент журнала) — прежний `<order_id>#no_show`.
* Та же durable-очередь, что у результатов, ключ элемента — тот же: второй
  «не пришёл» того же захода не встаёт.
* Портал ставит встрече `BOT_NO_SHOW`, звонит организатору колокольчиком и
  открывает загрузку записи вручную. Исчерпание попыток — сообщение владельцу:
  «колокольчика у организатора не будет — предупреди его сам».
* Одновременно разовый наряд «зайти сейчас» закрывается (`status: finished`,
  `finish_reason: join_failed`): на стороне шлюза новое «зайти сейчас» по той же
  встрече заведёт свежий наряд. ⚠️ Сам портал сегодня повторно шлюз НЕ зовёт: пока
  встреча «идёт» по часам (разовая — 120 мин от нажатия), повторное нажатие
  открывает её карточку, а доставку повторяет только наряду, который до шлюза не
  доехал (`joinNowActions.ts`, `findLiveMeetingInRoom`). Чтобы кнопка снова звала
  бота после «бот не пришёл», нужна правка портала — хвост плана.

Остальные события хода (`bot_joined`, `transcribing`, `interrupted`) портал уже
принимает, но **бот их пока не шлёт** — это сторона Ф10d/Ф11a (статусная
машина). Пока их нет, статус «идёт запись» портал выводит своим контрольным
временем, а не сообщением бота.

## Потолки полей портала (нарушение = 422, то есть отказ навсегда)

| Поле | Потолок портала | Что делает бот |
|---|---|---|
| всё тело | 8 МиБ | режет транскрипт, затем протокол |
| `protocol_md` | 1 МиБ | режет и ставит `protocol_truncated: true` |
| `transcript.text` | 8 МиБ | режет и ставит `transcript.truncated: true` |
| `tasks` | 300 | обрезает список |
| `participants`, `expected_participants` | 300 каждый | обрезает список |
| `meeting_id` | 64 знака | ⚠️ валидатор наряда пропускает до 128 — идентификатор длиннее 64 знаков портал отвергнет навсегда. Сегодня id портала короткие, поэтому расхождение записано, а не «исправлено» вслепую |
| `started_at`, `ended_at`, `generated_at`, `occurred_at` | ISO **со смещением** (`Z` тоже принимается), 20–40 знаков | шлёт как есть из `meta` бота (`toISOString()` → `…Z`) |
