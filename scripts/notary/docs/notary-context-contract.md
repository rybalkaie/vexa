## 1. Где и в каком формате живёт знание в `*-context` (РАЗМ1)

### 1.1. Место

Каждый репозиторий контекста компании держит бот-знание в выделенном поддереве:

```
<context-repo>/knowledge/notary/
  glossary.yaml         # доменные термины (ЕДИНЫЙ источник для ASR-словаря И протокол-глоссария)
  org-structure.yaml    # ростер ролей (человек → зона ответственности → доменная лексика)
  README.md             # человекочитаемая памятка команде: как править эти файлы (PR, не push в main)
```

- `anzhee-context/knowledge/notary/…` — знание Anzhee.
- `mpfirst-context/knowledge/notary/…` — знание МПервый.

**Почему выделенное поддерево `knowledge/notary/`, а не существующие прозовые файлы**
(`company/team.md`, `restricted/finmodel-orgstruktura.md`, `company/baza-znaniy/*.md`):
бот-знание машиночитаемо и детерминированно парсится; прозовая база компании остаётся
прозой (бот её не читает). Чёткая граница «машинное / человеческое». Команда правит
`knowledge/notary/*` так же, как правит `watched.yaml` — структурированный конфиг с ревью.

### 1.2. Формат — YAML

YAML, а не JSON: знание правит КОМАНДА (двусторонняя правка, §3), а YAML человечнее
(комментарии, читаемость). Прецедент уже есть — `_config/watched.yaml` (тоже
командно-правимый структурированный конфиг). Прод-venv нотариуса уже несёт `pyyaml`
(им читается `watched.yaml` в `cli/meeting_watch.py`).

> **Дисциплина тестов.** Системный `python3` юнит-тестов pyyaml НЕ несёт. Загрузчик знания
> Ф5 (`lib/context_knowledge.py`, см. §4) обязан: (а) `import yaml` лениво внутри функции,
> не на уровне модуля; (б) тесты — `@unittest.skipUnless(yaml, …)` ИЛИ инъекция уже
> распарсенных entries (как `participant_filter` инъектируется в `series_memory`). Чистые
> проекции (§4) тестируются на вход-словаре без YAML.

### 1.3. Схема `glossary.yaml`

ЕДИНЫЙ источник терминов. Из ОДНОЙ записи выводятся ОБЕ проекции (§4):

```yaml
# knowledge/notary/glossary.yaml
version: 1
terms:
  - canonical: "РСЯ"               # каноничное написание (как должно быть в протоколе и vocab)
    scope: anzhee                  # anzhee | mpfirst | cross  (company-scope, см. 1.5)
    note: "рекламная сеть Яндекса"  # опц., человекочитаемый контекст для промпт-блока
    aliases:                       # ASR-искажения этого термина
      - "Гарсия"
      - "Гарсии"
    asr_sounds_like: true          # aliases → sounds_like в speechmatics-vocab (проекция A). Дефолт true.
    protocol_regex: true           # aliases → детерминированная regex-замена в протоколе (проекция B). Дефолт false.
  - canonical: "Bolong"
    scope: mpfirst                 # Bolong — производитель МПервый, в Anzhee не подставляется (C2)
    note: "контрагент/поставщик мини-проекторов"
    aliases: ["Лонг", "баллон"]
    protocol_regex: true
  - canonical: "ЭДО"
    scope: cross                   # кросс-компанийный термин — дублём в ОБА репо (C3), см. 1.5
    note: "электронный документооборот"
```

Поля:
- `canonical` (обяз.) — строка, как термин должен писаться.
- `scope` (обяз.) — `anzhee` | `mpfirst` | `cross`. Определяет company-scoping (1.5).
- `aliases` (опц.) — список ASR-искажений. Питают проекции A/B по флагам ниже.
- `note` (опц.) — контекст для промпт-блока генерации (проекция B, prompt).
- `asr_sounds_like` (опц., дефолт **true**) — класть `aliases` в `sounds_like` ASR-словаря.
- `protocol_regex` (опц., дефолт **false**) — делать из `aliases` детерминированные
  regex-замены в готовом протоколе. **Дефолт false осознанно**: слепая замена в тексте
  рискует затереть легитимные слова (см. docstring `glossary.py` про «следов»/«летнее»);
  включаем только для токенов без легитимного значения в домене («Гарсия», «Лонг»).

Это покрывает оба нынешних слоя `glossary.py` (промпт-блок + `_PROTOCOL_REPLACEMENTS`)
И ASR-словарь — одной записью. Недостающие термины (оффер, АКБ — REQ A3) добавляются как
обычные записи в Ф5.

### 1.4. Схема `org-structure.yaml`

Ростер ролей серии (вход для `series_roster.get_roster`, ЗАВ1/Ф5). Доменная лексика
(`keywords`) — бот-специфична (её нет в прозовом `team.md`), поэтому ростер курируется
здесь, а не парсится из прозы.

```yaml
# knowledge/notary/org-structure.yaml
version: 1
rosters:
  # ключ — slug серии (тот же, что папка в me/встречи, watched.yaml, series-display.json)
  series-ezhenedelnaya-koordinaciya-8399ea:
    company: anzhee
    roles:
      - name: "Мария Михина"
        domain: "поставки"
        keywords: ["поставк", "контейнер", "ктк", "отгруз", "таможн", "логист", "закуп"]
      - name: "Сона Енгибарян"
        domain: "коммерция"
        keywords: ["продаж", "выручк", "оффер", "акб", "лид", "клиент", "тендер"]
      # … остальные роли
```

Структура `roles[*]` 1-в-1 повторяет `series_roster.RosterEntry` (`name`/`domain`/`keywords`) —
Ф5 меняет ТОЛЬКО тело `get_roster` (источник `_STATIC_ROSTERS` → YAML), сигнатура и
потребители (`map_from_roster_domain`, `format_roster_hint`, тесты) не меняются.

### 1.5. Company-scope и кросс-компанийное (C2/C3)

- Бот выбирает репозиторий по **компании встречи** (поле `company` в разметке серии,
  заводится в Ф6 поверх `watched.yaml`): `anzhee → anzhee-context`, `mpfirst → mpfirst-context`.
- При загрузке для встречи компании X бот читает из `X-context` записи со `scope: X`
  **и** `scope: cross`. Записи `scope` другой компании в этот репо просто не кладут.
  Так «Bolong» (`scope: mpfirst`) в Anzhee-координации не подставляется (C2).
- **Кросс-компанийный термин (`scope: cross`) дублируется в ОБА репо** (план C3: «дублём в
  оба `*-context`, не в me/»). Чтобы дубли не разъехались — **lint синхронности** (Ф5):
  набор `cross`-записей в `anzhee-context` и `mpfirst-context` обязан совпадать (сверка
  по `canonical`+`aliases`). Правка одного `cross`-дубля без второго = ошибка lint
  (запускать в pre-PR проверке / вручную при правке).
- Company→repo карта живёт в коде нотариуса (маленький dict, не в `*-context` — иначе
  курица-яйцо), переопределяема env. Дефолт: `{"anzhee": "anzhee-context", "mpfirst": "mpfirst-context"}`.

## 2. Где живёт код-загрузчик (Ф5 создаёт)

Контракт фиксирует ИНТЕРФЕЙС; код пишет Ф5.

```
lib/context_knowledge.py        # Ф5: единый загрузчик YAML-знания из VPS-клона *-context
  load_glossary(company) -> list[GlossaryEntry]      # записи glossary.yaml (scope==company | cross)
  load_org_structure(company) -> dict[slug, list[RosterEntry]]
  context_root() -> Path         # $MEETING_NOTARY_CONTEXT_DIR (дефолт /srv/meeting-notary/context)
  repo_for_company(company) -> str   # company→repo-name
```

Дисциплина загрузчика (как `auto_vocab/sources.py`): нет клона/файла/битый YAML →
**пустой результат**, НЕ падаем, НЕ зануляем (graceful degradation; поведение «как до Ф5» —
fallback на текущие источники в переходный период). Best-effort.

## 3. Механизм «бот ↔ репо `*-context` на VPS» (РИСК5)

### 3.1. Топология

```
GitHub (private)                      VPS  /srv/meeting-notary/context/
  anzhee-dev/anzhee-context     ─pull→   anzhee-context/   (read-only клон бота)
  rybalkaie/mpfirst-context     ─pull→   mpfirst-context/  (read-only клон бота)
```

- `MEETING_NOTARY_CONTEXT_DIR=/srv/meeting-notary/context` (env, `.env.notary`) — корень,
  где лежат клоны. Загрузчик (§2) резолвит `<context-dir>/<repo>/knowledge/notary/*.yaml`.
- На маке (dev / LOCAL_FINALIZE=0) дефолт — `~/Projects/<repo>` (там клоны уже есть).

### 3.2. READ-путь (дефолт, безопасный) — клон + pull, read-only

- Бот **читает знание read-only**. Никаких локальных коммитов в эти клоны на read-пути.
- Обновление: **systemd-таймер `meeting-notary-context-pull`** (зеркало существующего
  `meeting-notary-vocab-sources` — ежедневный pull, можно чаще) делает на каждом клоне
  `git -C <clone> fetch && git reset --hard origin/HEAD` (НЕ merge — у бота нет локальных
  правок на read-пути, hard-reset к origin исключает конфликты вовсе). Сбой сети → клон
  остаётся на последнем good-состоянии (degradation), бот читает что есть.
- **Credentials READ:** выделенный **fine-grained PAT / deploy-token**, scope =
  `contents: read` ТОЛЬКО на эти два репо, выданный machine-user'у (НЕ личный токен
  Михаила/Татьяны). Хранится как `NOTARY_CONTEXT_GIT_TOKEN` в `vexa/.env.notary`.
  Клон через `https://x-access-token:${NOTARY_CONTEXT_GIT_TOKEN}@github.com/<org>/<repo>.git`
  ИЛИ ssh deploy-key (read-only) на репо. Токен — в URL remote'а на диске VPS только в
  git-config клона (0600), не в коде, не в логах.

### 3.3. WRITE-BACK (Ф7, авто-выученное знание) — через PR, НЕ прямой push в main

Когда бот сам предлагает знание (Ф7, D1/D2 — auto_vocab → контекст компании):

- Бот пишет правку в **отдельную ветку** (`notary/auto-knowledge`), правит ТОЛЬКО
  `knowledge/notary/*` (своё поддерево — не пересекается с прозой команды), и **открывает PR**
  в `*-context`. **Прямой push в `main` командного репо ЗАПРЕЩЁН** (safe default).
- Михаил/Татьяна ревьюят и мёржат PR — это и есть «бот вносит, раз в неделю отчитывается,
  команда корректирует» (D2): отчёт = ссылка на PR / дайджест внесённого.
- **Credentials WRITE — ОТДЕЛЬНЫЙ токен** `NOTARY_CONTEXT_GIT_WRITE_TOKEN` (scope
  `contents: write` + `pull_requests: write` на два репо) ИЛИ `gh auth` machine-user'а.
  Разделён с read-токеном: компрометация read-пути не даёт записи.
- **Разрешение конфликтов при двусторонней правке команды:**
  - Команда правит `main` напрямую (человек). Бот — только через ветку+PR.
  - Перед открытием PR бот **пересоздаёт ветку от свежего `origin/main`** (rebase/recreate),
    так что PR всегда поверх последнего состояния — команда не «перетёрта».
  - Бот пишет ТОЛЬКО `knowledge/notary/` → текстовых конфликтов с прозой команды нет
    по построению; конфликт возможен только внутри bot-поддерева и решается ревьюером PR.
  - Бот **никогда не делает force-push в `main`**, никогда не мёржит свой PR сам.

### 3.4. Что делает живой человек (control — НЕ автоном)

Этот контракт ПРОЕКТИРУЕТ механизм. **Реально выдаёт доступ / выпускает токены / делает
первый push в боевой `*-context` — владелец** (control: секреты + командные репо с
конфиденциальным знанием). Пробное чтение/запись — в тестовый/локальный клон, не в боевой
командный репо (см. §7 проверка).

## 4. Один источник → две проекции (НЕС2 / РИСК2)

`glossary.yaml` (§1.3) — ЕДИНЫЙ источник. Из него Ф5 строит ДВЕ проекции, обе из одного
`load_glossary(company)`:

```
                         load_glossary(company)            ← lib/context_knowledge.py (§2)
                          /                     \
        Проекция A: ASR-словарь            Проекция B: протокол-глоссарий
        speechmatics-vocab                 glossary.py
        {content: canonical,               (1) PROJECT_GLOSSARY_PROMPT_BLOCK  ← canonical+note+aliases
         sounds_like: aliases}                 (промпт генерации)
        (если asr_sounds_like)             (2) _PROTOCOL_REPLACEMENTS  ← aliases→canonical
                                               (regex по готовому протоколу, если protocol_regex)
```

- **Проекция A (ASR, `auto_vocab/sources.py` → speechmatics-vocab):** для каждой записи
  с `asr_sounds_like` эмитит `{content: canonical, sounds_like: aliases}`, company-scoped.
  Питает движок ASR (Speechmatics) ДО распознавания.
- **Проекция B (протокол, `glossary.py`):** `PROJECT_GLOSSARY_PROMPT_BLOCK` и
  `_PROTOCOL_REPLACEMENTS` становятся ФУНКЦИЯМИ, строящими блок/список из
  `load_glossary(company)`. Применяется ПОСЛЕ генерации протокола (`llm_postprocess.py:1429`).

**Инвариант синхронности (РИСК2): Ф5 переносит ОБЕ проекции ОДНИМ шагом.** Если перенести
только одну (напр. ASR на YAML, а `glossary.py` оставить хардкодом) — LLM чинит протокол по
новому источнику, regex по старому → рассинхрон качества дайджеста. Обе проекции обязаны
читать `load_glossary` синхронно. Это явный критерий приёмки Ф5.

## 5. Канал доставки знания/словаря на VPS (УПУ3)

Сегодня деплой копирует локальные json (`make deploy-notary` — код; `make deploy-vocab` —
`config/speechmatics-vocab.json`). Знание `*-context` доставляется ОТДЕЛЬНЫМ каналом —
git-pull клонов (не rsync с мака): источник истины знания = GitHub-репо команды, не мак.

**Новый канал — `make deploy-context`** (корневой `Makefile`, рядом с `deploy-notary`/
`deploy-vocab`) + рекуррентный systemd-таймер на VPS:

```
make deploy-context            # первичный клон ОБОИХ репо на VPS (idempotent: clone | pull)
                               #   читает NOTARY_CONTEXT_GIT_TOKEN из .env.notary, scope read-only
systemd: meeting-notary-context-pull.{service,timer}   # ежедневный git fetch + reset --hard origin
```

- `deploy-context` — РАЗОВЫЙ bootstrap (как `deploy-vocab`), запускает **живой человек**
  (нужен реальный токен — §3.4). Дальше клоны поддерживает таймер.
- Соотношение каналов: **код** → `deploy-notary` (rsync мак→VPS); **ASR-словарь** →
  `deploy-vocab` (scp json) + проекция A пишет в него из знания; **знание** → `deploy-context`
  (git-pull из GitHub). `me-mirror`/`methods-push` (зеркало `~/Projects/me/` мак→VPS) знание
  НЕ несут — оно развязано от `me/` (C4, Ф6).

> Реализацию таймера (`.service`/`.timer`) и боевой `deploy-context` проводит Ф5/владелец.
> Ф4 фиксирует канал и его дефолты. `make deploy-context` Ф4 добавляет в корневой `Makefile`
> как готовую команду (инертна без токена; запуск — человек).

## 6. Прод-синк памяти серии `*-memory.json` (наследие Ф2 → Ф4, task 5)

**Проблема (Ф2 §5):** finalize пишет `<date>-memory.json` рядом с протоколом в свой
output-dir; коллектор тащил на долговечную сторону ТОЛЬКО `.md` → на бою память серии не
доезжала в архив владельца.

**Решение (реализовано в Ф4, НЕ через `get_series_root`):** коллектор `_do_finalize_and_collect`
синкает sidecar-файл памяти рядом с протоколом тем же транспортом, что и `.md`:
`collector.py::_sync_series_memory`. Подробности — в коде (docstring) и в пакете сдачи Ф4.

- Имя файла памяти выводится из протокола-источника (`<date>.md` → `<date>-memory.json`,
  `series_memory.MEMORY_FILE_SUFFIX`) — date-ключ совпадает с тем, что писал finalize.
- **Защитно к топологии:** если output-dir finalize == долговечный корень (память уже на
  месте) — синк видит `src == dst` и пропускает (no-op). Если output-dir эфемерный — копирует.
- Best-effort: память — вторичный артефакт, сбой синка НЕ влияет на доставку протокола и
  НЕ алертит владельца. Содержимое не читается/не логируется (РИСК4/ПДн).

**Граница (для Ф8, боевой регресс):** синк гарантирует ВИДИМОСТЬ + ДОЛГОВЕЧНОСТЬ памяти в
архиве. Накопление памяти на READ-стороне finalize (он читает `resolve_memory` из своего
output-dir) работает, пока output-dir персистентен между встречами (`/opt/.../_tmp` — диск,
не OS-tmp, переживает перезагрузку). Ф8 подтверждает накопление на бою; если output-dir
когда-либо чистится при деплое — durable-копия (этот синк) + переключение READ-корня на
durable станут страховкой (отдельный follow-up, НЕ Ф4: это правка READ-пути finalize).

## 8. Безопасность (опасная тройка + секреты)

- Знание (`knowledge/notary/*`) — производные термины/роли/доменная лексика, **НЕ ПДн сверх
  уже публичного** (имена и так в составе встреч). Сырьё реплик сюда не попадает.
- Полные протоколы групповых координаций в `*-context` НЕ кладём (туда течёт знание, не
  сырьё — РИСК1). Круг читателей `*-context` = Михаил/Татьяна; публикация знания гейтится
  типом встречи (Ф6, E1–E5).
- Токены — только `.env.notary` (read и write раздельны, §3.2/3.3), scoped на два репо,
  machine-user. Не в коде, не в git-истории, не в логах, не в auto-memory.
- Бот в WRITE-back пишет ТОЛЬКО `knowledge/notary/` своей ветки; не трогает `restricted/`,
  прозу, чужие поддеревья; не мёржит сам.

## 9. Журнал решений Ф4 (safe defaults, режим to-the-end)

| Развилка | Решение | Почему safe |
|---|---|---|
| Место знания | `<repo>/knowledge/notary/` (выделенное поддерево) | граница машинное/человеческое; не конфликтует с прозой команды |
| Формат | YAML | командно-правимо (как watched.yaml), прод-venv несёт pyyaml |
| Доступ READ | read-only PAT/deploy-token, scoped 2 репо, machine-user | компрометация не даёт записи; не личные креды М/Т |
| Доступ WRITE (Ф7) | отдельный токен, ветка+**PR**, не push в main | команда на main не перетирается; ревью-гейт |
| Конфликты | бот пишет только своё поддерево, ветка от свежего origin, no force-push | двусторонняя правка без коллизий по построению |
| Канал | `deploy-context` (git-pull) + systemd-таймер, отдельно от deploy-vocab | источник знания = GitHub команды, не мак; развязка от me/ |
| Кросс-термины | дубль в оба репо, `scope: cross`, lint синхронности | соответствует плану C3; lint ловит расхождение дублей |
| Прод-синк памяти | синк sidecar в коллекторе, защитно к src==dst | НЕ get_series_root (исключён); работает в обеих топологиях |

**Эскалация (НЕ автоном):** реальная выдача доступа, выпуск токенов, первый боевой push в
`*-context`, провижн systemd-таймера на VPS, боевой `make deploy-context` — control,
запускает владелец. Ф4 спроектировала и зафиксировала; боевое включение — Ф5+/владелец.
